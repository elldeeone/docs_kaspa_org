## From Blockchain to BlockDAG

Traditional blockchains enforce a strict linear sequence of blocks. When two miners find a block at roughly the same time, only one can be included in the canonical chain; the other becomes an orphan and its work is discarded. This fundamental constraint limits how fast blocks can be produced: if the block rate is too high relative to network propagation time, orphan rates spike and security degrades.

Kaspa replaces this linear chain with a **BlockDAG** (Directed Acyclic Graph). In a BlockDAG, each block can reference **multiple parent blocks** rather than a single parent. This means that blocks created in parallel by different miners are all incorporated into the ledger.

<Callout>
In Kaspa's BlockDAG, parallel blocks created by honest miners are incorporated into the DAG structure. The GHOSTDAG protocol classifies blocks as either blue (part of the selected chain) or red (merged but not in the main chain). Both contribute to transaction throughput, though red blocks do not add to the main chain's accumulated proof-of-work in the same way blue blocks do.
</Callout>

## How the DAG Structure Works

Every Kaspa block header contains a `parents_by_level` structure — a run-length encoded list of parent hashes at multiple DAG levels — rather than a single `prevBlockHash`. When a miner constructs a new block, it references **up to `max_block_parents`** of the current DAG tips. This value is derived from `ghostdag_k / 2`, clamped to a minimum of 10 and a **hard maximum of 16**. At 10 BPS (`k=124`), `k/2 = 62` far exceeds the cap, so `max_block_parents` is 16. This cap is a performance optimization to prevent parent references per round from growing too quickly with BPS. Implementations choose parents from available tips under consensus constraints (for example, blue-work ordering and mergeset rules), and parent-selection heuristics may evolve across node versions.

This produces a graph with the following properties:

- **Directed**: Edges point from child blocks to their parents (backward in time).
- **Acyclic**: No block can be its own ancestor; the graph has no cycles.
- **Convergent**: Even if miners produce blocks concurrently, the DAG structure ensures all blocks are eventually seen and included by subsequent blocks.

A simplified DAG might look like this:

```
        ┌──── B2 ────┐
        │             │
  B0 ── B1 ── B3 ──── B5 ── B6
        │             │
        └──── B4 ────┘
```

In this example, `B5` references `B2`, `B3`, and `B4` as parents. All three blocks are included in the DAG despite having been created in parallel.

## Block Rate and Throughput

Kaspa currently operates at **10 blocks per second (10 BPS)**, having transitioned from 1 BPS via the Crescendo hardfork activation. This is possible because the BlockDAG architecture decouples the block rate from the orphan rate. In a traditional blockchain, pushing the block rate to 10 BPS would result in catastrophic orphan rates and compromise security. In a BlockDAG, parallel blocks are simply merged into the graph.

The relationship between block rate, network delay, and security is governed by the GHOSTDAG protocol's `k` parameter, which sets an upper bound on the number of parallel blocks expected within one network propagation delay. The `k` value is calculated using the formula from the PHANTOM paper (equation 1, section 4.2), where `x = 2Dλ` — `D` is the estimated network delay bound (5 seconds), `λ` is the block rate, and the factor of 2 provides a safety margin. For 10 BPS, this gives `x = 2 × 5 × 10 = 100`, yielding `k = 124` with a delta (probability bound) of 0.01 (1%). As long as honest miners produce fewer than `k` parallel blocks during propagation, the protocol can distinguish honest blocks from adversarial ones with high confidence.

<Callout type="info">
At 10 BPS, the target interval between blocks is 100 milliseconds, so first inclusion can happen quickly under normal network conditions. Finality remains probabilistic and is associated with much deeper confirmation depth (for example, ~12 hours at a finality depth of 432,000 blocks at 10 BPS).

All parameter values on this page reflect **production mainnet** configuration. Simulation environments may use different tuning values for research and stress testing.
</Callout>

## Parallel Block Creation

Because all blocks are included, miners do not need to "race" in the same way they do on a traditional blockchain. Two miners who find valid blocks within milliseconds of each other both have their blocks accepted. This has several consequences:

- **Fairness**: Compared with longest-chain systems where parallel blocks are discarded, including parallel blocks can reduce connectivity advantages for better-connected miners.
- **Throughput**: The total transaction throughput is the aggregate of all blocks, not limited to a single block per interval.
- **Security**: The total proof-of-work securing the network includes every mined block, not just those on the longest chain.

## Ordering: A Post-Hoc Process

A key insight of the BlockDAG design is that **block ordering does not need to happen at creation time**. Miners simply add blocks to the DAG. The [GHOSTDAG protocol](/docs/core-concepts/ghostdag) then determines a canonical ordering of all blocks after the fact.

This separation of concerns — block production versus block ordering — is what allows the system to scale the block rate without sacrificing consensus security. Ordering is computed locally by each node using the same deterministic algorithm, so all nodes agree on the same canonical sequence of transactions.

## DAG Width and Network Conditions

The "width" of the DAG at any point in time reflects the degree of concurrency in block production. Under normal network conditions with 10 BPS, the DAG typically has a width proportional to the product of the block rate and the network propagation delay (`D × λ`). With an estimated network delay bound (`D`) of 5 seconds and a block rate (`λ`) of 10 BPS, roughly 50 blocks might exist in parallel at any moment. The GHOSTDAG `k` parameter (124 for 10 BPS) is computed using `2Dλ = 100` with a safety factor of 2, ensuring that even under worst-case propagation the protocol correctly classifies blocks with probability exceeding 99%.

The GHOSTDAG protocol classifies blocks into blue (honest majority) and red (potentially adversarial) sets, and constructs a linear ordering from the DAG that respects the causal relationships encoded by parent references.

## Advantages Over Traditional Blockchains

| Property | Traditional Blockchain | Kaspa BlockDAG |
|---|---|---|
| Block references | Single parent | Multiple parents |
| Parallel blocks | Orphaned (wasted) | All included |
| Block rate | Limited by propagation | 10 BPS (and beyond) |
| Miner fairness | Favors well-connected miners | Proportional to hash rate |
| PoW utilization | Partial (orphans wasted) | Full (all blocks count) |
| First confirmation | Minutes | ~100ms target interval (actual inclusion varies) |
