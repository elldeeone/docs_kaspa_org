## What Is SPV?

**Simplified Payment Verification (SPV)** is a method that allows a client to verify that a transaction has been included in the ledger without downloading and validating the entire blockchain (or, in Kaspa's case, the entire BlockDAG). SPV was first described by Satoshi Nakamoto in the Bitcoin whitepaper as a way to enable lightweight wallets.

An SPV client downloads only block headers rather than full blocks. Since headers are small (a few hundred bytes each versus potentially megabytes for a full block), an SPV client can operate with a fraction of the storage and bandwidth requirements of a full node.

<Callout>
SPV clients trust that the majority of hash power is honest — they verify proof-of-work and block inclusion but do not independently validate every transaction in every block.
</Callout>

<Callout type="info">
This page is conceptual guidance. Kaspa does not currently define a single canonical "SPV client implementation spec" in this docs section.
</Callout>

## SPV in a BlockDAG Context

SPV in Kaspa's BlockDAG is conceptually similar to SPV in Bitcoin, but the DAG structure introduces additional considerations:

### Multiple Parents

In a traditional blockchain, each block header points to a single parent, forming a simple chain of headers. An SPV client can follow this chain from the genesis block to the current tip. In Kaspa, each block header references **multiple parents**, so the SPV client must track a DAG of headers rather than a linear chain.

This means an SPV client needs to:

1. Download and store the DAG of block headers.
2. Determine canonical ordering information from trusted node responses and/or local header processing, depending on client design.
3. Track selected-parent/blue-score progress used by the chosen verification strategy.

### Header Volume

At 10 BPS, Kaspa produces approximately 864,000 block headers per day. While each header is small, the aggregate volume is significantly larger than what a Bitcoin SPV client would encounter (~144 headers per day). SPV clients in Kaspa need to account for this higher header throughput in their sync and storage strategies.

<Callout type="info">
Despite the higher header volume, headers are still much smaller than full blocks. Storage impact depends on the wallet's sync strategy, retention policy, and encoding.
</Callout>

## Proof-of-Inclusion

To verify that a specific transaction was included in the DAG, an SPV client requests a **proof-of-inclusion** from one or more full nodes. A typical proof package can include:

1. **Merkle proof**: A cryptographic proof that the transaction is included in a specific block's Merkle tree. This is the same mechanism used in Bitcoin — the block header contains the Merkle root of all transactions in the block, and the proof provides the sibling hashes along the path from the transaction to the root.

2. **Block header**: The header of the block containing the transaction, which the client can validate for proof-of-work and parent-link consistency.

3. **Ordering/finality evidence**: Depending on the client model, ordering confidence can come from local header processing, trusted checkpoints, or multi-peer cross-checking.

The SPV client can then verify, under its chosen trust model:

- The transaction is included in the block (via the Merkle proof).
- The block is part of the DAG (via parent references to known headers).
- The block has a valid proof-of-work.
- The transaction has reached the confirmation depth required by the wallet's policy.

## GHOSTDAG-Aware Verification

A key difference between SPV in Kaspa and SPV in Bitcoin is that some Kaspa light-client designs include **GHOSTDAG-aware** logic. Depending on design, this can include:

- **Blue/red awareness** for confidence heuristics.
- **Blue-score depth tracking** rather than linear-chain block counts.
- **Selected-parent progression** to reason about canonical ordering conflicts.

## Security Considerations

SPV clients in Kaspa inherit the same fundamental security assumptions as SPV clients in Bitcoin:

### Honest Majority Assumption

SPV clients assume that the majority of hash power follows the protocol honestly. If an attacker controls a majority of the hash power, they could potentially present an SPV client with a fraudulent chain of headers containing fabricated transactions.

### Eclipse Attacks

An SPV client that connects only to adversarial nodes could be fed a false view of the DAG. Mitigations can include:

- Connecting to multiple independent peers.
- Using checkpoints from trusted software releases or independent sources.
- Cross-referencing header data from multiple sources.

### Transaction Withholding

A full node could prove that a transaction is included in a block but withhold information about a conflicting transaction in a different block that takes precedence in the GHOSTDAG ordering. SPV clients mitigate this by waiting for sufficient confirmations before considering a transaction final.

<Callout>
SPV provides practical security for everyday transactions. For high-value transfers, users should wait for deeper confirmations or use a full node for verification.
</Callout>

## Light Client Sync Strategies (Conceptual)

Given the high header volume in Kaspa, light clients can employ several strategies to reduce sync time and resource usage. These are design options, not protocol-mandated behavior:

### Header Checkpoints

Some clients can ship with recent checkpoints (or trusted sync anchors) and then verify forward from that point, reducing initial sync time.

### Header Compression

Compression techniques can reduce the bandwidth required to transmit headers between full nodes and light clients.

### Selective Header Download

For clients that only need recent activity, downloading from a recent trusted point can reduce sync cost. Security tradeoffs depend on what trust anchors and proofs are used.

### UTXO Commitment Verification

Kaspa block headers include a commitment to the UTXO set. A light client can use this in snapshot-validation flows, but commitment matching alone does not replace full historical inclusion proofs for arbitrary past transactions.

## Mobile Wallet Implications

SPV is particularly important for mobile wallets, which operate under constraints of limited storage, bandwidth, and processing power. Depending on wallet design, light-client mode can enable mobile wallets to:

- **Verify incoming payments** from proof packages returned by full nodes.
- **Track wallet-relevant activity** using the wallet's indexing/sync method.
- **Submit signed transactions** to connected full nodes.
- **Track confirmations** with wallet-defined confidence thresholds.

The main tradeoff is header-sync cost versus trust assumptions. For example, a client offline for a day may need to process on the order of ~864,000 new headers at 10 BPS unless it uses checkpointed/trusted sync shortcuts.
