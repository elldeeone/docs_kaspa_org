## What Is SPV?

**Simplified Payment Verification (SPV)** is a method that allows a client to verify that a transaction has been included in the ledger without downloading and validating the entire blockchain (or, in Kaspa's case, the entire BlockDAG). SPV was first described by Satoshi Nakamoto in the Bitcoin whitepaper as a way to enable lightweight wallets.

An SPV client downloads only block headers rather than full blocks. Since headers are small (a few hundred bytes each versus potentially megabytes for a full block), an SPV client can operate with a fraction of the storage and bandwidth requirements of a full node.

<Callout>
SPV clients trust that the majority of hash power is honest — they verify proof-of-work and block inclusion but do not independently validate every transaction in every block.
</Callout>

## SPV in a BlockDAG Context

SPV in Kaspa's BlockDAG is conceptually similar to SPV in Bitcoin, but the DAG structure introduces additional considerations:

### Multiple Parents

In a traditional blockchain, each block header points to a single parent, forming a simple chain of headers. An SPV client can follow this chain from the genesis block to the current tip. In Kaspa, each block header references **multiple parents**, so the SPV client must track a DAG of headers rather than a linear chain.

This means an SPV client needs to:

1. Download and store the DAG of block headers.
2. Run a local copy of the GHOSTDAG algorithm on the headers to determine the canonical ordering and blue/red classification.
3. Identify the selected parent chain (the "spine" of the DAG).

### Header Volume

At 10 BPS, Kaspa produces approximately 864,000 block headers per day. While each header is small, the aggregate volume is significantly larger than what a Bitcoin SPV client would encounter (~144 headers per day). SPV clients in Kaspa need to account for this higher header throughput in their sync and storage strategies.

<Callout type="info">
Despite the higher header volume, Kaspa block headers are compact. The total header data for an entire year at 10 BPS is still manageable for modern mobile devices, on the order of a few gigabytes.
</Callout>

## Proof-of-Inclusion

To verify that a specific transaction was included in the DAG, an SPV client requests a **proof-of-inclusion** from a full node. This proof consists of:

1. **Merkle proof**: A cryptographic proof that the transaction is included in a specific block's Merkle tree. This is the same mechanism used in Bitcoin — the block header contains the Merkle root of all transactions in the block, and the proof provides the sibling hashes along the path from the transaction to the root.

2. **Block header**: The header of the block containing the transaction, which the SPV client can verify is part of the DAG by checking its parent references and proof-of-work.

3. **DAG position**: The SPV client uses its local GHOSTDAG computation to determine where the block falls in the canonical ordering and how many confirmations (blue score depth) the block has accumulated.

The SPV client can then verify:

- The transaction is included in the block (via the Merkle proof).
- The block is part of the DAG (via parent references to known headers).
- The block has a valid proof-of-work.
- The block is in the blue set and has sufficient confirmations (via local GHOSTDAG computation).

## GHOSTDAG-Aware Verification

A key difference between SPV in Kaspa and SPV in Bitcoin is that Kaspa SPV clients must be **GHOSTDAG-aware**. This means:

- **Blue set verification**: The client must determine whether the block containing their transaction is in the blue set. A transaction in a red block may still be valid, but it has a different security profile than one in a blue block.
- **Confirmation depth**: Instead of counting blocks on top of the transaction's block (as in Bitcoin), the client counts the increase in blue score since the block was added. This provides a more accurate measure of finality in a DAG.
- **Selected chain awareness**: The client should track the selected parent chain to determine the canonical ordering of transactions and detect potential conflicts.

## Security Considerations

SPV clients in Kaspa inherit the same fundamental security assumptions as SPV clients in Bitcoin:

### Honest Majority Assumption

SPV clients assume that the majority of hash power follows the protocol honestly. If an attacker controls a majority of the hash power, they could potentially present an SPV client with a fraudulent chain of headers containing fabricated transactions.

### Eclipse Attacks

An SPV client that connects only to adversarial nodes could be fed a false view of the DAG. Mitigations include:

- Connecting to multiple independent peers.
- Using hardcoded checkpoints for known-good DAG states.
- Cross-referencing header data from multiple sources.

### Transaction Withholding

A full node could prove that a transaction is included in a block but withhold information about a conflicting transaction in a different block that takes precedence in the GHOSTDAG ordering. SPV clients mitigate this by waiting for sufficient confirmations before considering a transaction final.

<Callout>
SPV provides practical security for everyday transactions. For high-value transfers, users should wait for deeper confirmations or use a full node for verification.
</Callout>

## Light Client Sync Strategies

Given the high header volume in Kaspa, SPV clients can employ several strategies to reduce sync time and resource usage:

### Header Checkpoints

The client can ship with recent header checkpoints — known-good points in the DAG that have been verified by the developer community. The client only needs to download and verify headers from the most recent checkpoint forward, significantly reducing initial sync time.

### Header Compression

Block headers in the DAG contain repeated information (such as parent hashes that appear in multiple headers). Compression techniques can reduce the bandwidth required to transmit headers between full nodes and SPV clients.

### Selective Header Download

For clients that only need to verify recent transactions, it may be sufficient to download only the headers from a recent pruning point forward, rather than the entire header history. Combined with UTXO commitments in headers, this allows a client to verify the current state without processing the full header DAG.

### UTXO Commitment Verification

Kaspa block headers include a commitment to the UTXO set. An SPV client can download a UTXO snapshot at a recent point and verify it against the header commitment. This allows the client to check whether a specific UTXO exists (and thus whether a payment has been received) without needing a full Merkle proof for the historical transaction.

## Mobile Wallet Implications

SPV is particularly important for mobile wallets, which operate under constraints of limited storage, bandwidth, and processing power. Kaspa's SPV model enables mobile wallets to:

- **Verify incoming payments** by requesting Merkle proofs from full nodes and checking them against locally stored headers.
- **Monitor the UTXO set** for outputs addressed to the wallet's keys.
- **Submit transactions** by broadcasting signed transactions to connected full nodes.
- **Track confirmations** by following the DAG's growth and computing blue score increases for pending transactions.

The main tradeoff is that mobile wallets must either download a significant number of headers or rely on trusted checkpoints. With Kaspa's header rate, a mobile client that has been offline for a day would need to sync approximately 864,000 headers upon reconnection. Efficient sync protocols and checkpoint mechanisms make this practical on modern mobile hardware.
