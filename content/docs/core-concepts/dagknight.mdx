## Overview

DAGKnight is a consensus protocol designed to operate on BlockDAG structures, developed as the natural successor to GHOSTDAG. Its defining innovation is that it is **parameterless** — it does not require a predetermined `k` value to distinguish honest blocks from adversarial ones. Instead, DAGKnight dynamically adapts to the actual network conditions it observes, achieving optimal confirmation times without making assumptions about network propagation delay.

<Callout>
DAGKnight removes the need to fix a delay parameter in advance. GHOSTDAG requires choosing `k` based on an estimated upper bound on network delay (`D`); DAGKnight achieves consensus without this assumption, making it robust to changing network conditions.
</Callout>

## From GHOSTDAG to DAGKnight

GHOSTDAG operates with a fixed parameter `k` that is calculated from the expected network delay bound `D` and the block rate `λ`. For Kaspa at 10 BPS, `k = 124`, computed assuming a 5-second delay bound with a 1% probability threshold. This works well when the actual network delay stays within the assumed bound, but it introduces a fundamental tradeoff:

- **If `D` is overestimated**: The protocol is safe but confirmation times are slower than necessary, because `k` is larger than needed.
- **If `D` is underestimated**: The protocol may misclassify honest blocks as red, potentially degrading security.

DAGKnight eliminates this tradeoff entirely. It does not take `D` as an input parameter. Instead, it infers the effective delay from the DAG structure itself and adjusts its behavior accordingly.

| Property | GHOSTDAG | DAGKnight |
|---|---|---|
| Delay parameter | Fixed `k` based on estimated `D` | None — adapts automatically |
| Confirmation time | Depends on chosen `k` | Optimal for actual conditions |
| Security assumption | Bounded network delay | Honest majority only |
| Block classification | Blue/red via k-cluster | Blue/red via adaptive analysis |

## How DAGKnight Works

DAGKnight analyzes the structure of the DAG to determine consensus ordering. At a high level, it works by examining the relationship between any two blocks and determining their relative order based on how the rest of the network's blocks relate to them.

For two blocks `X` and `Y` in the DAG, DAGKnight considers the blocks that are in the "future" of `X` but not `Y`, and vice versa. If significantly more blocks build on `X` than on `Y`, the protocol concludes that `X` came first and should precede `Y` in the ordering. The key insight is that honest miners, who see `X` before `Y`, will naturally build on `X` — and the DAG structure records this collective behavior.

The protocol achieves this without knowing the delay `D` because:

1. **The DAG encodes timing information implicitly**: Blocks that were produced close together in time tend to be in each other's anticones, while blocks separated by significant time tend to have ancestor/descendant relationships.
2. **Honest majority behavior is observable**: When a majority of hash power is honest, their block-building patterns reveal the true temporal ordering of blocks.
3. **Adaptive thresholds**: Rather than using a fixed `k` to classify blocks, DAGKnight computes ordering confidence from the observed DAG topology.

## Optimal Confirmation Times

One of DAGKnight's most important theoretical properties is that it achieves **asymptotically optimal confirmation times**. This means that for any given network delay `D` and attacker hash rate, no other consensus protocol can consistently confirm transactions faster than DAGKnight.

In GHOSTDAG, confirmation time is bounded by the chosen `k`, which is calibrated for the worst-case delay. If the actual delay is much lower than the assumed bound, users still wait longer than necessary. DAGKnight, by contrast, automatically provides faster confirmations when the network is performing well and slower (but still safe) confirmations when conditions degrade.

<Callout type="info">
DAGKnight achieves the theoretical minimum confirmation latency for any given attacker fraction and network delay — without needing to know the delay in advance. This is a provably optimal result from the DAGKnight paper.
</Callout>

## Formal Security Properties

The DAGKnight paper (Sompolinsky and Zohar, 2022) establishes the following security properties:

- **Safety**: Under an honest majority assumption (attacker controls less than 50% of hash power), DAGKnight guarantees that confirmed transactions will not be reversed, regardless of the actual network delay.
- **Liveness**: Transactions submitted by honest users will eventually be confirmed, even under adversarial network conditions (as long as the honest majority holds).
- **Optimality**: The confirmation time achieved by DAGKnight is asymptotically optimal — no protocol can do better without additional assumptions about the network.

These properties hold without any assumption about an upper bound on network delay `D`. The only requirement is that a majority of mining power follows the protocol honestly.

## The DAGKnight Paper

The protocol was formally presented in the paper "DAGKnight: A Parameterless Generalization of Nakamoto Consensus" by Yonatan Sompolinsky and Aviv Zohar (2022). The paper proves that parameterless consensus is achievable in the BlockDAG setting and provides the DAGKnight construction as a concrete protocol achieving this goal.

Key contributions of the paper include:

- A formal definition of parameterless consensus and what it means for a protocol to be "optimal."
- The DAGKnight protocol construction and its proof of security.
- Analysis showing that DAGKnight's confirmation times match a known lower bound, establishing optimality.
- A comparison framework between parameterized protocols (like GHOSTDAG) and parameterless ones.

## Current Status

Kaspa currently runs **GHOSTDAG** as its consensus protocol. DAGKnight represents the planned next step in Kaspa's consensus evolution.

The transition from GHOSTDAG to DAGKnight is a significant protocol upgrade that requires:

- **Implementation**: Translating the theoretical protocol into production-quality code within the rusty-kaspa node.
- **Testing**: Extensive simulation and testnet validation to ensure correctness under diverse network conditions.
- **Hard fork coordination**: Deploying DAGKnight requires a network-wide hard fork, since the consensus rules change fundamentally.

<Callout>
GHOSTDAG is the battle-tested consensus protocol running on Kaspa mainnet today. DAGKnight is the theoretical successor that eliminates the need for a fixed delay parameter. The upgrade path from GHOSTDAG to DAGKnight is a key item on Kaspa's research and development roadmap.
</Callout>

## Relationship to GHOSTDAG

DAGKnight and GHOSTDAG share the same foundational ideas — both operate on a BlockDAG, both classify blocks into blue and red sets, and both produce a total ordering of blocks. The critical difference is how they determine the blue/red classification:

- **GHOSTDAG**: Uses the fixed parameter `k` to define a k-cluster constraint. Blocks whose blue anticone exceeds `k` are classified as red.
- **DAGKnight**: Determines classification adaptively by analyzing the DAG structure, without a fixed threshold.

Because DAGKnight generalizes GHOSTDAG, the existing BlockDAG architecture, transaction model, mining infrastructure, and wallet ecosystem would all remain compatible. The change is purely at the consensus ordering layer.
