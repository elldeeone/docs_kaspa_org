## Overview

Kaspa uses a **stack-based scripting language** derived from Bitcoin Script. Every transaction output contains a **script public key** (locking script) that defines the conditions under which the output can be spent. To spend that output, a transaction input must provide a **signature script** (unlocking script) that satisfies those conditions.

The scripting system is intentionally not Turing-complete — scripts always terminate and their execution cost is bounded, preventing denial-of-service attacks through unbounded computation.

<Callout>
Kaspa's scripting language is based on Bitcoin Script but has evolved independently. KIP-10 reactivated many opcodes that were disabled in Bitcoin, giving Kaspa a more expressive scripting capability.
</Callout>

## Standard Scripts

### Pay-to-Public-Key (P2PK)

The most common script type in Kaspa is **Pay-to-Public-Key**, which locks an output to a specific Schnorr public key:

**Script Public Key (locking):**
```
OP_DATA_32 <32-byte-x-only-pubkey> OP_CHECKSIG
```

**Signature Script (unlocking):**
```
OP_DATA_64 <64-byte-schnorr-signature>
```

Validation proceeds as follows:
1. The signature script pushes the signature onto the stack.
2. The script public key pushes the public key onto the stack.
3. `OP_CHECKSIG` pops both values and verifies the Schnorr signature against the transaction's sighash. If valid, it pushes `true`; otherwise `false`.

### Pay-to-Script-Hash (P2SH)

**P2SH** allows locking an output to the hash of an arbitrary script. The spender reveals the full script at spend time:

**Script Public Key (locking):**
```
OP_BLAKE2B OP_DATA_32 <32-byte-script-hash> OP_EQUAL
```

**Signature Script (unlocking):**
```
<signatures and data> <serialized-redeem-script>
```

The node hashes the provided redeem script with BLAKE2b, checks it matches the hash in the script public key, then executes the redeem script with the remaining stack items. This approach keeps the locking script compact regardless of the complexity of the spending conditions.

<Callout type="info">
Kaspa uses BLAKE2b for script hashing, unlike Bitcoin which uses SHA-256 and RIPEMD-160. BLAKE2b is faster and provides equivalent security.
</Callout>

## Script Execution

Script execution follows a stack-based model: the **signature script** is executed first, pushing data onto the stack. The **script public key** is then executed on the same stack. After both scripts complete, the top stack value is checked — if it is non-zero (truthy), the spend is valid. The execution environment is isolated; scripts cannot access external state beyond the transaction data they are validating.

## KIP-10: Transaction Introspection

**KIP-10** is a significant upgrade to Kaspa's scripting capabilities. Rather than reactivating previously disabled opcodes, KIP-10 introduced **transaction introspection opcodes** and extended arithmetic support, enabling scripts to inspect properties of the transaction they are part of.

Key additions in KIP-10:

| Category | Opcodes | Description |
|---|---|---|
| Transaction introspection | `OP_TXINPUTCOUNT`, `OP_TXOUTPUTCOUNT`, `OP_TXINPUTINDEX`, `OP_TXINPUTAMOUNT`, `OP_TXINPUTSPK`, `OP_TXOUTPUTAMOUNT`, `OP_TXOUTPUTSPK` | Allow scripts to read input/output counts, amounts, and script public keys of the current transaction |
| Extended arithmetic | `OP_ADD`, `OP_SUB` | Extended to support 8-byte (i64) integers instead of the previous 4-byte limit (`OP_MUL`, `OP_DIV`, `OP_MOD` remain disabled) |

Transaction introspection enables scripts to enforce constraints on how funds are spent -- for example, requiring that a specific output amount or destination exists in the transaction. This opens the door to covenants, vaults, and other advanced spending conditions.

<Callout>
Many opcodes that are disabled in Bitcoin (such as `OP_CAT`, `OP_LSHIFT`, `OP_RSHIFT`, and string manipulation opcodes) remain disabled in Kaspa. KIP-10's approach focused on adding new transaction introspection capabilities rather than reactivating legacy opcodes.
</Callout>

## Signature Operations and Mass Cost

Each signature verification operation in a script contributes to the transaction's **compute mass**. The cost is:

```
sig_op_mass = sig_op_count × 1000
```

Standard transactions have one `OP_CHECKSIG` per input, so a 3-input transaction has a compute mass of 3,000. Scripts with `OP_CHECKMULTISIG` count each potential signature check toward the sigop total.

This mass cost ensures that transactions with many signature operations pay higher fees, preventing abuse of computationally expensive verification.

## Lock Time Scripts

Kaspa supports time-based spending conditions through lock time mechanisms:

The transaction's `lock_time` field prevents inclusion before a specified DAA score or timestamp. At the script level, `OP_CHECKLOCKTIMEVERIFY` (CLTV) enforces absolute time locks and `OP_CHECKSEQUENCEVERIFY` (CSV) enforces relative time locks (a number of blocks since the UTXO was created).

These opcodes enable vesting schedules, payment channels, and hash-time-locked contracts (HTLCs) for atomic swaps.

## Conditional Scripts

With `OP_IF`/`OP_ELSE`/`OP_ENDIF`, scripts can implement branching logic. A practical example is a **hash-time-locked contract (HTLC)**:

```
OP_IF
  OP_BLAKE2B <hash> OP_EQUALVERIFY <pubkey-A> OP_CHECKSIG
OP_ELSE
  <timeout> OP_CHECKLOCKTIMEVERIFY OP_DROP <pubkey-B> OP_CHECKSIG
OP_ENDIF
```

This script can be spent either by providing the hash preimage and A's signature (before timeout) or by B's signature (after timeout).

## Comparison with Bitcoin Script

| Feature | Kaspa Script | Bitcoin Script |
|---|---|---|
| Signature scheme | Schnorr (secp256k1) | ECDSA + Schnorr (Taproot) |
| Hash function | BLAKE2b | SHA-256, RIPEMD-160 |
| Standard address type | P2PK (direct public key) | P2PKH, P2WPKH, P2TR |
| Arithmetic opcodes | `OP_ADD`, `OP_SUB` active; `OP_MUL`, `OP_DIV`, `OP_MOD` disabled | Mostly disabled |
| String opcodes | Disabled | Disabled |
| Transaction introspection | Available (KIP-10) | Not available (natively) |
| Turing completeness | No | No |

## Script Validation Process

When a node validates a transaction, each input is validated independently:

1. **Deserialize** the signature script and script public key.
2. **Execute** the signature script, building up the stack.
3. **Execute** the script public key on the resulting stack.
4. **Check** that the top stack element is truthy (non-zero).
5. **Count** signature operations for mass calculation.
6. **Reject** if any step fails, if the stack is malformed, or if the script exceeds size limits.
