## What Is UTXO?

In Kaspa, there are no account balances stored on-chain. Instead, the network tracks a set of **Unspent Transaction Outputs (UTXOs)** — discrete units of value, each locked by a script that specifies the conditions under which it can be spent. Your "balance" is the sum of all UTXOs that you hold the keys to unlock.

Every transaction consumes one or more existing UTXOs as **inputs** and creates one or more new UTXOs as **outputs**. The consumed UTXOs are removed from the UTXO set, and the newly created UTXOs are added. This process is atomic — either all inputs are consumed and all outputs are created, or the transaction is invalid and has no effect.

<Callout>
The UTXO model treats value like physical cash: you spend specific "coins" (UTXOs) and receive change back. There is no running balance that gets incremented or decremented.
</Callout>

## How UTXOs Work

Consider a simple example. Alice has a UTXO worth 100 KAS and wants to send 30 KAS to Bob:

```
Input:                          Outputs:
┌─────────────────────┐        ┌─────────────────────┐
│ Alice's UTXO        │        │ Bob: 30 KAS         │
│ 100 KAS             │───────>│                     │
│ (consumed/spent)    │        ├─────────────────────┤
└─────────────────────┘        │ Alice: 69.999 KAS   │
                               │ (change)            │
                               ├─────────────────────┤
                               │ Fee: 0.001 KAS      │
                               └─────────────────────┘
```

Alice's 100 KAS UTXO is consumed entirely. Two new UTXOs are created: one for Bob (30 KAS) and one returning the change to Alice (69.999 KAS). The difference (0.001 KAS) is the transaction fee paid to miners.

Key rules:

- **Inputs must reference existing UTXOs**: You can only spend outputs that exist in the current UTXO set and have not already been spent.
- **Inputs are consumed entirely**: You cannot partially spend a UTXO. If you have a 100 KAS UTXO and want to send 30 KAS, you must consume the full 100 KAS and create a change output.
- **Output values must not exceed input values**: The sum of output values plus the fee must equal the sum of input values exactly.
- **Each UTXO can be spent only once**: Once a UTXO is used as an input, it is permanently removed from the UTXO set.

## UTXO vs. Account Model

The two dominant models for tracking state in blockchains are the UTXO model (used by Bitcoin and Kaspa) and the account model (used by Ethereum). Each has distinct characteristics:

| Property | UTXO Model (Kaspa) | Account Model (Ethereum) |
|---|---|---|
| State representation | Set of unspent outputs | Map of addresses to balances |
| Parallelism | Natural — independent UTXOs can be processed concurrently | Requires careful ordering — account nonces serialize transactions |
| Privacy | Each transaction can use fresh change addresses | Addresses are reused, making tracking easier |
| Transaction structure | Explicit inputs and outputs | Sender, receiver, value, nonce |
| Double-spend detection | Check if UTXO exists in the set | Check nonce ordering |
| State size | Proportional to number of UTXOs | Proportional to number of accounts |

<Callout type="info">
The UTXO model's natural parallelism is a key reason Kaspa adopted it. In a BlockDAG where multiple blocks are created simultaneously, transactions in different blocks that spend different UTXOs can be validated independently without conflicts.
</Callout>

## Why UTXO Suits the BlockDAG

In Kaspa's BlockDAG, multiple miners produce blocks in parallel. These blocks may contain different transactions, and the [GHOSTDAG protocol](/docs/core-concepts/ghostdag) later determines a canonical ordering. The UTXO model aligns with this architecture because:

1. **Independent validation**: Two transactions that spend different UTXOs are completely independent. They can appear in different parallel blocks and both remain valid regardless of ordering.
2. **Simple conflict detection**: A conflict occurs if and only if two transactions attempt to spend the same UTXO. This is a simple set-membership check, not a complex state-dependency analysis.
3. **Deterministic resolution**: When GHOSTDAG orders conflicting transactions, the first one in the ordering is accepted and the second is rejected. The resulting UTXO set is identical regardless of which node computes it.
4. **No nonce ordering**: Unlike account-based systems, there is no requirement that transactions from the same sender be processed in a specific sequence. A user can broadcast multiple independent transactions simultaneously, and they can be included in different parallel blocks.

## UTXO Set Management

The **UTXO set** is the complete collection of all unspent outputs at any given point in the DAG. It represents the current state of all spendable value in the network. Nodes maintain the UTXO set in memory and on disk for fast lookups during transaction validation.

Key aspects of UTXO set management:

- **Size**: The UTXO set grows when transactions create more outputs than they consume, and shrinks when transactions consolidate multiple inputs into fewer outputs.
- **Lookup performance**: Validating a transaction requires checking that each input's referenced UTXO exists in the set. This must be fast, so the UTXO set is typically stored in an indexed data structure.
- **Persistence**: The UTXO set is stored persistently. When a node restarts, it loads the UTXO set rather than replaying all historical transactions.

## UTXO Commitments and MUHASH

Kaspa block headers include a **UTXO commitment** — a cryptographic hash that commits to the entire UTXO set at that point in the DAG. This commitment uses **MUHASH** (Multiplicative Hash), an incremental hashing scheme with a critical property: the hash can be updated efficiently when UTXOs are added or removed, without recomputing over the entire set.

```
MUHASH update:
  add(utxo):    commitment = commitment * hash(utxo)
  remove(utxo): commitment = commitment * hash(utxo)^(-1)
```

This means that as each block is processed and UTXOs are created and consumed, the UTXO commitment can be updated incrementally in time proportional to the number of UTXOs changed — not the total UTXO set size.

The UTXO commitment serves several purposes:

- **New node sync**: A node joining the network can download the UTXO set from a peer and verify it against the commitment in the block headers, ensuring correctness without replaying all historical transactions.
- **Consistency verification**: Nodes can verify that their local UTXO set matches the consensus state by checking against the header commitment.
- **SPV support**: Light clients can use UTXO commitments to verify the existence of specific UTXOs without downloading the full set.

## UTXO Growth and Pruning

Unbounded UTXO set growth is a concern for any UTXO-based system. Each unspent output must be stored indefinitely (until spent), and "dust" outputs — tiny UTXOs that cost more in fees to spend than they are worth — can accumulate and bloat the set.

Kaspa addresses UTXO growth through several mechanisms:

- **Storage mass (KIP-9)**: Transactions that create more UTXOs than they consume are penalized with additional [mass](/docs/core-concepts/fees-and-mass), making it economically costly to bloat the UTXO set.
- **Minimum output value**: Outputs below a dust threshold are rejected by relay policy, preventing the creation of uneconomical UTXOs.
- **Consolidation incentives**: Because storage mass penalizes UTXO creation and rewards consolidation, users are economically motivated to consolidate small UTXOs into larger ones.

<Callout>
The UTXO set size directly impacts node performance. Unlike block history (which can be [pruned](/docs/core-concepts/pruning)), the full UTXO set must be maintained by every validating node. Keeping its growth in check is essential for long-term sustainability.
</Callout>

## Practical Considerations

### Wallet UTXO Management

Wallets must manage their UTXOs carefully:

- **UTXO selection**: When constructing a transaction, the wallet must choose which UTXOs to use as inputs. Common strategies include selecting the fewest UTXOs that cover the required amount, or targeting specific UTXOs to minimize change.
- **Change outputs**: Most transactions create a change output back to the sender. The wallet must track these change UTXOs alongside received outputs.
- **Consolidation**: Wallets that receive many small payments (such as mining wallets) accumulate many small UTXOs. Periodically consolidating these into fewer, larger UTXOs reduces future transaction sizes and fees.

### Transaction Chaining

A user can spend a UTXO that was created in a still-unconfirmed transaction (called **chained** or **dependent** transactions). The child transaction is valid only if the parent transaction is eventually confirmed. Kaspa's mempool supports tracking these dependencies, but long chains of unconfirmed transactions are generally discouraged.
