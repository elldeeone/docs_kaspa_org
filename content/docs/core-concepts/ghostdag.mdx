## Overview

GHOSTDAG (Greedy Heaviest-Observed Sub-Tree Directed Acyclic Graph) is the consensus protocol at the heart of Kaspa. It solves a fundamental problem: given a DAG of blocks produced in parallel by many miners, how do you establish a single, agreed-upon ordering of all transactions?

GHOSTDAG extends the principles of Nakamoto consensus (the longest-chain rule used by Bitcoin) into the DAG domain. Instead of selecting the longest chain and discarding orphan blocks, GHOSTDAG includes **all** blocks and uses a deterministic algorithm to order them.

<Callout>
GHOSTDAG is a generalization of Nakamoto consensus. A blockchain is a special case of a BlockDAG where the width is always 1.
</Callout>

## From GHOST to GHOSTDAG

GHOSTDAG builds on the earlier GHOST (Greedy Heaviest-Observed Sub-Tree) protocol, which was proposed as a modification to Bitcoin's consensus. GHOST selects the heaviest subtree rather than the longest chain, which improves security under high block rates. However, GHOST still produces a chain — off-chain blocks are used for weight calculations but not included in the ledger.

GHOSTDAG goes further: it includes all blocks in the ledger and constructs a total ordering over them. This means every block's transactions are processed, and every miner's work contributes to both security and throughput.

## Blue and Red Sets

The core mechanism of GHOSTDAG is the partitioning of blocks into two sets:

- **Blue set**: Blocks that are considered to have been mined honestly and in good faith. These blocks are well-connected to the rest of the DAG and are consistent with the expected rate of parallel block production.
- **Red set**: Blocks that may have been produced by an adversary attempting to disrupt consensus, or blocks that are poorly connected to the DAG. Red blocks are still included in the ledger, but they are ordered after blue blocks and their transactions are given lower priority.

The classification works as follows: for any block `B`, GHOSTDAG examines how many blocks were created in parallel with `B` (that is, blocks that neither reference `B` as an ancestor nor are referenced by `B`). If this number is within the expected range (governed by the parameter `k`), the block is classified as blue. If it has too many parallel blocks that are not in the blue set, it is classified as red.


## The k Parameter

The parameter `k` is central to GHOSTDAG's security and performance characteristics. It represents the **maximum number of parallel blocks** that the protocol expects honest miners to produce within one network propagation delay.

- **Higher k**: Tolerates more parallelism, allowing a higher block rate for a given network delay. However, it also gives an attacker more room to inject blocks, so a larger fraction of the network's hash power is needed for security.
- **Lower k**: Provides tighter security guarantees but limits the block rate, since the protocol is less tolerant of parallel blocks.

The value of `k` is derived from the block rate and the expected upper bound on network propagation delay. For Kaspa's current 10 BPS rate, `k` is set to accommodate the observed network conditions while maintaining a security threshold well above 50% honest hash power.

<Callout type="info">
The k parameter creates a precise tradeoff: it determines how much parallelism the network can sustain while still guaranteeing that an attacker with less than 50% of the hash power cannot rewrite history.
</Callout>

## Constructing the Total Order

GHOSTDAG produces a **total (linear) ordering** of all blocks in the DAG through the following process:

1. **Select the chain**: GHOSTDAG identifies a selected parent chain through the DAG, analogous to the "longest chain" in Bitcoin. This chain is built by greedily following the parent with the heaviest blue subtree at each step.

2. **Order blue blocks first**: For each block on the selected chain, GHOSTDAG collects all blue blocks in its "merging set" (blocks that are reachable from this chain block but not from the previous one) and orders them.

3. **Append red blocks**: Red blocks in the merging set are placed after the blue blocks.

4. **Resolve conflicts**: If two transactions in different blocks conflict (for example, double-spend attempts), the transaction in the block that appears earlier in the ordering takes precedence. The conflicting transaction in the later block is rejected.

This process is entirely deterministic: given the same DAG, every node running GHOSTDAG will compute the same ordering.

## Confirmations and Finality

In a traditional blockchain, a transaction is considered "confirmed" after a certain number of blocks are built on top of it (e.g., 6 confirmations in Bitcoin). In Kaspa's GHOSTDAG, confirmations work similarly but are measured in terms of the blue score.

The **blue score** of a block is the number of blue blocks in its past (its ancestors). As more blocks are added to the DAG and the blue score of a transaction's block increases, the probability of that transaction being reversed decreases exponentially.

At 10 BPS, confirmations accumulate rapidly:

| Time elapsed | Approximate blue score increase | Security level |
|---|---|---|
| 1 second | ~10 | Low |
| 5 seconds | ~50 | Moderate |
| 10 seconds | ~100 | High |
| 60 seconds | ~600 | Very high |

<Callout>
Full probabilistic finality — equivalent to Bitcoin's 6-confirmation security — is achieved in roughly 10 seconds at 10 BPS, compared to approximately 60 minutes for Bitcoin.
</Callout>

## Relationship to Nakamoto Consensus

GHOSTDAG preserves the key security properties of Nakamoto consensus:

- **Liveness**: As long as honest miners control a majority of the hash power, new transactions will continue to be confirmed.
- **Safety**: Once a transaction has sufficient confirmations, it cannot be reversed without controlling a majority of the hash power.
- **Incentive compatibility**: Honest mining (following the protocol) is the optimal strategy for rational miners.

The critical difference is that GHOSTDAG achieves these properties while processing all blocks rather than just one chain. This allows the block rate to be increased without degrading security, as long as `k` is set appropriately for the network conditions.

## GHOSTDAG in Practice

When a Kaspa node receives a new block, it performs the following steps:

1. Validates the block header and proof-of-work.
2. Adds the block to the local DAG.
3. Recomputes the GHOSTDAG ordering for affected portions of the DAG.
4. Updates the UTXO set based on the new ordering.
5. Propagates the block to peers.

Because GHOSTDAG ordering is computed incrementally, adding a new block does not require reprocessing the entire DAG. The algorithm efficiently updates the blue/red classification and the selected parent chain.
