## Overview

GHOSTDAG (Greedy Heaviest-Observed Sub-Tree Directed Acyclic Graph) is the consensus protocol at the heart of Kaspa. It solves a fundamental problem: given a DAG of blocks produced in parallel by many miners, how do you establish a single, agreed-upon ordering of all transactions?

GHOSTDAG extends the principles of Nakamoto consensus (the longest-chain rule used by Bitcoin) into the DAG domain. Instead of selecting the longest chain and discarding orphan blocks, GHOSTDAG includes **all** blocks and uses a deterministic algorithm to order them.

<Callout>
GHOSTDAG is a generalization of Nakamoto consensus. A blockchain is a special case of a BlockDAG where each block has at most one parent.
</Callout>

## From GHOST to GHOSTDAG

GHOSTDAG builds on concepts from the earlier GHOST (Greedy Heaviest-Observed Sub-Tree) protocol and extends them with the PHANTOM paper's approach. The key innovation is that GHOSTDAG includes all blocks in the ledger and constructs a total ordering over them by classifying blocks into blue and red sets based on k-cluster constraints. This means every block's transactions are processed, and every miner's work contributes to both security and throughput.

## Blue and Red Sets

The core mechanism of GHOSTDAG is the partitioning of blocks into two sets based on k-cluster validation:

- **Blue set** (`mergeset_blues`): Blocks that satisfy the k-cluster constraint. Specifically, a block can be added to the blue set if: (1) its blue anticone size does not exceed `k`, and (2) adding it doesn't cause any existing blue block's blue anticone to exceed `k`.
- **Red set** (`mergeset_reds`): Blocks that violate the k-cluster constraint. These blocks are still included in the ledger and their transactions are processed, but they don't contribute to the blue score or blue work calculations. Additionally, red block coinbase rewards (subsidy and fees) are not paid to the red block's miner — instead, they are collected by the merging block's miner.

The classification algorithm iterates through the mergeset in topological order and checks each candidate block against the k-cluster constraints. If a block would violate these constraints, it's classified as red; otherwise, it's added to the blue set.

## The k Parameter

The parameter `k` is central to GHOSTDAG's security and performance characteristics. It represents the **maximum blue anticone size** that the protocol tolerates for blue blocks. The anticone of a block consists of all blocks that are neither ancestors nor descendants of that block.

The value of `k` is calculated using the formula from section 4.2 of the PHANTOM paper (equation 1), which ensures that anticones larger than `k` occur with probability less than `δ` (delta). The calculation uses:

- `x = 2Dλ` where `D` is the network delay bound (5 seconds) and `λ` is the block rate
- `δ = 0.01` (1% probability threshold for large anticones)

For Kaspa's 10 BPS configuration, `k = 124`.

- **Higher k**: Tolerates more parallelism, allowing a higher block rate for a given network delay, but requires larger storage and computation for GHOSTDAG calculations.
- **Lower k**: Provides tighter bounds on block anticones but limits the sustainable block rate.

<Callout type="info">
The k parameter creates a precise tradeoff: it determines how much parallelism the network can sustain while keeping the probability of anticones exceeding k below 1%.
</Callout>

## Constructing the Total Order

GHOSTDAG produces a **total (linear) ordering** of all blocks in the DAG through the following process:

1. **Select the parent with highest blue work**: From the candidate parents, select the one with the highest cumulative blue work (the sum of proof-of-work from all blue blocks in its past).

2. **Compute the mergeset**: Identify all blocks in the anticone of the selected parent that are reachable from the new block's other parents.

3. **Color blocks blue or red**: Process the mergeset in topological order by blue work, applying the k-cluster validation to determine which blocks are blue and which are red.

4. **Calculate blue score and blue work**: The blue score equals the selected parent's blue score plus the number of blue blocks in the mergeset. Blue work is the selected parent's blue work plus the sum of proof-of-work from mergeset blues.

5. **Order blocks for transaction processing**: Blocks are processed in consensus order — starting with the selected parent, then the remaining mergeset blocks (both blue and red) interleaved in ascending blue work order (with hash as tiebreaker).

6. **Resolve conflicts**: If two transactions in different blocks conflict (for example, double-spend attempts), the transaction in the block that appears earlier in the ordering takes precedence. The conflicting transaction in the later block is rejected.

This process is entirely deterministic: given the same DAG, every node running GHOSTDAG will compute the same ordering.

## Confirmations and Finality

In Kaspa's GHOSTDAG, confirmation depth is measured using **blue score** — the cumulative count of blue blocks in a block's past. As more blocks are added to the DAG and the blue score increases, the probability of reorganization decreases.

At 10 BPS, blue score accumulates rapidly at approximately 10 blocks per second, providing fast confirmations. However, it's important to distinguish between **confirmations** (relative confidence based on blue score depth) and **finality** (absolute irreversibility).

**Finality** in Kaspa is defined by the `finality_depth` parameter, which provides 12 hours of depth. At 10 BPS, this equals 432,000 blocks (10 blocks/second × 43,200 seconds). Blocks beyond this depth are considered final.

**Pruning** is a separate mechanism with its own depth, defined as the maximum of either 30 hours of depth or a lower bound derived from finality depth, merge depth, mergeset size limit, and `k`. In practice, the pruning depth is significantly larger than the finality depth, providing a safety margin before historical data is removed.

For practical transaction acceptance, users can rely on much shorter confirmation depths (tens to hundreds of blocks) depending on their security requirements, similar to how Bitcoin users don't always wait for full finality.

## Relationship to Nakamoto Consensus

GHOSTDAG preserves key security properties similar to Nakamoto consensus:

- **Liveness**: As long as the network assumptions hold (honest mining following the protocol, bounded network delay), new transactions will continue to be confirmed.
- **Safety**: Once a transaction has sufficient blue score depth, the probability of reorganization becomes negligible.
- **Deterministic ordering**: All nodes compute the same transaction order given the same DAG structure.

The critical difference is that GHOSTDAG achieves these properties while processing all blocks rather than just one chain. This allows the block rate to be increased without degrading security, as long as `k` is set appropriately for the network conditions based on the PHANTOM paper's security analysis.

## GHOSTDAG in Practice

When a Kaspa node receives a new block, the header processor performs the following steps:

1. **Pre-GHOSTDAG validation**: Validates proof-of-work, parent relationships, and basic header properties.
2. **GHOSTDAG computation**: Calculates the GHOSTDAG data (selected parent, blue/red classification, blue score, blue work) for the new block.
3. **Post-GHOSTDAG validation**: Validates that the block's claimed blue score matches the computed value and performs additional consensus checks.
4. **Body processing**: If the header is valid, processes the block body including transactions and updates the UTXO set.
5. **Propagation**: Propagates the valid block to peers.

The GHOSTDAG algorithm efficiently computes results incrementally by reusing stored data from parent blocks, avoiding the need to reprocess the entire DAG for each new block.
