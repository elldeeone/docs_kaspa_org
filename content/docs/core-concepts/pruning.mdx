## The Data Growth Challenge

Kaspa operates at 10 blocks per second, producing vastly more block data per unit of time than traditional blockchains. Without data management strategies, the storage requirements for running a node would grow at an unsustainable rate, putting full participation out of reach for most users.

Pruning is Kaspa's solution to this problem. It allows nodes to discard historical block data that is no longer needed for consensus validation, while retaining all the information necessary to verify the current state and process new blocks.

<Callout>
Pruning is essential to Kaspa's scalability. Without it, the 10 BPS block rate would generate hundreds of gigabytes of data per year, making it impractical for most users to run a full node.
</Callout>

## What Gets Pruned

When a block reaches sufficient depth in the DAG (past the pruning depth), the following data is discarded:

- **Transaction bodies**: The full transaction data, including inputs, outputs, and signatures.
- **Block bodies**: The list of transactions included in the block.
- **Signature scripts**: The unlocking scripts attached to transaction inputs.

In essence, once a block is pruned, the specific details of what transactions it contained are no longer stored by pruned nodes.

## What Is Retained

Even after pruning, nodes retain critical data structures:

- **Headers/proofs around the active consensus horizon**: Pruned nodes keep the header/proof/state data needed for ongoing validation and synchronization. Fully pruned historical headers can be deleted.
- **UTXO set**: The complete set of unspent transaction outputs is maintained. This represents the current state of all spendable coins and is all that is needed to validate new transactions.
- **UTXO commitment**: A cryptographic commitment to the UTXO set is included in block headers, allowing nodes to verify the integrity of the UTXO set they hold.
- **DAG relation data required for current operation**: Pruned nodes keep relations needed near the pruning horizon, but do not preserve full historical DAG topology indefinitely.

<Callout type="info">
The UTXO set is a compact representation of current spendable state. A pruned node still validates new blocks and transactions, but with retained recent header/proof/state data rather than a complete historical DAG record.
</Callout>

## Pruning Depth

The **pruning depth** defines how many blocks deep a block must be (in terms of blue score) before it is eligible for pruning. This depth is set to ensure that:

1. **Finality**: Blocks at the pruning depth have achieved overwhelming probabilistic finality. The probability of a reorganization reaching this depth is negligible under any realistic attack scenario.
2. **Reorg safety**: Even in the event of temporary network partitions or adversarial behavior, the pruning depth provides a wide margin of safety before data is discarded.

The pruning depth is measured in terms of the blue score relative to the current DAG tip. As the DAG grows, blocks whose blue score falls below the pruning threshold are candidates for pruning.

## How Pruning Preserves Consensus

A pruned node can still fully participate in consensus because:

1. **New transaction validation**: Validating a new transaction requires checking that its inputs reference existing UTXOs and that the signatures are valid. Both of these checks use only the current UTXO set, which is fully retained.
2. **New block validation**: Validating a new block requires checking the proof-of-work (from the header), verifying the block's transactions, and confirming that the block's parent references are valid (from retained headers).
3. **GHOSTDAG ordering**: Ongoing GHOSTDAG processing uses retained consensus data near the active/pruning horizon instead of requiring an indefinitely complete historical topology.
4. **UTXO commitment verification**: The UTXO commitment in block headers allows nodes to verify that their UTXO set is consistent with the consensus state.

In short, pruned nodes lose the ability to look up historical transaction details, but they retain full ability to validate and extend the DAG.

## Pruned Nodes vs Archival Nodes

Kaspa supports two types of nodes:

### Pruned Nodes

- Store required header/proof data near the active pruning horizon, the UTXO set, and recent block bodies.
- Discard block bodies and transaction data beyond the pruning depth.
- Can fully validate new blocks and transactions.
- Can participate in consensus and mining.
- Have significantly lower storage requirements.
- This is the default node configuration.

### Archival Nodes

- Store the complete history of all blocks and transactions.
- Never prune any data.
- Can serve historical block and transaction data to other nodes and applications.
- Required for block explorers, analytics services, and applications that need access to full transaction history.
- Have much higher storage requirements that grow linearly with time.

<Callout>
Running a pruned node is sufficient for most users, including miners. Archival nodes are primarily needed by infrastructure providers such as block explorers and analytics services.
</Callout>

## Syncing a New Node

When a new node joins the network, it does not need to download and replay the entire history from the genesis block. Instead, it can sync using the following process:

1. **Header/proof synchronization**: The node downloads the header/proof data required around the pruning point and recent history.
2. **UTXO set download**: The node downloads the UTXO set at the pruning point from peers.
3. **UTXO commitment verification**: The node verifies that the downloaded UTXO set matches the UTXO commitment in the block headers, ensuring the set has not been tampered with.
4. **Recent block download**: The node downloads full block data (including transaction bodies) for blocks above the pruning depth.
5. **Validation and catch-up**: The node validates recent blocks against the UTXO set and catches up to the current DAG tip.

This process is significantly faster than replaying the entire history, since the node only needs to process recent blocks rather than every transaction ever made.

## Impact of Block Rate on Data Growth

At 10 BPS, Kaspa produces approximately:

| Time period | Approximate blocks |
|---|---|
| 1 minute | 600 |
| 1 hour | 36,000 |
| 1 day | 864,000 |
| 1 year | ~315 million |

The headers for these blocks are small and manageable. The block bodies and transaction data, however, would grow to enormous sizes without pruning. By discarding this data after finality/pruning conditions, pruned nodes maintain a bounded storage footprint that depends primarily on UTXO state plus retained consensus/pruning data rather than full historical transaction volume.

## Pruning and SPV

Pruning has implications for [SPV (Simplified Payment Verification)](/docs/core-concepts/spv) clients. Since pruned nodes do not retain historical transaction data, SPV proofs for old transactions may not be available from pruned nodes. Applications that need to verify historical transactions should query archival nodes or use UTXO commitments to verify current state.
