## Overview

A Kaspa address is a human-readable string that encodes a public key or script hash, identifying a destination for KAS payments. Addresses use **Bech32 encoding**, a format designed for error detection and resistance to transcription mistakes. Unlike raw public keys or script hashes, addresses include a human-readable prefix that identifies the network and a checksum that catches typos.

<Callout>
Kaspa addresses are derived from public keys using one-way cryptographic functions. You can freely share your address to receive payments — it does not reveal your private key.
</Callout>

## Address Format

A Kaspa address consists of three parts:

```
kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswss2k9eppq0sg6v0h2pjkxrfnfyqt
└──┬─┘ └┬┘└──────────────────────────┬──────────────────────────────┘
prefix  ver                     data + checksum
```

1. **Prefix**: Identifies the network. Separated from the rest of the address by a colon (`:`).
2. **Version byte**: Encodes the address type (e.g., public key or script hash).
3. **Data and checksum**: The public key or script hash encoded in Bech32, followed by an error-detecting checksum.

## Network Prefixes

Each Kaspa network uses a distinct prefix to prevent accidentally sending funds to an address on the wrong network:

| Network | Prefix | Usage |
|---|---|---|
| Mainnet | `kaspa:` | Production network with real value |
| Testnet | `kaspatest:` | Public test network for developers |
| Simnet | `kaspasim:` | Local simulation network |
| Devnet | `kaspadev:` | Development network |

A transaction constructed for mainnet will be rejected on testnet and vice versa, because the address prefix is part of the encoding and validation process.

## Address Types

### Pay-to-Public-Key (P2PK)

The standard Kaspa address type is **Pay-to-Public-Key (P2PK)** using Schnorr signatures over the secp256k1 curve. The address directly encodes a 32-byte x-only public key (the x-coordinate of the public key point on the elliptic curve).

The script public key for a P2PK address has the form:

```
OP_DATA_32 <32-byte-public-key> OP_CHECKSIG
```

To spend a UTXO locked to a P2PK address, the spender must provide a valid Schnorr signature corresponding to the public key encoded in the address.

<Callout type="info">
Kaspa uses x-only public keys (32 bytes) rather than compressed public keys (33 bytes). This follows the approach adopted by Bitcoin's Taproot upgrade, where the y-coordinate parity is implicitly even.
</Callout>

### Pay-to-Script-Hash (P2SH)

Kaspa also supports **Pay-to-Script-Hash (P2SH)** addresses, where the address encodes a BLAKE2b hash of a script rather than a public key directly. To spend, the spender must reveal the full script and provide inputs that satisfy it.

P2SH addresses are identified by a different version byte in the encoding, distinguishing them from P2PK addresses.

## Address Derivation

The process of deriving an address from a private key follows these steps:

1. **Generate a private key**: A 256-bit random number on the secp256k1 curve.
2. **Compute the public key**: Multiply the private key by the secp256k1 generator point to get the public key point. Extract the 32-byte x-coordinate.
3. **Encode the address**: Apply Bech32 encoding with the appropriate network prefix and version byte.

```
Private Key (256-bit)
    │
    ▼ (secp256k1 point multiplication)
Public Key (32-byte x-only)
    │
    ▼ (Bech32 encoding with prefix)
Address: kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswss...
```

## HD Wallet Derivation

Kaspa wallets use **Hierarchical Deterministic (HD) derivation** following BIP-32, BIP-39, and BIP-44 standards. This allows an entire tree of key pairs to be derived from a single seed phrase (typically 12 or 24 words).

### Derivation Path

The standard derivation path for Kaspa follows the BIP-44 structure:

```
m / 44' / 111111' / account' / change / index
```

| Level | Value | Description |
|---|---|---|
| Purpose | `44'` | BIP-44 multi-account hierarchy |
| Coin Type | `111111'` | Kaspa's registered coin type |
| Account | `0'`, `1'`, ... | Account index (hardened) |
| Change | `0` or `1` | `0` for receiving addresses, `1` for internal change addresses |
| Index | `0`, `1`, `2`, ... | Sequential address index |

The **coin type `111111`** is Kaspa's registered identifier in the SLIP-44 registry, which assigns unique coin type numbers to different cryptocurrencies.

<Callout>
A single 12-word or 24-word mnemonic phrase can derive an unlimited number of Kaspa addresses. Wallets typically generate new receiving addresses for each transaction to improve privacy.
</Callout>

## Multisig Addresses

Kaspa supports **multi-signature (multisig) addresses** where spending requires signatures from multiple parties. A typical M-of-N multisig scheme requires at least M signatures out of N possible signers.

Multisig in Kaspa is implemented via P2SH, where the script encodes the multisig conditions. Since Kaspa uses Schnorr signatures, which are linear, advanced multisig schemes can aggregate multiple signatures into a single signature for greater efficiency and privacy.

The script for a basic multisig would look like:

```
OP_M <pubkey1> <pubkey2> ... <pubkeyN> OP_N OP_CHECKMULTISIG
```

Where `M` is the required number of signatures and `N` is the total number of public keys.

## Address Validation

When processing an address, nodes and wallets perform several validation checks:

1. **Prefix check**: Verify that the prefix matches the expected network (e.g., `kaspa:` for mainnet).
2. **Bech32 decoding**: Decode the address and verify the Bech32 checksum. If any character has been altered, the checksum will fail.
3. **Version byte check**: Ensure the version byte corresponds to a known address type.
4. **Data length check**: Verify that the decoded data has the expected length (32 bytes for P2PK, 32 bytes for P2SH).

Bech32 encoding can detect up to 4 character errors in an address and has a very low probability of accepting addresses with more errors. This makes it significantly more robust than older encoding schemes like Base58Check.

<Callout type="info">
Always validate addresses before sending transactions. Most wallet software performs these checks automatically, but applications integrating with Kaspa should implement full address validation.
</Callout>
