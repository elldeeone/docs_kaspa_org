## UTXO Model

Kaspa uses an **Unspent Transaction Output (UTXO) model**, the same fundamental model used by Bitcoin. In this model, there are no account balances. Instead, the network tracks a set of unspent outputs, each of which is locked by a script (typically requiring a specific public key's signature to spend).

When you "own" KAS, what you actually own is the ability to unlock one or more UTXOs. When you send KAS to someone, you consume (spend) your existing UTXOs as inputs and create new UTXOs as outputs — one for the recipient and, if necessary, one back to yourself as change.

<Callout>
The UTXO model provides natural parallelism: transactions that consume different UTXOs are inherently independent and can be validated concurrently. This aligns well with Kaspa's BlockDAG architecture.
</Callout>

## KAS Denominations

The native currency of Kaspa is **KAS**. The smallest indivisible unit is called a **sompi**:

| Unit | In Sompi | In KAS |
|---|---|---|
| 1 sompi | 1 | 0.00000001 |
| 1 KAS | 100,000,000 | 1 |

All values in the Kaspa protocol and transaction format are denominated in sompi. One KAS equals 100,000,000 sompi (10^8), identical to the relationship between bitcoin and satoshi.

## Transaction Structure

A Kaspa transaction consists of the following fields:

### Version

An integer specifying the transaction format version. This allows the protocol to introduce new transaction features in the future while maintaining backward compatibility.

### Inputs

Each input references a previous transaction output that is being spent:

- **Previous outpoint**: The transaction ID and output index of the UTXO being consumed.
- **Signature script**: The unlocking script that satisfies the conditions of the referenced output's script public key. For standard pay-to-public-key transactions, this contains a Schnorr signature.
- **Sequence number**: Used for relative time locks and transaction replacement signaling.

### Outputs

Each output defines a new UTXO:

- **Value**: The amount of sompi being locked in this output.
- **Script public key**: The locking script that defines the conditions under which this output can be spent. The most common form is a pay-to-public-key script containing the recipient's public key.

### Lock Time

A value that restricts when the transaction can be included in a block. It can represent either a DAA (Difficulty Adjustment Algorithm) score or a timestamp, depending on the value:

- Values below 500,000,000,000 are interpreted as DAA scores.
- Values at or above 500,000,000,000 are interpreted as Unix timestamps in milliseconds.

### Subnetwork ID

A 20-byte identifier that associates the transaction with a specific subnetwork. Most standard transactions use the native subnetwork ID. Subnetworks provide a mechanism for layer-2 protocols and specialized transaction types to operate within the Kaspa framework.

<Callout type="info">
The subnetwork ID is a forward-looking feature. The native subnetwork (used for standard KAS transfers) has the ID `0x0000000000000000000000000000000000000000`. The coinbase subnetwork ID is `0x0100000000000000000000000000000000000000`.
</Callout>

## Schnorr Signatures

Kaspa uses **Schnorr signatures** over the secp256k1 curve for transaction signing. Schnorr signatures offer several advantages over the ECDSA signatures used in Bitcoin's original design:

- **Linearity**: Schnorr signatures are linear, which means multiple signatures can be aggregated into a single signature. This enables more efficient multi-signature schemes.
- **Provable security**: Schnorr signatures have a formal security proof under the random oracle model, reducing to the hardness of the discrete logarithm problem.
- **Simplicity**: The signing and verification algorithms are simpler than ECDSA, reducing the surface area for implementation bugs.
- **Efficiency**: Batch verification of multiple Schnorr signatures is faster than verifying them individually.

A standard Kaspa signature signs a hash of the transaction data using the SigHash scheme, which specifies which parts of the transaction are covered by the signature.

### SigHash Types

Kaspa supports the following SigHash types, which control what parts of the transaction are included in the signed data:

- **SigHashAll**: Signs all inputs and outputs. This is the default and most common type.
- **SigHashNone**: Signs all inputs but no outputs, allowing outputs to be modified after signing.
- **SigHashSingle**: Signs all inputs and only the output with the same index as the input being signed.
- **SigHashAnyOneCanPay**: Can be combined with the above types. When set, only the current input is signed, allowing others to add additional inputs.

## Transaction Mass

Instead of a simple byte-size limit, Kaspa uses a concept called **transaction mass** to measure the resource cost of a transaction. Mass accounts for multiple dimensions of resource consumption:

- **Compute mass**: The computational cost of verifying the transaction's scripts and signatures.
- **Transient mass** (KIP-13): The serialized size of the transaction in bytes, reflecting network propagation and mempool costs.
- **Storage mass** (KIP-9): The impact on the UTXO set. Transactions that create many new UTXOs without consolidating existing ones incur higher storage mass.

The total mass of a transaction is the **maximum** of these three components (not the sum). Each block has a maximum mass capacity, and transactions are selected by miners based on their fee-to-mass ratio.

<Callout>
Transaction mass is designed to align economic incentives with resource consumption. A transaction that is expensive for the network to process (in terms of compute, bandwidth, or state growth) must pay a proportionally higher fee.
</Callout>

## Fees

Transaction fees in Kaspa are calculated based on the transaction's mass. Users set a fee rate in sompi per unit of mass, and the total fee is:

```
fee = fee_rate * transaction_mass
```

Miners prioritize transactions by their fee-to-mass ratio, similar to how Bitcoin miners prioritize by fee-per-byte. During periods of high demand, users can increase their fee rate to ensure faster inclusion.

Because Kaspa operates at 10 BPS with all blocks included in the DAG, the aggregate block space available per second is significantly higher than in a traditional blockchain. This generally results in lower fees, as there is more capacity to absorb transaction demand.

### Minimum Fee

Every transaction must include a minimum fee to be relayed by the network. This minimum fee prevents spam and denial-of-service attacks. Transactions below the minimum fee are rejected by nodes and not propagated.

## Transaction Lifecycle

A Kaspa transaction goes through the following stages:

1. **Construction**: The sender selects UTXOs to spend, constructs inputs and outputs, and computes the change amount.
2. **Signing**: The sender signs each input with their private key using Schnorr signatures.
3. **Broadcasting**: The signed transaction is submitted to a Kaspa node, which validates it and adds it to the mempool.
4. **Inclusion**: A miner includes the transaction in a new block.
5. **Ordering**: The [GHOSTDAG protocol](/docs/core-concepts/ghostdag) determines where the block (and thus the transaction) falls in the canonical ordering.
6. **Confirmation**: As more blocks are added to the DAG, the transaction accumulates confirmations and reaches finality.

## Coinbase Transactions

Each block contains a special **coinbase transaction** that mints new KAS as a block reward. The coinbase transaction has no inputs (since it creates new coins) and its outputs distribute the block reward to the miner.

Kaspa's block reward follows a smooth emission schedule based on a chromatic scale (musical half-notes), decreasing the reward roughly once per year. Coinbase outputs have a maturity requirement: they cannot be spent until a certain number of confirmations have passed.

## Double-Spend Prevention

In a BlockDAG, two blocks might contain conflicting transactions (transactions that attempt to spend the same UTXO). GHOSTDAG resolves these conflicts deterministically:

1. The canonical ordering produced by GHOSTDAG determines which transaction is seen first.
2. The first transaction in the ordering is accepted; the conflicting transaction in a later block is rejected.
3. The block containing the rejected transaction is still included in the DAG (and the miner still receives the block reward), but the conflicting transaction within it has no effect.

This approach ensures that double-spend attempts are always resolved in a consistent manner across all nodes.
