This guide walks through building a production-grade payment gateway that accepts KAS. The architecture generates a unique address per invoice, monitors deposits in real time via UTXO subscriptions, tracks confirmation depth using DAA scores, and periodically consolidates funds.

## Architecture Overview

```
Customer --> Unique kaspa: address --> UtxoProcessor detects deposit
                                        |
                                        v
                                  Track DAA score depth
                                        |
                                        v
                                  Mark invoice as paid
                                        |
                                        v
                                  Consolidate UTXOs --> Hot wallet
```

Each invoice gets its own derived address from an HD wallet. The `UtxoProcessor` watches all active addresses and fires events when payments arrive.

## Step 1 -- HD Address Generation

Derive a unique address per invoice using BIP-44 key derivation:

```typescript
import { Mnemonic, XPrv } from "kaspa-wasm";

const mnemonic = new Mnemonic(process.env.GATEWAY_MNEMONIC!);
const seed = mnemonic.toSeed("");
const xprv = new XPrv(seed);

function deriveAddress(invoiceIndex: number): {
  address: string;
  privateKey: any;
} {
  // m/44'/111111'/0'/0/index
  const key = xprv.derivePath(`m/44'/111111'/0'/0/${invoiceIndex}`).toPrivateKey();
  const address = key.toPublicKey().toAddress("mainnet").toString();
  return { address, privateKey: key };
}
```

<Callout type="info">
Each invoice should use a fresh `invoiceIndex` so that payments are isolated. Store the mapping of invoice ID to derivation index in your database.
</Callout>

## Step 2 -- Watch for Deposits

Use `UtxoProcessor` to subscribe to UTXO events across all active invoice addresses:

```typescript
import { RpcClient, Resolver, Encoding, UtxoProcessor, UtxoContext } from "kaspa-wasm";

const rpc = new RpcClient({ resolver: new Resolver(), encoding: Encoding.Borsh, networkId: "mainnet" });
await rpc.connect();

const processor = new UtxoProcessor({ rpc, networkId: "mainnet" });
const context = new UtxoContext({ processor });
await processor.start();
await context.trackAddresses(getActiveInvoiceAddresses()); // from your DB
```

## Step 3 -- Track Confirmations via DAA Score

Kaspa does not use a simple block-height confirmation count. Instead, confirmation depth is measured by the difference in **DAA score** (Difficulty Adjustment Algorithm score) between the transaction's accepting block and the current virtual DAA score.

```typescript
processor.addEventListener("balance", async (event: any) => {
  const balance = event.data;
  // balance contains: mature, pending, outgoing, matureUtxoCount, pendingUtxoCount, stasisUtxoCount
  console.log(`Balance update: ${balance.mature} sompi mature, ${balance.pending} sompi pending`);

  // Check each tracked invoice address for sufficient balance
  for (const addr of getActiveInvoiceAddresses()) {
    const addrBalance = await rpc.getBalanceByAddress({ address: addr });
    const invoice = await db.findInvoiceByAddress(addr);
    if (!invoice) continue;

    await db.updateInvoiceBalance(invoice.id, BigInt(addrBalance.balance));
  }
});
```

To check confirmation depth, compare the deposit's DAA score against the current virtual:

```typescript
async function getConfirmationDepth(depositDaaScore: bigint): Promise<bigint> {
  const info = await rpc.getBlockDagInfo();
  return info.virtualDaaScore - depositDaaScore;
}
```

<Callout type="warn">
A DAA score depth of **10** is generally considered safe for low-value transactions. For high-value payments, wait for a depth of **100+** (roughly 10 seconds at 10 BPS). Kaspa's GHOSTDAG consensus provides fast probabilistic finality.
</Callout>

## Step 4 -- Handle Partial Payments

Since Kaspa uses the UTXO model, a customer might send less than the invoiced amount. Your gateway should sum all UTXOs received at the invoice address, verify each deposit has sufficient DAA score depth, and only mark the invoice paid when the total meets the required amount and all deposits are confirmed.

## Step 5 -- Consolidate UTXOs

Periodically sweep funds from invoice addresses into your hot wallet to prevent UTXO fragmentation:

```typescript
import { createTransactions, kaspaToSompi } from "kaspa-wasm";

async function consolidate(invoiceKeys: any[], hotWalletAddress: string) {
  const { transactions } = await createTransactions({
    entries: context,
    outputs: [],          // No explicit outputs -- everything goes to change
    changeAddress: hotWalletAddress,
    priorityFee: 0n,
  });

  for (const tx of transactions) {
    tx.sign(invoiceKeys);
    await tx.submit(rpc);
  }
}
```

<Callout type="info">
`createTransactions` automatically handles the case where many small UTXOs must be combined across multiple transactions. Submit them in order since each depends on outputs from the previous one.
</Callout>

## Production Considerations

| Concern | Recommendation |
|---|---|
| Key storage | Use HSM or encrypted key vault; never store mnemonics in plaintext |
| Node reliability | Run your own node with `--utxoindex` instead of relying on public resolvers |
| Database | Use an ACID-compliant database with write-ahead logging for payment records |
| Idempotency | Deduplicate deposits by UTXO outpoint (transaction ID + output index) |
| Expiry | Expire unpaid invoices after a timeout and stop tracking those addresses |
| Reorgs | Listen for `"reorg"` events from the UtxoProcessor and re-check balances when they occur |
