## Why Upgrade

Keeping your kaspad node up to date ensures you have the latest consensus rules, performance improvements, security fixes, and feature additions. Some upgrades are optional (performance enhancements), while others are mandatory (consensus rule changes or hardforks). Running outdated software after a consensus change will cause your node to fork off the network.

<Callout type="warn">
Mandatory upgrades tied to consensus changes (such as hardforks) must be applied before the activation height. Nodes that do not upgrade in time will reject valid blocks and diverge from the network.
</Callout>

## Crescendo Hardfork

The Crescendo hardfork transitioned Kaspa from 1 BPS to 10 BPS. This was one of the most significant upgrades in Kaspa's history, requiring changes across the entire stack:

- **Block rate**: Increased from 1 block per second to 10 blocks per second.
- **GHOSTDAG K parameter**: Increased from `k=18` (1 BPS) to `k=124` (10 BPS) to accommodate the higher number of parallel blocks during network propagation.
- **Block rewards**: Adjusted to maintain the same emission schedule despite the higher block rate (each block's reward is 1/10th of what it was at 1 BPS).
- **Finality depth**: Recalculated for the new block rate.

<Callout type="info">
The Crescendo hardfork was activated at a predetermined DAA score. Nodes running pre-Crescendo software stopped being able to validate new blocks after the activation point. If you are setting up a new node today, the current release already includes Crescendo support and no special action is needed.
</Callout>

## Pre-Upgrade Checklist

Before upgrading kaspad, verify the following:

1. **Read the release notes**: Check the [rusty-kaspa releases page](https://github.com/kaspanet/rusty-kaspa/releases) for the target version. Note any breaking changes, new flags, or required actions.
2. **Check compatibility**: Confirm whether the upgrade requires a database reset or is backward-compatible with existing data.
3. **Back up your data directory**: Copy the data directory (for example `~/.rusty-kaspa/kaspa-mainnet/datadir/`) to a safe location. This allows recovery if the upgrade fails.
4. **Plan downtime**: The upgrade process requires stopping the node temporarily. On a mining setup, this means brief mining downtime.
5. **Verify system requirements**: New versions may have different resource requirements. Check that your system meets the updated minimums.

## Upgrade Process

### Standard Upgrade (Binary Replacement)

For most upgrades, the process is straightforward:

```bash
# 1. Stop the running node
# If running as a systemd service:
sudo systemctl stop kaspad

# If running in the foreground, send SIGINT (Ctrl+C) and wait for graceful shutdown.

# 2. Replace the binary
# If built from source:
cd /path/to/rusty-kaspa
git fetch origin
git checkout v0.X.Y  # Replace with target version tag
cargo build --release --bin kaspad

# Or replace the downloaded binary:
cp /path/to/new/kaspad /usr/local/bin/kaspad

# 3. Start the node
sudo systemctl start kaspad
# Or:
kaspad --utxoindex --rpclisten=0.0.0.0:16110
```

### Upgrade with Database Reset

Some major upgrades change the database schema and require a fresh sync. The release notes will explicitly state when this is necessary.

```bash
# Stop the node
sudo systemctl stop kaspad

# Replace the binary (as above)

# Start with database reset
kaspad --reset-db --utxoindex --rpclisten=0.0.0.0:16110
```

<Callout>
A database reset triggers a full re-sync. Duration is environment-dependent (hardware, network, and DAG size), so plan downtime conservatively for operational workloads.
</Callout>

## Verifying a Successful Upgrade

After starting the upgraded node, confirm the upgrade succeeded:

1. **Check the version**: Query `GetInfo` via RPC and verify the reported server version matches the expected release.
2. **Monitor sync**: Watch the logs to confirm the node syncs to the DAG tip. The blue score and timestamp should advance to the present.
3. **Verify peers**: Ensure the node connects to peers. Post-hardfork, nodes on incompatible versions will not peer with each other, so a healthy peer count confirms you are on the correct chain.
4. **Test RPC**: If you use RPC features, verify that your clients can still connect and receive expected responses.

## Backward Compatibility

Compatibility expectations are release-specific. Do not assume that minor versions are always backward-compatible; confirm DB and RPC compatibility from the exact target release notes.

Key compatibility considerations:

- **Database format**: If the on-disk format changes, the old database cannot be read by the new version (and vice versa). A `--reset-db` is required.
- **RPC interface**: New RPC methods may be added and existing behavior can change. Check release notes for deprecated or removed methods.
- **P2P protocol**: Nodes on incompatible versions may fail to communicate. After a hardfork activation, old-version nodes will be unable to sync.

## Rollback Procedures

If an upgrade causes problems: stop the node, replace the binary with the previous version, restore the data directory from your pre-upgrade backup (if the database format changed), and restart.

<Callout type="warn">
Rollback is only possible if you backed up the data directory before upgrading and the network has not undergone a consensus change. After a hardfork activation, rolling back to a pre-hardfork version will leave your node on an incompatible chain fork.
</Callout>
