## Overview

Running kaspad in Docker provides a consistent, reproducible deployment environment. Containers isolate the node from the host system, simplify upgrades, and integrate with orchestration tools like Docker Compose and Kubernetes.

<Callout type="info">
The official rusty-kaspa repository does not publish pre-built Docker images at the time of writing. You will need to build your own image from the source code or use a community-maintained image.
</Callout>

## Dockerfile

The following Dockerfile builds kaspad from source using a multi-stage build to minimize the final image size:

```dockerfile
# Build stage
FROM rust:1.78-bookworm AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y protobuf-compiler libclang-dev
COPY . .
RUN cargo build --release --bin kaspad

# Runtime stage
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y ca-certificates && rm -rf /var/lib/apt/lists/*
COPY --from=builder /build/target/release/kaspad /usr/local/bin/kaspad
EXPOSE 16110 16111 17110 18110
ENTRYPOINT ["kaspad"]
```

Build the image by cloning the rusty-kaspa repository and running `docker build -t kaspad:latest .` from the repo root.

## Docker Compose

A `docker-compose.yml` file manages the node with persistent storage:

```yaml
services:
  kaspad:
    image: kaspad:latest
    container_name: kaspad
    restart: unless-stopped
    command:
      - "--utxoindex"
      - "--rpclisten=0.0.0.0:16110"
      - "--appdir=/data"
      - "--nologfiles"
    ports:
      - "16110:16110"   # gRPC
      - "16111:16111"   # P2P
      - "17110:17110"   # wRPC Borsh
      - "18110:18110"   # wRPC JSON
    volumes:
      - kaspad-data:/data
    deploy:
      resources:
        limits:
          memory: 16G
          cpus: "4.0"
        reservations:
          memory: 8G

volumes:
  kaspad-data:
    driver: local
```

Start the node with `docker compose up -d`.

<Callout>
The `--nologfiles` flag is recommended for Docker deployments. Container logs should be collected through Docker's logging driver rather than written to files inside the container. Use `docker logs kaspad` to view output.
</Callout>

## Port Mapping

Expose the appropriate ports based on your use case:

| Port | Service | When to Expose |
|---|---|---|
| 16111 | P2P | Always (required for peer connections) |
| 16110 | gRPC | When external clients or miners need RPC access |
| 17110 | wRPC Borsh | When using wRPC Borsh clients |
| 18110 | wRPC JSON | When using wRPC JSON clients or web applications |

## Data Persistence

The `kaspad-data` named volume ensures blockchain data persists across container restarts and upgrades. Without a volume, the node would re-sync from scratch every time the container is recreated.

<Callout type="warn">
Never store blockchain data on a tmpfs or ephemeral storage in production. A full re-sync after data loss can take hours. Always use a persistent volume backed by SSD storage.
</Callout>

To back up the data directory, stop the container, use `docker run --rm` with the volume mounted to create a tar archive, then restart.

## Health Checks

Add a health check to your Docker Compose configuration to monitor node availability. A simple TCP check against the gRPC port works well:

```yaml
healthcheck:
  test: ["CMD-SHELL", "nc -z localhost 16110 || exit 1"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 60s
```

For a more thorough check, install `grpcurl` in the image and call the `GetInfo` RPC method directly.

## Resource Considerations

Allocate at least 8 GB of memory (tune with `--ram-scale`) and 4 CPU cores minimum. Use SSD-backed volumes for the data directory; avoid network-attached storage where possible, as I/O latency impacts sync performance.
