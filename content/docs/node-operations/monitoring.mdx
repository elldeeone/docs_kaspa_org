## Overview

Monitoring your Kaspa node ensures it remains synced, connected, and performing well. kaspad provides several mechanisms for observing node state: RPC methods for querying status, built-in performance metrics logging, and standard log output for diagnosing issues.

## RPC Status Methods

### GetInfo

The `GetInfo` RPC method returns basic information about the running node:

- **Server version**: The kaspad software version.
- **Is synced**: Whether the node considers itself fully synced with the network.
- **Mempool size**: Current count of mempool transactions.

This is the simplest health check. If `GetInfo` responds and reports `isSynced: true`, the node is operational.

### GetServerInfo

`GetServerInfo` provides server/network metadata that is not included in `GetInfo`, including:

- `networkId` (for example `mainnet`, `testnet-10`, `simnet`)
- `virtualDaaScore`
- RPC API version/revision

### GetSyncStatus

`GetSyncStatus` currently returns a single boolean field: `isSynced`.

<Callout type="info">
A node can report `isSynced: false` temporarily during normal operation if it briefly falls behind the DAG tip. This is common during high-load periods. If the node remains unsynced for more than a few minutes, investigate potential issues.
</Callout>

### GetMetrics

The `GetMetrics` RPC method returns comprehensive operational metrics organized into several categories:

**Process Metrics**:
- Resident memory size and virtual memory size
- CPU usage (cores)
- File descriptor count

**Connection Metrics**:
- Number of active peer connections

**Bandwidth Metrics**:
- Bytes sent and received per second
- Total bytes sent and received since node start

**Consensus Metrics**:
- Number of blocks and headers processed
- DAG tip count
- Virtual parent count
- Mempool size (number of unconfirmed transactions)

```bash
# Example: Query metrics using grpcurl
grpcurl -plaintext localhost:16110 protowire.RPC/GetMetrics
```

## Performance Metrics Logging

kaspad can log performance metrics periodically using the `--perf-metrics` flag:

```bash
kaspad --utxoindex --perf-metrics --perf-metrics-interval-sec=30
```

This outputs metrics to the log at the specified interval, including CPU usage, memory consumption, peer count, and bandwidth statistics. Example log output:

```
Processed 418 blocks and 425 headers in the last 10.00s (...)
```

<Callout>
Performance metrics logging is generally low-overhead and recommended for production nodes. Validate impact on your environment and logging volume.
</Callout>

## Key Metrics to Watch

| Metric | Starter Range | Action If Out of Range |
|---|---|---|
| Peer count | 10-100+ | Check firewall, network connectivity, `--outpeers` setting |
| Sync status | `isSynced: true` | Verify network connectivity and system resources |
| Mempool size | Varies with network activity | Sustained growth may indicate transaction processing issues |
| CPU usage | Below 80% of available cores | Consider increasing resources or reducing `--ram-scale` |
| Memory usage | Below container/system limit | Adjust `--ram-scale` downward |
| Bandwidth | Consistent with peer count | Check for network issues if bandwidth drops to zero |

Treat these values as operational starting points, not protocol-level invariants.

## Log Analysis

kaspad writes structured log output to both stdout and log files (unless `--nologfiles` is set). Key log messages to watch for:

- **`Processed ... blocks and ... headers in the last ...`** — Indicates consensus pipeline progress.
- **`[WRN]`** — Warnings about non-critical issues such as peer disconnections or temporary errors.
- **`[ERR]`** — Errors that may require attention, such as database issues or validation failures.
- **Performance monitor output** (when enabled) — CPU, memory, and I/O counters useful for capacity tuning.

<Callout type="warn">
Persistent `[ERR]` messages in the logs should be investigated promptly. While isolated errors are often transient (e.g., a peer sending malformed data), repeated errors can indicate database corruption, resource exhaustion, or software bugs.
</Callout>

## Setting Up Alerts

For production deployments, set up automated monitoring and alerting:

1. **Sync status check**: Poll `GetInfo`/`GetSyncStatus` periodically and alert if `isSynced` is `false` for more than 5 minutes.
2. **Peer count check**: Alert if the peer count drops below a minimum threshold (e.g., fewer than 5 peers).
3. **Process liveness**: Monitor the kaspad process and alert if it exits unexpectedly.
4. **Resource usage**: Monitor system-level CPU, memory, and disk usage. Alert before resources are exhausted.

These checks can be implemented with standard monitoring tools such as Prometheus, Grafana, Nagios, or simple cron-based scripts.
