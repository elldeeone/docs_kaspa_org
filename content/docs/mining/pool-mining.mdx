## Overview

Pool mining is an operational setup where a third-party pool coordinates work and payouts for participating miners. Pool behavior, accounting logic, dashboards, and payout policies are off-protocol and not defined by `rusty-kaspa` or KIPs.

## How Pool Mining Works

Pool behavior is implementation-specific. For canonical behavior, rely on Kaspa consensus and node docs; for pool behavior, rely on the selected pool's official documentation.

Use this page as a configuration checklist, not as a normative specification of pool internals.

## Choosing a Pool

Pool endpoints, fees, payout methods, and minimum payout thresholds are operational settings controlled by each pool and can change at any time.

When choosing a pool, verify:

- The official pool website and current stratum endpoints
- Fee model and payout method (PPLNS/PPS/PROP)
- Minimum payout threshold and payout frequency
- Region-specific endpoints and expected latency
- Reputation, uptime history, and transparency

<Callout type="warn">
Pool policy is off-protocol. Always confirm pool URLs, fees, and payout rules on the pool's official website before mining.
</Callout>

## Payout Methods

Payout method definitions and formulas are pool-policy details. Confirm exact meaning, timing, and settlement rules directly in the selected pool documentation.

## Configuring Mining Software

Different miners expose different CLI flags and sometimes use different names for the same concept (for example `--user` vs `-u`, `--pool` vs `-o`).

```bash
<miner-binary> \
  --algo KASPA \
  --pool stratum+tcp://<pool-host>:<port> \
  --user kaspa:<your_wallet_address>[.<worker_name>] \
  --pass <pool-password-or-x>
```

<Callout type="info">
Treat command syntax as a template only. Use the exact flags from your miner's official documentation and release notes for the version you run.
</Callout>

### ASIC Miner Configuration

ASIC and miner firmware interfaces vary by vendor and version. Use vendor documentation for exact UI/flag names and failover semantics.

## Setting Up Worker Names

Worker-label syntax is pool-specific. Some pools allow an optional worker label in the wallet/user field (for example, a `wallet.worker` style suffix). Verify the exact format in your pool's official documentation.

```
kaspa:qr...your_wallet_address.worker_name
```

Examples:
- `kaspa:qr...abc123.gpu-rig-01`
- `kaspa:qr...abc123.office-asic`

How labels appear in dashboards and payout records depends on pool implementation.

## Monitoring Your Earnings

Pool website dashboards and APIs are operator-managed services and are outside canonical protocol scope. Treat each pool's official documentation as the source of truth for account lookup, worker telemetry, and payout views.

### Miner Console Output

Console fields and metric names are miner-specific. Use your miner's official docs to interpret counters and errors.

<Callout type="warn">
If mining telemetry looks abnormal, validate against your miner and pool documentation before taking action.
</Callout>

## Pool Mining vs. Solo Mining

| Factor | Pool Mining | Solo Mining |
|---|---|---|
| Income consistency | Steady, proportional payouts | Highly variable (feast or famine) |
| Fees | Pool-defined fee (varies by operator) | No pool fee (but you pay for node hosting) |
| Setup complexity | Easier (no full node required) | Harder (must run and maintain kaspad) |
| Minimum hashrate | Any amount is viable | Needs significant hashrate to find blocks regularly |
| Block rewards | Shared proportionally | Full block reward when you find a block |
| Privacy | Pool knows your hashrate and address | Only the network sees your blocks |

<Callout type="info">
Pool mining and solo mining are a variance/operations tradeoff, not a protocol mandate. Pool mining generally reduces payout variance but adds pool-fee and counterparty considerations; solo mining removes pool counterparty risk but has higher variance and requires node operations.
</Callout>

## Tips for Pool Mining

- Use official pool and miner docs for current syntax, endpoints, and payout behavior.
- Keep node-side assumptions separate from pool-side assumptions.
- Re-check configuration after miner firmware/software upgrades.
