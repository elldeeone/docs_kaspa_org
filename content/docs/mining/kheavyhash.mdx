## Overview

kHeavyHash is Kaspa's proof-of-work (PoW) algorithm, used to secure a high-throughput BlockDAG running at 10 blocks per second (BPS).

The algorithm combines a heavy matrix multiplication step with the cSHAKE256 hash function, creating a compute profile that is distinct from the pure hash-chaining approaches used by SHA-256d (Bitcoin) or Ethash (former Ethereum PoW).

## How kHeavyHash Works

The kHeavyHash function operates in three stages:

### Step 1: Initial Hash

The block header is first hashed using **cSHAKE256**, producing a 256-bit digest. This serves as the input vector for the next stage.

```
hash_0 = cSHAKE256("ProofOfWorkHash", pre_pow_hash || timestamp || padding || nonce)
```

### Step 2: Matrix Multiplication

The 256-bit hash output is transformed through a **64x64 nibble-based matrix stage**. At a high level, the digest is expanded into nibbles, processed against the generated matrix, recomposed to bytes, and then mixed back into the hash pipeline.

```text
vector_nibbles = expand_to_nibbles(hash_0)
heavy_bytes = matrix_heavy_stage(vector_nibbles)
mixed = hash_0 XOR heavy_bytes
```

This matrix stage is the "heavy" part of kHeavyHash and dominates computational cost in nonce search.

### Step 3: Final Hash

The output of the matrix multiplication is XORed with the original hash, and the result is hashed again with cSHAKE256 to produce the final PoW hash:

```
result = cSHAKE256("HeavyHash", hash_0 XOR vector_out)
```

The final result is compared against the block's target difficulty. If `result < target`, the block is valid.

<Callout type="info">
The three-stage design (hash, matrix multiply, hash) ensures that the algorithm cannot be shortcut. Both the hashing and the linear algebra steps must be performed in full for every nonce attempt.
</Callout>

## Matrix Generation

The 64x64 matrix used in kHeavyHash is generated deterministically from each block header template's `pre_pow_hash`. Specifically:

- The matrix is derived from `pre_pow_hash`, so all nodes/miners compute the same matrix for a given header template.
- During nonce search for a fixed template, the matrix remains stable. A different template (different pre-PoW context) yields a different matrix.
- Each matrix element is a 4-bit value, making the full matrix 64 x 64 x 4 bits = 2,048 bytes (2 KB) in size.

Because the matrix is small enough to fit in on-chip memory or registers, it does not impose significant memory-hardness requirements. This is a deliberate design choice that distinguishes kHeavyHash from memory-hard algorithms like Ethash or RandomX.

## Difficulty Adjustment in a DAG Context

Kaspa's difficulty adjustment mechanism differs fundamentally from blockchain-based systems like Bitcoin because Kaspa operates as a **blockDAG** with multiple blocks produced in parallel.

### Per-Block Difficulty

Every block in the Kaspa DAG carries its own difficulty target. The difficulty adjustment algorithm (DAA) recalculates the target for each new block based on:

1. **Timestamps of recent DAG blocks**: The algorithm examines a window of recent blocks across the DAG to estimate the current network hashrate.
2. **DAA score progression**: The DAA score is used by consensus-time logic alongside sampled-window data.
3. **Target block rate**: The DAA aims to maintain the target rate of **10 blocks per second** across the entire network.

### How It Differs from Bitcoin

| Aspect | Bitcoin | Kaspa |
|---|---|---|
| Block rate | 1 block per ~10 minutes | 10 blocks per second |
| Adjustment frequency | Every 2,016 blocks (~2 weeks) | Every block |
| Parallel blocks | None (strict chain) | Multiple blocks per DAG level |
| Difficulty granularity | Coarse, step-wise | Fine-grained, continuous |

Because Kaspa adjusts difficulty on every block, the network can react much faster to hashrate changes than epoch-based systems, though stabilization time still depends on sampled-window dynamics.

### Block Difficulty at 10 BPS

At 10 blocks per second, the expected time between any two consecutive blocks from the network's perspective is **100 milliseconds**. This extremely high throughput means:

- **Individual block difficulty is lower** than in slow blockchains, since each block only needs to represent roughly 1/10th of a second of network hashrate.
- **Total work per second is equivalent** to what would be a single high-difficulty block in a slower system -- the security budget is distributed across many blocks.
- **Orphan/DAA management**: The DAG structure means that blocks produced simultaneously by different miners are not "orphaned" but are instead merged into the DAG. The difficulty must account for network propagation delays to ensure that the DAG does not grow faster than nodes can process it.

<Callout type="info">
Per-block difficulty adjustment plus DAG-based parallel block inclusion can reduce some variance patterns seen in slower epoch-adjustment systems, but miner outcomes still depend on hashrate share, latency, and pool policy.
</Callout>

## Summary

kHeavyHash is a carefully engineered proof-of-work function that balances several goals:

- **Security**: The combination of cSHAKE256 hashing and matrix multiplication makes the algorithm resistant to algebraic shortcuts.
- **DAG compatibility**: Fine-grained, per-block difficulty adjustment keeps the 10 BPS target stable under varying hashrate conditions.
- **Simplicity**: The algorithm avoids memory-hardness, keeping implementation straightforward across diverse hardware platforms.
