## Overview

Solo mining means you run your own Kaspa full node and mine directly against the network without sharing rewards with a pool. When you find a block, you receive the entire block reward. However, because you are competing against the total network hashrate, solo mining is only practical if you have sufficient hashing power to find blocks at a reasonable frequency.

Because Kaspa targets 10 blocks per second, solo miners can observe shorter wall-clock intervals between possible block opportunities than on slower-block-interval networks. Actual outcomes still depend on your share of total network hashrate and variance.

<Callout type="warn">
Solo mining requires running a full Kaspa node and keeping it synced at all times. If your node falls behind the DAG tip, your mined blocks will be rejected by the network.
</Callout>

## Requirements

Before you begin, ensure you have the following:

- **Hardware**: Mining-capable hardware supported by your chosen miner implementation.
- **Full node**: A running and fully synced instance of `kaspad` (the Kaspa full node daemon).
- **Mining software**: A miner that supports Kaspa-compatible solo mode for your hardware and current node version.
- **Kaspa wallet address**: A Kaspa address to receive block rewards.
- **Stable internet connection**: Low latency is important at 10 BPS to ensure your blocks propagate quickly.
- **Sufficient disk space**: The Kaspa UTXO set and DAG data require ongoing storage growth. Check current node-operations guidance for up-to-date sizing before deployment.

## Step 1: Set Up kaspad

Download and build or install `kaspad` from the official Kaspa repository. Then start the node with the required flags for mining.

Solo mining is a two-step process: first you run a `kaspad` full node, then you run a separate miner application that connects to the node and specifies your mining address. The mining address is configured on the **miner**, not on the node.

### Running kaspad

```bash
kaspad
```

**Key flags:**

| Flag | Purpose |
|---|---|
| `--utxoindex` | Enables address/UTXO-indexed RPC queries. Useful for wallet and explorer workflows, but not required for basic `getBlockTemplate` solo mining. |

<Callout type="info">
The `--utxoindex` flag causes `kaspad` to maintain an additional index over the UTXO set. This increases disk usage and initial sync time. Enable it when you need address/UTXO-indexed RPC methods; solo mining itself can run without it.
</Callout>

### Optional Flags

```bash
kaspad \
  --rpclisten=0.0.0.0:16110 \
  --listen=0.0.0.0:16111
```

| Flag | Purpose |
|---|---|
| `--rpclisten` | Sets the gRPC listen address. Default is `localhost:16110`. Set to `0.0.0.0:16110` if your miner runs on a different machine. |
| `--listen` | Sets the P2P listen address. Default is `0.0.0.0:16111`. |
| `--enable-unsynced-mining` | Allows the node to accept blocks from RPC while not fully synced. Only use this for testing purposes. |

<Callout type="warn">
The `kaspad` node does **not** have a `--mining-address` flag. The mining address is specified when launching your miner software (see Step 2). Do not pass a mining address to `kaspad`.
</Callout>

### Wait for Sync

After starting `kaspad`, wait for it to fully sync with the network. You can monitor sync progress in the log output. The node will display messages indicating the current blue score and DAG tip as it catches up.

```
[INF] Blue score: 58234012, DAG tip timestamp: 2025-12-01 14:22:33
```

Mining before the node is fully synced will result in rejected blocks.

## Step 2: Connect Your Miner

Once `kaspad` is running and synced, connect your mining software to the node's gRPC endpoint.

### Miner Configuration

Miner binaries, transport modes, and flag names are software-specific and outside canonical `rusty-kaspa`/`kips` scope. For solo mining, configure your miner with:

- A Kaspa payout address
- The gRPC endpoint of your synced `kaspad` node (default local endpoint: `127.0.0.1:16110`)

<Callout type="info">
Use your miner's official documentation for exact command syntax and required solo-mode options.
</Callout>

## Step 3: Monitor Your Mining

### Hashrate Monitoring

Your mining software will report hashrate and status in miner-specific output formats. Treat node-side acceptance and chain inclusion as canonical, and miner-side counters as local telemetry.

### Checking Block Rewards

You can verify that blocks you mined are being accepted by checking your wallet balance or querying the node:

- **Using the CLI wallet**: Open `kaspa-wallet`, connect to your node, and run the `list` command to see your account balances.
- **Using the wRPC API**: Query the `getBalanceByAddress` method via the wRPC interface (see the [wRPC API](/docs/developer-guide) documentation).

### Expected Block Frequency

Your expected time between blocks depends on your share of the total network hashrate:

```
Expected blocks per day = (your_hashrate / network_hashrate) * 10 BPS * 86400 seconds
```

For example, if the network hashrate is 50 TH/s and you have 5 GH/s:

```
(5 / 50,000,000) * 10 * 86400 = 0.0864 blocks/day ~ 1 block every ~11.5 days
```

<Callout type="warn">
Solo mining income is highly variable. You may go long periods without finding a block, then find several in quick succession. Pool mining provides more consistent payouts if income stability is important to you. See the [Pool Mining](/docs/mining/pool-mining) guide for details.
</Callout>

## Troubleshooting

### Common Issues

| Problem | Likely Cause | Solution |
|---|---|---|
| Miner cannot connect to kaspad | gRPC port not accessible | Check `--rpclisten` flag and firewall rules. |
| Blocks found but not accepted | Node not fully synced | Wait for full sync before mining. |
| Unexpected hashrate telemetry | Miner/hardware tuning is implementation-specific | Use your miner or hardware vendor docs for tuning guidance. |
| "UTXO index not available" error | Missing `--utxoindex` for address-index RPC | Restart `kaspad` with `--utxoindex` if your workflow requires those RPC methods. |

### Performance Tips

- Keep the node fully synced and monitor `kaspad` logs as canonical sync/health indicators.
- Keep RPC connectivity between miner and node stable.
- Re-validate miner settings after upgrades.
