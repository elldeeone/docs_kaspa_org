## Overview

Kaspa wallets use **Hierarchical Deterministic (HD)** key derivation following the BIP-32, BIP-39, and BIP-44 standards. This means a single mnemonic seed phrase (12 or 24 words) can deterministically generate an unlimited number of key pairs and addresses. Wallet portability depends on using the same derivation account type/path.

## BIP-39: Mnemonic Generation

The wallet creation process begins with generating a **BIP-39 mnemonic** — a human-readable representation of cryptographic entropy.

1. **Entropy generation**: The wallet generates cryptographically secure entropy (commonly 128-bit for 12 words or 256-bit for 24 words).
2. **Checksum**: A SHA-256 checksum prefix is appended to the entropy.
3. **Word mapping**: The bitstream is split into 11-bit groups and mapped to words from the BIP-39 English wordlist (2048 words).
4. **Seed derivation**: The mnemonic is passed through PBKDF2-HMAC-SHA512 with 2048 iterations to produce a 512-bit seed.

The result is a 24-word phrase like: `abandon ability able about above absent absorb abstract absurd abuse access accident ...`

<Callout>
Your mnemonic is the root of all your keys. Anyone who obtains it can derive every address and spend all funds in your wallet. Write it on paper and store it in a secure physical location. Never store it digitally or share it with anyone.
</Callout>

## BIP-32: HD Key Tree

From the 512-bit seed, BIP-32 defines a tree structure for deriving child keys. Each node in the tree can produce child nodes, creating a hierarchy:

```
Master Key (from seed)
├── Child 0
│   ├── Grandchild 0/0
│   ├── Grandchild 0/1
│   └── ...
├── Child 1
│   ├── Grandchild 1/0
│   └── ...
└── ...
```

Each derivation step uses HMAC-SHA512 to combine the parent key with an index number, producing both a child private key and a chain code. The chain code enables further derivation without revealing the parent key.

**Hardened derivation** (indicated by an apostrophe `'` in the path) uses the parent's private key as input, making it impossible to derive the child key from the parent's public key alone. This is critical for security — the purpose, coin type, and account levels all use hardened derivation.

## BIP-44: Derivation Path

BIP-44 standardizes the HD tree structure for multi-coin wallets. For standard (BIP-32) Kaspa accounts, the derivation path is:

```
m / 44' / 111111' / account' / change / index
```

Each component has a specific meaning:

| Level | Value | Purpose |
|---|---|---|
| Purpose | `44'` | BIP-44 standard (hardened) |
| Coin type | `111111'` | Kaspa's registered coin type (hardened) |
| Account | `0'`, `1'`, etc. | Separate accounts within the wallet (hardened) |
| Change | `0` or `1` | `0` = receive addresses, `1` = change addresses |
| Index | `0`, `1`, `2`, ... | Sequential address index |

<Callout type="info">
Kaspa tooling commonly uses coin type `111111` for standard accounts. Some account families use different derivation purposes/paths (for example multisig and legacy compatibility paths), so keep account type/path consistent when restoring.
</Callout>

### Path variants by account type

- **Standard BIP-32 accounts**: Use purpose `44'` and coin type `111111'`.
- **Multisig accounts**: Use a different purpose (`45'`) in current wallet tooling.
- **Legacy accounts**: Use an older derivation family (including `/972/` paths).

Wallet recovery is portable when both sides use the same account type and derivation path.

## Receive Addresses vs Change Addresses

The **change** level in the derivation path distinguishes two categories of addresses:

- **Receive addresses** (`change = 0`): These are the addresses you share with others to receive payments. Each new receive address is derived by incrementing the index: `m/44'/111111'/0'/0/0`, `m/44'/111111'/0'/0/1`, `m/44'/111111'/0'/0/2`, and so on.

- **Change addresses** (`change = 1`): When a transaction spends a UTXO and the amount exceeds what is needed, the remainder is sent to a change address. Change addresses are derived from the same seed but on a separate branch: `m/44'/111111'/0'/1/0`, `m/44'/111111'/0'/1/1`, etc.

Using separate branches for receive and change improves privacy by making it harder for observers to link your transactions.

## Account Discovery

When recovering a wallet from a seed phrase, the wallet must discover which accounts have been used. The standard algorithm is:

1. Start with account `0'`.
2. Derive the first 20 receive addresses (the **gap limit**).
3. Check if any of those addresses have transaction history on the network.
4. If activity is found, record the account and proceed to account `1'`.
5. Repeat until an account with no activity is found.

## Address Gap Limit

The **gap limit** (typically 20) defines how many consecutive unused addresses the wallet checks before concluding that no further addresses are in use. If you have generated receive addresses with gaps between them (e.g., you generated address index 25 without using indices 5 through 24), some wallets may not discover the later addresses during recovery.

<Callout type="warn">
Avoid creating large gaps between used addresses. If you skip many address indices, a wallet recovering from seed may not find all your funds. Most wallets generate addresses sequentially and handle this automatically.
</Callout>

## Cross-Wallet Compatibility

Because Kaspa wallets share BIP-32/39 foundations, the same seed phrase can be portable across wallets when the same account type/path is used:

- A wallet created in the **Web Wallet** can be recovered in the **CLI Wallet**.
- A wallet created in **KasVault** can be recovered on a **Ledger** device.
- Any wallet using the same derivation path family will discover the same set of addresses and balances.

This portability is a fundamental advantage of the HD derivation standard.

## Schnorr Key Pairs

At each leaf of the derivation tree, the derived private key is a 256-bit scalar on the secp256k1 curve. Kaspa wallet flows primarily use **Schnorr signatures**, while ECDSA-related address/version and script support also exists in protocol tooling. The public key is used to derive Kaspa addresses.

The derivation process itself is identical whether the resulting key pair will be used for Schnorr or ECDSA signing — the signature scheme is applied at the transaction signing step, not during key derivation.
