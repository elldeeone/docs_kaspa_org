## Overview

The Kaspa ecosystem offers several wallet options, each suited to different use cases. Kaspa wallets use BIP-32/39-based HD derivation, but full portability depends on using the same account type/path family (standard, multisig, or legacy). Mnemonic flows commonly use 12-word or 24-word phrases.

This page helps you understand the wallet architecture, choose the right wallet for your needs, and understand the trade-offs between security, convenience, and functionality.

## Wallet Architecture

The Kaspa wallet stack is organized into four tiers, from low-level primitives up to complete wallet applications. Each tier builds on the one below it.

### Tier 1: Wallet Primitives

The foundation of the wallet stack is a set of cryptographic and encoding primitives. These are standalone building blocks that handle the core operations any wallet needs.

| Primitive | Purpose |
|---|---|
| **Mnemonics** | BIP-39 seed phrase generation and recovery. Supports 12-word and 24-word phrases with optional passphrases. Converts human-readable word sequences into deterministic seeds for key derivation. |
| **Keys** | secp256k1 elliptic curve key operations. Generates private/public keypairs, handles key serialization, and provides the signing primitives used for Schnorr signatures. Built on a customized `kaspa-bip32` crate. |
| **Derivation** | BIP-32 hierarchical deterministic derivation. Standard accounts use BIP-44 style paths (`m/44'/111111'/account'/change/index`), with separate variants for multisig/legacy account families. |
| **Addresses** | Kaspa address encoding and validation. Prefixes include `kaspa:` (mainnet), `kaspatest:` (testnet), `kaspasim:` (simnet), and `kaspadev:` (devnet). Address versions include public-key, script-hash, and ECDSA-related variants. |

These primitives are available as standalone Rust crates (`kaspa-bip32`, `kaspa-addresses`, `kaspa-consensus-core`) and through the WASM SDK for JavaScript/TypeScript environments.

### Tier 2: Wallet SDK

The [Wallet SDK](/docs/wallets/wallet-sdk) provides infrastructure components for building wallet engines. It handles the complex aspects of interacting with Kaspa's UTXO model.

| Component | Role |
|---|---|
| **UtxoProcessor** | Connects to a Kaspa node via wRPC and processes the stream of UTXO change notifications. Manages subscriptions and tracks UTXO additions and removals in real time. |
| **UtxoContext** | Maintains the current UTXO state for a set of addresses. Provides the UTXO set that the transaction generator draws from when constructing transactions. |
| **Generator** | Constructs transactions from available UTXOs. Handles input selection, output creation, fee calculation, change addresses, and automatic compound transactions when many small UTXOs need consolidation. |

The SDK also provides event notifications (balance changes, UTXO discovery, transaction confirmations), pending transaction tracking, and account ID management.

<Callout type="info">
A key design principle of Kaspa's UTXO model: you send transactions but you receive UTXOs. Incoming payments arrive as individual UTXO notifications, not as consolidated transaction events. The SDK performs client-side aggregation to present a transaction-oriented view.
</Callout>

### Tier 3: Wallet API

The [Wallet API](/docs/wallets/wallet-api) wraps the SDK into a complete wallet management interface. It adds wallet file management, account lifecycle, encrypted storage, and a procedural interface for all wallet operations.

Key capabilities:

- **Wallet files** -- Create, open, close, and manage encrypted wallet files across platforms (filesystem, browser storage, extension storage).
- **Account management** -- Support for multiple account types (BIP-32, multisig, legacy, watch-only) running concurrently within a single wallet.
- **Key lifecycle** -- Automatic BIP-39 mnemonic handling, key derivation, import/export, and secure memory erasure.
- **Transaction operations** -- Send, estimate fees, and track transaction history with annotations.
- **Interoperability** -- Wallet files created by any application using the Wallet API (Kaspa CLI Wallet, Kaspa NG) are cross-compatible.

### Tier 4: Wallet Applications

At the top of the stack are the wallet applications that users interact with directly. These are built on the Wallet API (or the SDK, in some cases) and provide graphical or command-line interfaces.

| Application | Platform | Built On |
|---|---|---|
| [Web Wallet](https://wallet.kaspanet.io) | Browser | WASM SDK |
| [CLI Wallet](/docs/wallets/cli-wallet) | Terminal | Wallet API (Rust) |
| [Hardware Wallets](/docs/wallets/hardware-wallets) | Hardware device + companion software | Hardware signing flow |

## Wallet Types

### Web Wallet

The [Kaspa Web Wallet](https://wallet.kaspanet.io) runs entirely in your browser. Your keys are generated and stored locally in browser storage -- they never leave your device. The web wallet is the easiest way to get started with Kaspa and is suitable for everyday use.

### CLI Wallet

The [CLI Wallet](/docs/wallets/cli-wallet) (`kaspa-wallet`) is a command-line tool included in the rusty-kaspa project. It connects to a Kaspa node via wRPC and performs all key management and signing locally. The CLI wallet is ideal for server environments, scripting, and advanced operations like multi-sig and UTXO sweeps.

### Hardware Wallets

[Hardware wallets](/docs/wallets/hardware-wallets) store your private keys on a dedicated physical device with a secure element. They are generally the strongest option for long-term custody because signing can be isolated from day-to-day computing environments.

## Comparison Table

| Feature | Web Wallet | CLI Wallet | Hardware Wallets |
|---|---|---|---|
| Platform | Browser | Terminal | Dedicated device + companion software |
| Key storage | Browser (local encrypted data) | Encrypted wallet file | Secure element/chip on device |
| Automation and scripting | Limited | Strong | Limited |
| Hardware key isolation | No | No | Yes |
| Best for | Fast onboarding and daily use | Infrastructure, automation, advanced workflows | Long-term custody and high-value storage |

## Recommendations by Use Case

### Daily Spending and Receiving

Use the **Web Wallet** for straightforward sending and receiving. It is the fastest way to get started and works well for routine balances.

### Large Holdings and Long-Term Storage

Use a **hardware wallet**. Your private keys remain on the physical device and are not directly exposed to your workstation environment.

<Callout>
For significant holdings, a hardware wallet is strongly recommended. Software wallets -- even well-designed ones -- are only as secure as the device they run on.
</Callout>

### Developers and Server Environments

Use the **CLI Wallet**. It supports scripting, automation, and advanced features like multi-sig, UTXO sweeps, and watch-only mode. It is the best choice for managing mining payouts, running payment infrastructure, or integrating Kaspa into backend systems.

### dApp Interaction

Use a wallet that explicitly supports the dApp signing flow your application requires. Verify compatibility in the wallet provider's current documentation before relying on it in production.

### Custom Wallet Development

For building your own wallet application, choose the appropriate tier:

- **Wallet API** -- Use this when building a full wallet application with account management, storage, and encryption. This is the fastest path to a feature-complete wallet.
- **Wallet SDK** -- Use this when you need custom UTXO handling, specialized transaction construction, or exchange-grade control over the wallet engine.
- **Direct Node RPC** -- Use this when you need maximum control and are prepared to implement UTXO tracking, subscription management, and transaction construction from scratch.

## Seed Phrase Portability

For standard BIP-32 account families, wallets derive keys using BIP-44 style paths (`m/44'/111111'/0'/0/index`). In practice:

- Recovery is typically portable across wallets that support the same account family and derivation path.
- Both 12-word and 24-word mnemonic flows are common, but support details vary by wallet implementation.
- Legacy, multisig, or watch-only account models may require wallet-specific migration/import steps.

<Callout type="info">
Some wallet products use different backup/recovery models. Always verify recovery compatibility before funding a wallet.
</Callout>

## Choosing a Wallet: Quick Guide

- **New to Kaspa?** Start with the [Web Wallet](/docs/wallets/web-wallet).
- **Holding more than you can afford to lose?** Get a [hardware wallet](/docs/wallets/hardware-wallets).
- **Building applications or running infrastructure?** Use the [CLI Wallet](/docs/wallets/cli-wallet).
- **Interacting with dApps?** Use a wallet that documents dApp-signing support for your target application.
- **Building a custom wallet?** Start with the [Wallet API](/docs/wallets/wallet-api) or [Wallet SDK](/docs/wallets/wallet-sdk).
