## Overview

Web wallets provide a fast onboarding path and convenient day-to-day access. They are best treated as hot-wallet environments: convenient, but with stronger browser/device risk than dedicated hardware signing setups.

<Callout>
UI flows and feature availability can change between releases. Use the wallet's current official documentation and in-app prompts as the source of truth for exact steps.
</Callout>

## Safe Setup Flow

1. Open the official wallet URL from a trusted source.
2. Create or import a wallet using the wallet's supported mnemonic flow.
3. Back up recovery material offline before funding addresses.
4. Use an additional local unlock/password if offered.
5. Verify the first receive address and send a small test transaction.

## Sending and Receiving

- Use fresh receive addresses when practical.
- Verify destination addresses before signing.
- Treat transaction settlement policy (required confirmations) as your own risk decision, not a fixed protocol rule.

## UTXO Behavior

Kaspa wallets operate on UTXOs. Depending on your UTXO distribution, large sends may require extra consolidation/batching behavior handled by the wallet engine. If the wallet prompts for compounding/consolidation steps, review the prompt details before approval.

## Browser Security Practices

- Keep browser and OS updated.
- Avoid untrusted extensions in the profile used for wallet operations.
- Verify the exact URL each session.
- Do not store mnemonics/private keys in screenshots, notes apps, or cloud docs.
- Prefer a dedicated browser profile for financial operations.

<Callout type="warn">
For larger balances, use a hardware-signing workflow or cold-storage architecture. Browser wallets are operationally convenient but carry broader client-side attack surface.
</Callout>

## Recovery Discipline

- Test restore procedure with small balances before production use.
- Keep redundant physical backups in separate secure locations.
- Record wallet/network/account context needed for deterministic restore.
