## Overview

The Kaspa Wallet SDK is a Rust-based framework for building wallet applications on the Kaspa network. It is implemented as part of the [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) project and compiles to WebAssembly (WASM) for use in browser and Node.js environments. The SDK provides primitives that handle UTXO tracking, transaction construction, signing, fee calculation, and network communication through an event-driven architecture.

Rather than polling the network for changes, the SDK operates by registering addresses for monitoring and submitting transactions, then receiving transaction-related notification events and balance updates asynchronously.

<Callout type="info">
The same Rust code that powers the CLI wallet and web wallet is available as a library. You can build custom wallet applications using the same battle-tested components.
</Callout>

## Architecture

The SDK is built around three core infrastructure components that work together:

| Component | Role |
|---|---|
| **UtxoProcessor** | Singleton coordinator that bridges the RPC connection, address subscriptions, and UtxoContext instances |
| **UtxoContext** | Per-account interface that tracks addresses, caches UTXOs, maintains balances, and emits events |
| **Generator** | Transaction builder that selects UTXOs, calculates fees, handles compound transactions, and produces PendingTransaction objects |

Supporting these are the **PendingTransaction** (wraps a transaction for signing and submission) and **GeneratorSummary** (provides aggregate statistics after transaction generation).

## UtxoProcessor

The `UtxoProcessor` is the primary orchestration component. It manages UTXO processing between multiple `UtxoContext` instances and acts as a bridge between the Kaspa node RPC connection, address subscriptions, and account contexts.

There should be exactly one `UtxoProcessor` per RPC connection.

```typescript
const processor = new UtxoProcessor({
  rpc: rpcClient,       // RpcClient instance
  networkId: "mainnet"  // Network identifier
});

// Start processing — begins listening for UTXO notifications
await processor.start();

// ... wallet operations ...

// Stop processing — halts all notification handling
await processor.stop();
```

The UtxoProcessor is also the central event hub. All wallet events (balance changes, transaction notifications, connection status) are received through its event listener:

```typescript
processor.addEventListener("balance", (event) => {
  console.log("Balance changed:", event.data);
});
```

## UtxoContext

A `UtxoContext` represents a single wallet account. It monitors a set of addresses, aggregates UTXO entries, tracks balances in real time, and emits events whenever activity occurs.

```typescript
const context = new UtxoContext({
  processor: processor,
  id: accountId  // Optional: 64-character hex string
});

// Track addresses to begin monitoring
await context.trackAddresses([
  "kaspa:qr0...",
  "kaspa:qr1...",
]);
```

When `trackAddresses()` is called, the system:

1. Registers the addresses for transaction notifications via `subscribeUtxosChanged()`.
2. Enumerates all existing UTXOs for those addresses using `getUtxosByAddresses()`.
3. Posts discovery events for all detected UTXOs.

### Balance Tracking

The `UtxoContext` maintains a real-time balance with three components:

| Component | Description |
|---|---|
| **mature** | Funds available for spending (confirmed UTXOs past the maturity threshold) |
| **pending** | Funds received but not yet confirmed |
| **outgoing** | Funds being sent that have not yet been accepted |

```typescript
const balance = context.balance;
console.log("Mature:", balance.mature);
console.log("Pending:", balance.pending);
console.log("Outgoing:", balance.outgoing);
```

<Callout type="warn">
A `UtxoContext` is intended to represent a single account. For exchange implementations, create separate `UtxoContext` instances per user account to isolate activity and balances.
</Callout>

## Generator

The `Generator` creates transactions from UTXO entries. It dynamically calculates transaction mass, accounts for custom fee rates, automatically creates change outputs, and handles compound (batch/sweep) transactions when the UTXO set exceeds the maximum mass allowed in a single transaction.

```typescript
const generator = new Generator({
  entries: context,  // UtxoContext, IUtxoEntry[], or UtxoEntryReference[]
  outputs: [
    { address: "kaspa:qr0...", amount: kaspaToSompi("10") }
  ],
  changeAddress: "kaspa:qchange...",
  priorityFee: 1000n  // Optional: priority fee in sompi
});

// Iterate through transactions (may produce multiple for large UTXO sets)
let pending;
while (pending = await generator.next()) {
  await pending.sign([privateKey]);
  await pending.submit(rpc);
}

const summary = generator.summary();
console.log(`Generated ${summary.transactions} transaction(s), fees: ${summary.fees} sompi`);
```

### Compound Transactions

When a wallet holds many small UTXOs (common for mining payouts), a single transaction may not consume them all because of transaction mass limits. The Generator automatically handles this by creating a chain of compound transactions:

1. **Batch transactions**: Consolidate UTXOs into fewer, larger outputs sent to the change address.
2. **Final transaction**: The last transaction sends the requested amount to the destination address(es).

Each `PendingTransaction` has a `type` property that is either `"batch"` or `"final"`.

<Callout>
All compound transactions must be signed and submitted in sequence. Each subsequent transaction depends on the outputs of the previous one.
</Callout>

### Fee Calculation

Transaction fees in Kaspa are based on **transaction mass** (a function of size in bytes and script verification cost):

```
fee = transaction_mass * fee_rate
```

The Generator computes transaction mass automatically. Use `estimate()` to calculate fees without generating actual transactions:

```typescript
const estimate = await generator.estimate();
console.log(`Estimated fees: ${estimate.fees}, transactions: ${estimate.transactions}`);
```

## Events System

The Wallet SDK uses an event-driven architecture. All events are published through the `UtxoProcessor`.

### Event Types

| Event | Description |
|---|---|
| `"connect"` | RPC connection established |
| `"disconnect"` | RPC connection lost |
| `"utxo-proc-start"` | UtxoProcessor has started |
| `"utxo-proc-stop"` | UtxoProcessor has stopped |
| `"utxo-proc-error"` | UtxoProcessor encountered an error |
| `"utxo-index-not-enabled"` | Connected node does not have UTXO index enabled |
| `"sync-state"` | Node synchronization state change |
| `"daa-score-change"` | DAA score has changed |
| `"pending"` | Transaction mined but not yet mature |
| `"maturity"` | Transaction reached minimum confirmations |
| `"discovery"` | UTXOs discovered during initial address scanning |
| `"stasis"` | Coinbase transaction detected but not yet pending |
| `"reorg"` | Reorganization invalidated one or more UTXOs |
| `"balance"` | Account balance has changed |
| `"error"` | General error |

### Transaction Lifecycle

Transactions progress through: **Discovery** (startup scan) -> **Stasis** (coinbase only) -> **Pending** (mined, not mature) -> **Maturity** (spendable). A **Reorg** event can occur at any stage, invalidating affected UTXOs.

```typescript
processor.addEventListener("pending", (event) => {
  console.log(`Pending tx ${event.data.id}, value: ${event.data.value} sompi`);
});

processor.addEventListener("maturity", (event) => {
  console.log(`Mature tx ${event.data.id} is now spendable`);
});

processor.addEventListener("reorg", (event) => {
  console.log(`Reorg invalidated tx ${event.data.id}`);
});

processor.addEventListener("balance", (event) => {
  const { id, balance } = event.data;
  if (balance) {
    console.log(`Account ${id}: ${balance.mature} sompi (${balance.matureUtxoCount} UTXOs)`);
  }
});
```

## Complete Integration Example

```typescript
import {
  RpcClient, UtxoProcessor, UtxoContext, Generator,
  kaspaToSompi, sha256FromText
} from "kaspa-wasm";

// 1. Connect
const rpc = new RpcClient({ url: "ws://127.0.0.1:17110", networkId: "mainnet" });
await rpc.connect();

// 2. Create processor and register events
const processor = new UtxoProcessor({ rpc, networkId: "mainnet" });

processor.addEventListener("balance", (event) => {
  const { id, balance } = event.data;
  console.log(`[${id}] Balance: ${balance?.mature} sompi`);
});
processor.addEventListener("connect", () => console.log("Connected"));
processor.addEventListener("disconnect", () => console.log("Disconnected"));

// 3. Start processor and create context
await processor.start();

const context = new UtxoContext({
  processor,
  id: sha256FromText("my-wallet-account-0")
});

await context.trackAddresses(["kaspa:qr0abc...", "kaspa:qr1def..."]);

// 4. Build and send a transaction
const generator = new Generator({
  entries: context,
  outputs: [{ address: "kaspa:qrecipient...", amount: kaspaToSompi("50") }],
  changeAddress: "kaspa:qchange...",
  priorityFee: 1000n
});

let pending;
while (pending = await generator.next()) {
  await pending.sign([privateKey]);
  await pending.submit(rpc);
}

// 5. Cleanup
await context.clear();
await processor.stop();
await rpc.disconnect();
```

## Integration Patterns

### Multi-Account Wallet

Create a separate `UtxoContext` for each account and use the account ID to route events:

```typescript
const accounts = new Map();
for (let i = 0; i < numAccounts; i++) {
  const id = sha256FromText(`account-${i}`);
  const ctx = new UtxoContext({ processor, id });
  await ctx.trackAddresses(deriveAddresses(i));
  accounts.set(id, { context: ctx, index: i });
}

processor.addEventListener("balance", (event) => {
  const account = accounts.get(event.data.id);
  if (account) updateUI(account.index, event.data.balance);
});
```

### Exchange Wallet

For exchanges with many user deposit addresses, create one `UtxoContext` per user account:

```typescript
function createUserAccount(userId, depositAddresses) {
  const id = sha256FromText(`user-${userId}`);
  const ctx = new UtxoContext({ processor, id });
  ctx.trackAddresses(depositAddresses);
  return { context: ctx, id, userId };
}
```

<Callout type="warn">
For exchanges with a very large number of users, monitor memory usage. Each `UtxoContext` maintains its own UTXO cache. For extremely large-scale deployments, consider managing UTXOs directly through the `RpcClient` API.
</Callout>
