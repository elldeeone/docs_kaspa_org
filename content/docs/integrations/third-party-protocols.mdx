## Scope Boundary

This documentation set is canonical for Kaspa L1 node/wallet/RPC behavior. Third-party protocol layers built around Kaspa transaction metadata are external ecosystems and are not protocol-canonical in this docs set.

<Callout type="warn">
Treat third-party protocol rules, token/indexer state, and roadmap claims as external dependencies. Validate them directly with their maintainers and documentation before integrating.
</Callout>

## Integration Pattern (Generic)

External protocols commonly:

1. Encode metadata into standard Kaspa transactions.
2. Read ordered transaction history from Kaspa nodes.
3. Build derived state in external indexers/services.

Kaspa nodes remain authoritative for L1 transaction/block validity, while protocol-specific derived state is maintained by third-party software.

## Due-Diligence Checklist

- Verify protocol specification ownership and versioning.
- Verify deterministic replay rules for derived state.
- Verify indexer behavior across reorgs and node restarts.
- Verify operational SLOs (latency, data freshness, rollback handling).
- Verify security model and upgrade governance.

## Operational Recommendations

- Keep a local archival/indexing pipeline if your product depends on derived state.
- Pin exact protocol/indexer versions in production.
- Instrument cross-checks between node data and derived-state data.
- Plan explicit incident playbooks for indexer divergence.
