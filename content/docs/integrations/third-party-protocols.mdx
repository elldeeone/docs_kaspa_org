## Kaspa as a Pure L1

Kaspa is a pure Layer 1 protocol focused on fast, secure, and scalable value transfer. The node software validates blocks, transactions, and UTXO state — but does not natively execute smart contracts or support on-chain programmability beyond standard transaction scripts.

This design keeps the consensus layer lean and fast. Every node in the network validates the same minimal rule set, which is how Kaspa achieves 10 blocks per second with sub-second confirmation times.

<Callout type="info">
Native smart contract support (via a future scripting or execution layer) is on the Kaspa roadmap. Until that ships, all programmable functionality is built by third-party protocols on top of the L1.
</Callout>

## The Sequencer Pattern

Third-party protocols use Kaspa as a **decentralized sequencer**. The pattern works as follows:

1. **Embed metadata in transactions**: A protocol defines its own data format and encodes it in the `OP_RETURN` output or other script fields of a standard Kaspa transaction.
2. **Kaspa orders the transactions**: Because Kaspa's GHOSTDAG consensus produces a deterministic ordering of all transactions across the DAG, anyone running a Kaspa node sees the same sequence of protocol operations.
3. **Off-chain indexers interpret the data**: Protocol-specific indexers scan the Kaspa DAG, extract embedded metadata, validate protocol rules (e.g., token balances, minting limits), and build a derived state.

The key insight is that Kaspa provides **global ordering and data availability** without needing to understand the protocol's semantics. The L1 acts as an immutable, high-throughput sequencer that all participants can independently verify.

This is similar to how Ordinals and BRC-20 work on Bitcoin, but Kaspa's high block rate and fast finality make the sequencer pattern significantly more practical for real-time applications.

## KRC-20 Token Standard (Kasplex)

[Kasplex](https://kasplex.org) is the primary protocol building on the sequencer pattern. It defines the **KRC-20 token standard**, which enables fungible token operations (deploy, mint, transfer) on Kaspa.

### How KRC-20 Works

- **Token deployment**: A deploy transaction embeds metadata (token name, symbol, max supply, mint limit per transaction) in a Kaspa transaction.
- **Minting**: Users submit mint transactions that reference a deployed token. The Kasplex indexer validates that the mint does not exceed supply or per-transaction limits.
- **Transfers**: Token transfers are encoded as Kaspa transactions with embedded transfer metadata. The indexer updates token balances accordingly.
- **Indexer consensus**: Anyone can run a Kasplex indexer against a Kaspa archival node and independently derive the same token state. There is no trusted third party.

<Callout type="warn">
KRC-20 tokens are managed by third-party indexers, not by the Kaspa node itself. The Kaspa node sees only standard transactions. If an indexer has a bug or applies different rules, token state may diverge. Always verify which indexer implementation you are relying on.
</Callout>

## Smart Contracts on the Roadmap

The Kaspa project has smart contract support on its long-term roadmap. Potential approaches under discussion include:

- **A dedicated execution layer** that leverages the DAG's ordering guarantees for contract state transitions.
- **Enhanced scripting capabilities** that extend the existing transaction script engine with additional opcodes.

Until native smart contracts are available, the sequencer pattern and protocols like KRC-20 remain the primary way to build programmable applications on Kaspa.
