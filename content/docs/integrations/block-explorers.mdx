## Overview

Kaspa explorers present DAG-oriented data: blocks, transactions, addresses, and network metrics. For production integrations, treat public explorers as convenience surfaces and keep a node-backed RPC path for canonical data.

<Callout type="info">
Public explorer features and API availability can change without notice. Verify current endpoint coverage directly in each explorer's live documentation.
</Callout>

## Public Explorer Usage

Common usage patterns:

- Human verification of transaction status.
- Support/debug links in user-facing apps.
- Lightweight read-only lookups where strict availability guarantees are not required.

Do not make business-critical settlement decisions from a single third-party explorer source.

## Building Explorer Functionality from Node RPC

### Core Requirements

1. A running Kaspa node (`kaspad`) with required indexes enabled for your queries.
2. RPC connectivity (wRPC or gRPC).
3. A local database/indexer for query performance.
4. DAG-aware UI/backend logic for selected-parent and merge-set behavior.

### Useful RPC Methods

| Method | Purpose |
|---|---|
| `getBlock` | Retrieve block details by hash |
| `getBlocks` | Stream/range block retrieval for backfill |
| `getVirtualChainFromBlock` | Follow selected-parent changes |
| `getBlockDagInfo` | DAG-level metadata and liveness |
| `getUtxosByAddresses` | Address UTXO state (requires node index support) |
| `notifyBlockAdded` | Real-time block ingestion |
| `notifyVirtualChainChanged` | Reorg/selected-parent updates |

### Indexing Strategy

1. Backfill historical DAG data into your database.
2. Switch to subscription-based ingestion for new blocks.
3. Track virtual-chain updates to handle reorg effects.
4. Build address/transaction secondary indexes for UI queries.

## Reliability Guidance

- Keep your own node as the canonical source.
- Use explorer APIs as auxiliary read paths.
- Implement retries/timeouts and stale-data detection on third-party APIs.
- Log data source provenance for support/debug workflows.
