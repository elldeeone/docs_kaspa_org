## Overview

This guide is written for exchange engineers integrating Kaspa (KAS) into a cryptocurrency exchange platform. Kaspa is a UTXO-based, proof-of-work cryptocurrency with a BlockDAG structure and 10 blocks per second throughput. The integration requires running a Kaspa node, generating deposit addresses, detecting incoming deposits, and processing withdrawals.

## Running a Node

Exchanges should run their own Kaspa full node (`kaspad`) rather than relying on public infrastructure. For exchange integration, start the node with the **UTXO index** enabled:

```bash
kaspad --utxoindex
```

The `--utxoindex` flag builds an index of all UTXOs by address, which is required for the `getUtxosByAddresses` and `notifyUtxosChanged` RPC methods. Without this flag, the node cannot efficiently look up UTXOs for specific addresses.

<Callout type="warn">
The UTXO index increases disk usage and memory consumption. Ensure your node has adequate resources — at least 8 GB of RAM and 100 GB of SSD storage is recommended for exchange nodes.
</Callout>

## KAS Denominations

Kaspa's base unit is the **sompi**. One KAS equals 100,000,000 sompi (10^8), analogous to Bitcoin's satoshi. All RPC values and internal calculations use sompi. When displaying amounts to users, divide by 10^8 to convert to KAS.

## Address Generation

Exchanges should generate a unique deposit address for each user. Use HD derivation (BIP-44 path `m/44'/111111'/account'/0/index`) to derive addresses deterministically from a master seed. This allows you to:

- Generate new addresses without storing each private key individually.
- Recover all addresses from the seed phrase in case of disaster.
- Use separate accounts for hot wallet and cold storage.

See the [HD Derivation](/docs/wallets/hd-derivation) page for implementation details.

<Callout type="info">
Kaspa addresses use the `kaspa:` prefix with a Bech32-encoded payload. Validate the prefix and checksum when accepting user-submitted withdrawal addresses.
</Callout>

## Deposit Detection

The recommended approach for detecting deposits is subscribing to UTXO change notifications:

1. **Register addresses**: Call the `notifyUtxosChanged` RPC method with your list of deposit addresses.
2. **Receive notifications**: When a transaction involving any registered address is confirmed, the node sends a notification containing the added UTXOs (deposits) and removed UTXOs (spends).
3. **Credit the user**: When you receive a notification of a new UTXO on a user's deposit address, credit their internal balance.

### Confirmation Depth

Kaspa's DAG structure provides fast confirmations, but exchanges should wait for sufficient confirmation depth before crediting deposits:

| Transaction value | Recommended depth (blue score) | Approximate time |
|---|---|---|
| Small (< 1,000 KAS) | 100 | ~10 seconds |
| Medium (1,000–100,000 KAS) | 1,000 | ~100 seconds |
| Large (> 100,000 KAS) | 10,000 | ~17 minutes |
| Very large / critical | 432,000 | ~12 hours (finality) |

The confirmation depth is measured in **blue score** — the number of blue blocks added to the selected parent chain since the transaction was included. A depth of 432,000 represents Kaspa's finality threshold, after which reorgs are rejected by the protocol.

## Withdrawal Processing

To process a withdrawal:

1. **Construct the transaction**: Create a transaction with the user's withdrawal address as the output. Select UTXOs from the hot wallet to fund the transaction.
2. **Calculate the fee**: Fees are based on transaction mass. The SDK computes this automatically.
3. **Sign the transaction**: Sign with the hot wallet's private keys.
4. **Submit**: Call `submitTransaction` via wRPC to broadcast the signed transaction.
5. **Monitor**: Track the transaction's confirmation depth before marking the withdrawal as complete.

## UTXO Consolidation

Exchange hot wallets accumulate many UTXOs from user deposits. While there is no hard protocol limit on the number of inputs, the per-transaction mass limit means that in practice a standard transaction can include roughly **84 inputs** (with typical P2PK script sizes). A wallet with thousands of small UTXOs may need multiple transactions to send a large amount.

Regularly consolidate UTXOs during low-activity periods:

1. Select a batch of small UTXOs (roughly 84 per transaction, depending on script sizes).
2. Send them to a single address controlled by the hot wallet.
3. Repeat until the UTXO set is manageable.

<Callout>
UTXO consolidation is essential for exchange operations. Without regular consolidation, large withdrawals may fail or require complex multi-transaction chains.
</Callout>

## Handling Reorgs

Kaspa's DAG structure makes deep reorgs extremely unlikely, but shallow reorgs can occur. To handle them safely:

- **Monitor the virtual chain**: Use `getVirtualChainFromBlock` to detect changes in the selected parent chain.
- **Track confirmation depth**: Do not credit deposits until they reach sufficient depth.
- **Use the UTXO notification system**: The `notifyUtxosChanged` subscription handles reorgs transparently — removed UTXOs in the notification indicate a reorg has occurred.

## Fee Management

- **Minimum fees**: Kaspa has very low transaction fees (typically fractions of a KAS). Fees are based on transaction mass.
- **Priority fees**: During periods of high network activity, add a priority fee to ensure faster inclusion.
- **Fee estimation**: Query the node for the current fee rate, or compute the mass-based fee using the SDK.

## Security Considerations

- **Cold storage**: Keep the majority of exchange reserves in cold storage with keys that never touch an internet-connected machine.
- **Hot wallet limits**: Set maximum balances for hot wallets. Replenish from cold storage as needed.
- **Multi-sig**: Use the CLI wallet's multi-sig feature for cold storage, requiring multiple key holders to authorize withdrawals.
- **Address validation**: Always validate the `kaspa:` prefix and Bech32 checksum on withdrawal addresses.
- **Rate limiting**: Implement withdrawal rate limits and manual review for large amounts.

## Community Indexers

For exchanges that need historical transaction queries or advanced filtering beyond what the node's built-in RPC provides, [simply-kaspa-indexer](https://github.com/supertypo/simply-kaspa-indexer) is a standalone indexer that connects to a Kaspa node and indexes blocks and transactions into a database. This can simplify deposit reconciliation and transaction history queries at scale.
