Kaspa nodes expose a rich RPC interface that allows applications to query blockchain state, submit transactions, and subscribe to real-time events. The primary RPC implementation is provided by [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa), the Rust-based Kaspa node.

## Protocol Overview

Kaspa supports two RPC transports:

- **wRPC (WebSocket RPC)** — The primary and recommended protocol. It supports full-duplex communication, making it ideal for subscriptions and real-time notifications.
- **gRPC** — A binary protocol built on Protocol Buffers, suitable for high-performance server-to-server communication. See the [gRPC Interface](/docs/developer-guide/grpc) page for details.

<Callout type="info">
wRPC is the preferred protocol for most applications. It works natively in browsers via WebSockets and supports all RPC methods including subscriptions.
</Callout>

## Connection Details

| Network | Default wRPC Port | Default gRPC Port |
|---------|-------------------|-------------------|
| Mainnet | 16110 | 16111 |
| Testnet-10 | 16210 | 16211 |
| Testnet-11 | 16310 | 16311 |
| Simnet | 16510 | 16511 |

To connect to a local node via wRPC:

```
ws://127.0.0.1:16110
```

Public nodes are also available for development. The Kaspa WASM SDK provides built-in resolver functionality to discover public nodes automatically.

## Key RPC Methods

### getBlockDagInfo

Returns general information about the current state of the block DAG.

**Request:**

```json
{
  "method": "getBlockDagInfo",
  "params": {}
}
```

### submitTransaction

Submits a signed transaction to the network for propagation and inclusion in a block.

**Request:**

```json
{
  "method": "submitTransaction",
  "params": {
    "transaction": {
      "version": 0,
      "inputs": [
        {
          "previousOutpoint": {
            "transactionId": "abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890",
            "index": 0
          },
          "signatureScript": "41...",
          "sequence": 0,
          "sigOpCount": 1
        }
      ],
      "outputs": [
        {
          "amount": 100000000,
          "scriptPublicKey": {
            "version": 0,
            "scriptPublicKey": "2011a7215f668e921013eb7aac9b7e64b9ec6e757c1b648a89f32cb449a084850aac"
          }
        }
      ],
      "lockTime": 0,
      "subnetworkId": "0000000000000000000000000000000000000000"
    },
    "allowOrphan": false
  }
}
```

**Response:**

```json
{
  "transactionId": "1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef"
}
```

<Callout type="warn">
Transactions must be properly signed before submission. An invalid signature will cause the node to reject the transaction. Use the WASM SDK or a signing library to construct and sign transactions correctly.
</Callout>

### getUtxosByAddresses

Returns all unspent transaction outputs (UTXOs) for the given addresses.

**Request:**

```json
{
  "method": "getUtxosByAddresses",
  "params": {
    "addresses": [
      "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev"
    ]
  }
}
```

**Response:**

```json
{
  "entries": [
    {
      "address": "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev",
      "outpoint": {
        "transactionId": "abcdef1234567890abcdef1234567890abcdef1234567890abcdef1234567890",
        "index": 0
      },
      "utxoEntry": {
        "amount": 500000000000,
        "scriptPublicKey": {
          "version": 0,
          "scriptPublicKey": "..."
        },
        "blockDaaScore": 52345000,
        "isCoinbase": false
      }
    }
  ]
}
```

### getBalanceByAddress

Returns the total balance for a specific address. This is a convenience method that sums all UTXOs for the address.

**Request:**

```json
{
  "method": "getBalanceByAddress",
  "params": {
    "address": "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev"
  }
}
```

**Response:**

```json
{
  "balance": 500000000000
}
```

<Callout type="info">
Balances are returned in **sompi** (the smallest unit of KAS). 1 KAS = 100,000,000 sompi (10^8). To convert to KAS, divide by 100,000,000.
</Callout>

### getVirtualSelectedParentBlueScore

Returns the blue score of the current virtual selected parent. The blue score is a monotonically increasing value that serves as an analog to block height in a DAG structure.

**Request:**

```json
{
  "method": "getVirtualSelectedParentBlueScore",
  "params": {}
}
```

**Response:**

```json
{
  "blueScore": 48234567
}
```

### notifyBlockAdded

Subscribes to notifications whenever a new block is added to the DAG. This is a subscription method — after calling it, the node will push notifications to your connection.

**Request:**

```json
{
  "method": "notifyBlockAdded",
  "params": {}
}
```

**Notification (pushed by node):**

```json
{
  "method": "blockAddedNotification",
  "params": {
    "block": {
      "header": {
        "version": 1,
        "timestamp": 1700000001000,
        "daaScore": 52345679,
        "blueScore": 48234568,
        "blueWork": "...",
        "parents": [{ "parentHashes": ["..."] }]
      },
      "transactions": ["..."],
      "verboseData": {
        "hash": "...",
        "isChainBlock": true
      }
    }
  }
}
```

## Additional RPC Methods

Beyond the key methods above, the Kaspa RPC interface provides many additional methods:

| Method | Description |
|--------|-------------|
| `getBlockTemplate` | Get a block template for mining |
| `getInfo` | Get general node information |
| `getPeerAddresses` | List connected peer addresses |
| `getConnectedPeerInfo` | Get detailed info on connected peers |
| `getMempoolEntries` | List transactions in the mempool |
| `getMempoolEntry` | Get a specific mempool transaction |
| `getSubnetwork` | Get subnetwork information |
| `estimateNetworkHashesPerSecond` | Estimate the current network hash rate |
| `getCoinSupply` | Get the current circulating coin supply |
| `notifyVirtualSelectedParentBlueScoreChanged` | Subscribe to blue score changes |
| `notifyUtxosChanged` | Subscribe to UTXO changes for specific addresses |
| `notifyVirtualDaaScoreChanged` | Subscribe to DAA score changes |
| `notifyVirtualSelectedParentChainChanged` | Subscribe to chain changes |

## Subscription Model

Kaspa's wRPC interface supports a publish-subscribe model for real-time notifications. This is critical for applications that need to react to blockchain events as they happen.

Common subscription patterns:

1. **Watch for new blocks** — Use `notifyBlockAdded` to get notified whenever a new block enters the DAG.
2. **Watch for balance changes** — Use `notifyUtxosChanged` with specific addresses to detect incoming and outgoing transactions.
3. **Track confirmation depth** — Use `notifyVirtualSelectedParentBlueScoreChanged` to monitor the blue score and calculate confirmation depth for pending transactions.

```typescript
// Example: Subscribing to UTXO changes using wRPC
const client = new RpcClient({ url: "ws://127.0.0.1:16110" });
await client.connect();

// Subscribe to UTXO changes for an address
await client.subscribeUtxosChanged([
  "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev"
]);

client.addEventListener("utxos-changed", (event) => {
  const { added, removed } = event.data;
  console.log("New UTXOs:", added);
  console.log("Spent UTXOs:", removed);
});
```

## Error Handling

RPC calls may return errors in the following format:

```json
{
  "error": {
    "message": "Transaction is not valid: missing input UTXOs"
  }
}
```

Common error scenarios include:

- **Invalid transaction** — Malformed transaction or invalid signatures
- **UTXO not found** — Attempting to spend a UTXO that does not exist or has already been spent
- **Node syncing** — The node is still syncing and cannot serve the request
- **Rate limiting** — Too many requests in a short period

<Callout type="warn">
Always implement proper error handling and retry logic in your applications. Kaspa's fast block times (1 block per second) mean the UTXO set changes rapidly, and race conditions are possible when constructing transactions.
</Callout>

## Rate Limits and Best Practices

- **Use subscriptions** instead of polling whenever possible. Kaspa produces blocks every second, so polling is inefficient.
- **Batch UTXO queries** using `getUtxosByAddresses` with multiple addresses rather than making individual calls.
- **Cache block data** locally when iterating over the DAG to reduce RPC load.
- **Use the WASM SDK** for client-side applications — it handles connection management, serialization, and reconnection automatically. See the [WASM SDK](/docs/developer-guide/wasm-sdk) page.
- **Run your own node** for production applications to avoid dependency on public infrastructure and ensure reliable access.
