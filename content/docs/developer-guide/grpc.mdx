Kaspa nodes expose a gRPC interface alongside the primary wRPC (WebSocket RPC) interface. gRPC is a high-performance, language-neutral RPC framework built on HTTP/2 and Protocol Buffers. It is particularly well-suited for server-to-server communication, microservice architectures, and scenarios where strong typing and code generation are desired.

## When to Use gRPC

| Use Case | Recommended Protocol |
|----------|---------------------|
| Browser applications | wRPC (WebSocket) |
| Node.js applications | wRPC or gRPC |
| Rust applications | gRPC (native support) |
| High-frequency data pipelines | gRPC |
| Mobile applications | wRPC |
| Exchange backends | gRPC |

<Callout type="info">
For most application developers, the [wRPC interface](/docs/developer-guide/rpc-api) or the [WASM SDK](/docs/developer-guide/wasm-sdk) will be simpler to work with. gRPC is best when you need maximum performance or are building infrastructure-level tooling.
</Callout>

## Protobuf Definitions

The Kaspa gRPC interface is defined using Protocol Buffer (protobuf) files located in the rusty-kaspa repository. These `.proto` files define all message types and RPC service methods.

### Source Location

The protobuf definitions are located in the rusty-kaspa repository:

```
rusty-kaspa/
└── rpc/
    └── grpc/
        └── proto/
            ├── kaspadrpc.proto
            ├── messages.proto
            └── p2p.proto
```

The primary file is `messages.proto`, which defines the RPC request and response message types. The `kaspadrpc.proto` file defines the gRPC service with all available RPC methods.

### Key Message Types

The protobuf definitions include messages for all RPC operations. Here are some of the most commonly used:

```protobuf
// Request to get the current block DAG info
message GetBlockDagInfoRequestMessage {
}

message GetBlockDagInfoResponseMessage {
  string networkName = 1;
  uint64 blockCount = 2;
  uint64 headerCount = 3;
  repeated string tipHashes = 4;
  double difficulty = 5;
  int64 pastMedianTime = 6;
  repeated string virtualParentHashes = 7;
  string pruningPointHash = 8;
  uint64 virtualDaaScore = 9;
  RPCError error = 1000;
}

// Request to get UTXOs for addresses
message GetUtxosByAddressesRequestMessage {
  repeated string addresses = 1;
}

message GetUtxosByAddressesResponseMessage {
  repeated UtxosByAddressesEntry entries = 1;
  RPCError error = 1000;
}

// Submit a transaction
message SubmitTransactionRequestMessage {
  RpcTransaction transaction = 1;
  bool allowOrphan = 2;
}

message SubmitTransactionResponseMessage {
  string transactionId = 1;
  RPCError error = 1000;
}
```

## Generating Client Stubs

gRPC uses code generation to create client and server stubs from the protobuf definitions. Here is how to generate stubs for common languages.

### Rust

Rust is the native language of rusty-kaspa, and gRPC support is built-in via the `tonic` crate. The rusty-kaspa project includes build scripts that generate Rust code from the proto files automatically.

To use the Kaspa gRPC client in your Rust project, add the relevant crates from the rusty-kaspa workspace:

```toml
[dependencies]
kaspa-grpc-client = { git = "https://github.com/kaspanet/rusty-kaspa.git", branch = "master" }
kaspa-rpc-core = { git = "https://github.com/kaspanet/rusty-kaspa.git", branch = "master" }
tokio = { version = "1", features = ["full"] }
```

### Go

```bash
# Install the protobuf compiler and Go plugins
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# Generate Go code from proto files
protoc --go_out=. --go-grpc_out=. \
  -I ./proto \
  ./proto/messages.proto \
  ./proto/kaspadrpc.proto
```

### Python

```bash
# Install gRPC tools
pip install grpcio grpcio-tools

# Generate Python code from proto files
python -m grpc_tools.protoc \
  -I ./proto \
  --python_out=./generated \
  --grpc_python_out=./generated \
  ./proto/messages.proto \
  ./proto/kaspadrpc.proto
```

## Example Usage in Rust

The following example demonstrates connecting to a Kaspa node via gRPC, querying DAG information, and subscribing to block notifications.

### Basic Connection and Query

```rust
use kaspa_grpc_client::GrpcClient;
use kaspa_rpc_core::api::rpc::RpcApi;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Connect to a local Kaspa node via gRPC
    let client = GrpcClient::connect(
        "grpc://127.0.0.1:16111".to_string(),
        true,   // enable connection retries
        None,   // no TLS
        false,  // not verbose
        None,   // no subscription context
    )
    .await?;

    // Query the current block DAG info
    let dag_info = client.get_block_dag_info().await?;
    println!("Network: {}", dag_info.network);
    println!("Block count: {}", dag_info.block_count);
    println!("DAA score: {}", dag_info.virtual_daa_score);
    println!("Tip hashes: {:?}", dag_info.tip_hashes);

    // Get the current blue score
    let blue_score = client
        .get_virtual_selected_parent_blue_score()
        .await?;
    println!("Current blue score: {}", blue_score.blue_score);

    // Query balance for an address
    let balance = client
        .get_balance_by_address(
            "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev"
                .try_into()?,
        )
        .await?;
    println!("Balance: {} sompi ({} KAS)", balance, balance as f64 / 1e8);

    // Get UTXOs for an address
    let utxos = client
        .get_utxos_by_addresses(vec![
            "kaspa:qr35ennsep3hxfe7lnz5ee7j5jgmkjswsn35ennsep3hxfe7lkaspadev"
                .try_into()?,
        ])
        .await?;
    println!("UTXO count: {}", utxos.len());
    for entry in &utxos {
        println!(
            "  UTXO: {} sompi (DAA score: {})",
            entry.utxo_entry.amount, entry.utxo_entry.block_daa_score
        );
    }

    client.disconnect().await?;
    Ok(())
}
```

### Subscribing to Block Notifications

```rust
use kaspa_grpc_client::GrpcClient;
use kaspa_rpc_core::{api::rpc::RpcApi, notify::events::EventType};
use std::sync::Arc;
use tokio::sync::mpsc;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = GrpcClient::connect(
        "grpc://127.0.0.1:16111".to_string(),
        true,
        None,
        false,
        None,
    )
    .await?;

    // Start listening for block-added notifications
    client.start_notify(
        Default::default(),
        kaspa_rpc_core::Notification::BlockAdded(Default::default()),
    ).await?;

    println!("Listening for new blocks...");

    // Process incoming notifications
    // In production, use proper notification listener channels
    // provided by the GrpcClient
    loop {
        tokio::time::sleep(tokio::time::Duration::from_secs(1)).await;
        // Notifications are delivered via the client's notification channel
        // Process them according to your application's needs
    }
}
```

    .await?;

    // Build and sign a transaction (simplified example)
    // In practice, use kaspa-consensus-core and kaspa-wallet-core
    // for proper transaction construction and signing
    let tx: RpcTransaction = /* construct your signed transaction */;

    // Submit the transaction

## Streaming RPCs

gRPC supports server-side streaming, which Kaspa uses for subscription-based notifications. When you subscribe to events (such as block additions or UTXO changes), the node opens a server-side stream and pushes notifications as they occur.

Key streaming subscriptions:

- **NotifyBlockAdded** — Stream of new blocks added to the DAG
- **NotifyUtxosChanged** — Stream of UTXO changes for watched addresses
- **NotifyVirtualSelectedParentBlueScoreChanged** — Stream of blue score updates
- **NotifyVirtualDaaScoreChanged** — Stream of DAA score changes
- **NotifyVirtualSelectedParentChainChanged** — Stream of virtual chain changes

## Error Handling

gRPC uses standard status codes for error reporting:

| Status Code | Meaning |
|-------------|---------|
| `OK` | Request succeeded |
| `INVALID_ARGUMENT` | Malformed request (e.g., invalid hash format) |
| `NOT_FOUND` | Requested resource not found (e.g., unknown block hash) |
| `UNAVAILABLE` | Node is not ready (e.g., still syncing) |
| `INTERNAL` | Internal node error |

Additionally, each Kaspa RPC response includes an optional `RPCError` field that provides Kaspa-specific error details.

## Performance Considerations

- **Connection pooling** — Reuse gRPC connections rather than creating new ones for each request. gRPC connections multiplex multiple requests over a single HTTP/2 connection.
- **Streaming over polling** — Use streaming subscriptions instead of repeated polling. Kaspa produces blocks every second, making polling expensive.
- **Message size** — Be aware that responses for methods like `getBlock` with `includeTransactions=true` can be large for blocks with many transactions.
- **Keep-alive** — Configure gRPC keep-alive settings to maintain long-lived connections, especially important for subscription streams.

```rust
// Example: Configuring gRPC client with keep-alive
// The GrpcClient in rusty-kaspa handles this internally,
// but if building a custom client, configure your channel:
use tonic::transport::Channel;
use std::time::Duration;

let channel = Channel::from_static("http://127.0.0.1:16111")
    .keep_alive_timeout(Duration::from_secs(20))
    .keep_alive_while_idle(true)
    .connect()
    .await?;
```
