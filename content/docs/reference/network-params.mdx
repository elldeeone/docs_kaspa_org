# Network Parameters

This page provides a comprehensive reference of all configurable and fixed parameters that define the Kaspa network's behavior. Parameters are listed for mainnet post-Crescendo (10 BPS) unless otherwise noted.

<Callout type="info">
Values on this page are derived directly from the [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) reference implementation. Where a parameter is computed from constants (for example, `finality_depth = BPS * FINALITY_DURATION`), the formula is shown alongside the result.
</Callout>

---

## Block Timing and Production

| Parameter | Value | Description |
|-----------|-------|-------------|
| Block rate | **10 BPS** (blocks per second) | Target rate of block production across the network |
| Block time target | **100 ms** | Target interval between consecutive blocks (`1000 / BPS`) |
| Timestamp deviation tolerance | **132 seconds** | Maximum allowed deviation of a block's timestamp from the network's past median time |
| Past median time sample interval | **10 seconds** | Desired interval between sampled blocks for the median time window |
| Past median time sampled window size | **27 blocks** | Number of sampled blocks used to calculate the past median time |
| Past median time sample rate | **100 blocks** | Sample 1 in every 100 blocks for the median time window (`BPS * 10`) |

<Callout type="info">
Kaspa's 10 BPS rate makes it one of the fastest proof-of-work blockchains. At this rate, the network produces approximately 864,000 blocks per day. The high block rate is enabled by the GHOSTDAG protocol, which resolves conflicts between concurrent blocks without orphaning them.
</Callout>

## GHOSTDAG and Block Structure

| Parameter | Value | Description |
|-----------|-------|-------------|
| GHOSTDAG K | **124** | Upper bound on the expected anticone size for honest blocks. Computed such that the probability of a larger anticone is less than 1% given a 5-second network delay bound at 10 BPS |
| Network delay bound (D) | **5 seconds** | Estimated upper bound on network propagation delay |
| Anticone probability (delta) | **0.01** (1%) | Target upper bound on the probability of anticones larger than K |
| Maximum block parents | **16** | Maximum number of direct (level-0) parent blocks. Clamped to `min(max(K/2, 10), 16)` to balance DAG coverage with processing performance |
| Mergeset size limit | **248** | Maximum number of blocks in a block's merge set. Computed as `max(min(K * 2, 512), 180)` |
| Block version | **1** | Current block header version |
| Maximum block level | **225** | Maximum multi-level header level for the block DAG |

<Callout type="info">
The GHOSTDAG K parameter is derived from a Poisson analysis: given `x = 2 * D * BPS = 2 * 5 * 10 = 100`, K = 124 is the smallest value such that the cumulative Poisson probability with mean 100 exceeds 0.99. This ensures that honest blocks are overwhelmingly likely to have anticones smaller than K.
</Callout>

## Block Mass and Transaction Limits

| Parameter | Value | Description |
|-----------|-------|-------------|
| Maximum block mass | **500,000 grams** | Maximum total transaction mass allowed in a single block |
| Maximum transaction mass | **100,000 grams** | Maximum mass for a single standard transaction |
| Mass per transaction byte | **1** | Mass contribution per byte of serialized transaction data (compute mass) |
| Mass per script public key byte | **10** | Mass contribution per byte of script public key data (compute mass) |
| Mass per sig op | **1,000** | Mass contribution per signature operation (compute mass) |
| Transient byte-to-mass factor | **4** | Mass multiplier per byte for transient storage mass (KIP-0013), limiting block body size to ~125 KB |
| Storage mass parameter (C) | **10^12** (1,000,000,000,000) | Parameter for scaling inverse KAS value to mass units (KIP-0009). Equal to `SOMPI_PER_KASPA * 10,000` |

### Mass Types

Kaspa uses a multi-dimensional mass system where the effective mass of a transaction is the maximum across three independently computed mass values:

| Mass Type | Description |
|-----------|-------------|
| **Compute mass** | Based on serialized size, script public key bytes, and signature operations. Limits computational cost of block validation |
| **Transient mass** | Based on serialized size multiplied by the transient factor (4x). Limits the byte size of data propagated per block to ~125 KB |
| **Storage mass** | Context-dependent mass based on UTXO creation vs. consumption (KIP-0009). Penalizes UTXO set bloat by charging more for creating small or numerous outputs |

<Callout type="warn">
The effective mass of a transaction is `max(compute_mass, transient_mass, storage_mass)`. A transaction that is lightweight in compute terms can still have high mass if it fragments UTXOs into many small outputs.
</Callout>

### Transaction Constraints

| Parameter | Value | Description |
|-----------|-------|-------------|
| Transaction version | **0** | Current supported transaction version |
| Maximum inputs per transaction | **1,000** | Hard protocol limit on input count (practical limit is lower due to mass) |
| Maximum outputs per transaction | **1,000** | Hard protocol limit on output count (practical limit is lower due to mass) |
| Maximum signature script length | **10,000 bytes** | Maximum length of an input's signature script |
| Maximum script public key length | **10,000 bytes** | Maximum length of an output's script public key |
| Subnetwork ID length | **20 bytes** | Size of the subnetwork identifier field |
| Maximum sequence number | **2^64 - 1** | Maximum value for the transaction input sequence field |

## Difficulty Adjustment Algorithm (DAA)

| Parameter | Value | Description |
|-----------|-------|-------------|
| DAA window duration | **2,641 seconds** (~44 minutes) | Time span over which the DAA samples blocks |
| DAA sample interval | **4 seconds** | Desired interval between sampled blocks for difficulty calculation |
| DAA sampled window size | **661 blocks** | Number of sampled blocks in the DAA window (`ceil(2641 / 4)`) |
| DAA sample rate | **40 blocks** | Sample 1 in every 40 blocks (`BPS * 4`) |
| Minimum difficulty window size | **150** | Minimum number of samples before DAA activates. At 4-second intervals, this represents ~10 minutes of fixed difficulty at startup |
| DAA target time per block | **100 ms** | Target block interval the DAA adjusts toward |
| Maximum difficulty target | **2^255 - 1** | Highest allowed proof-of-work difficulty target (lowest difficulty) |

The DAA continuously adjusts the mining difficulty to maintain the target block rate. It samples the timestamps and difficulty of blocks within the DAA window and computes the new target based on the observed rate versus the expected rate.

<Callout type="info">
The DAA score serves as Kaspa's logical clock. It is analogous to Bitcoin's block height but increments along the selected parent chain of the DAG. Many protocol rules (lock times, coinbase maturity, finality) reference DAA score rather than wall-clock time.
</Callout>

## Consensus Depths and Finality

| Parameter | Value | Formula | Wall-clock equivalent |
|-----------|-------|---------|----------------------|
| Coinbase maturity | **1,000** DAA score | `BPS * 100s` | ~100 seconds |
| Merge depth | **36,000** blue score | `BPS * 3,600s` | ~1 hour |
| Finality depth | **432,000** blue score | `BPS * 43,200s` | ~12 hours |
| Pruning depth | **1,080,000** blue score | `max(lower_bound, BPS * 108,000s)` | ~30 hours |
| Pruning proof M | **1,000** | Pruning proof security parameter | -- |

<Callout type="warn">
The finality and pruning depths listed here reflect the Crescendo (10 BPS) parameters derived from time-based durations in the rusty-kaspa source code. The finality duration is 43,200 seconds (12 hours), and the pruning duration is 108,000 seconds (30 hours). These are multiplied by BPS to produce the depth in blue score units.
</Callout>

### Finality

Kaspa's finality window is set to a duration of **43,200 seconds (12 hours)**, which at 10 BPS produces a finality depth of **432,000 blue score**. Once a block's blue score is more than 432,000 behind the virtual selected parent's blue score, it is considered final:

- The block cannot be removed from the selected chain by any reorganization.
- All transactions accepted in that block are irreversibly confirmed.
- The finality point serves as a checkpoint that new nodes can trust during initial sync.

<Callout type="info">
While practical irreversibility is achieved much sooner (within seconds for typical transactions), the finality depth provides a mathematically guaranteed security bound against all possible attacks.
</Callout>

### Pruning

Pruning allows nodes to discard old block body data while retaining headers. This keeps storage requirements bounded:

- **Pruned nodes** store only block headers and UTXO state beyond the pruning depth.
- **Archival nodes** retain complete block data including all transaction bodies.
- The pruning point advances as the chain grows, keeping the required data window constant.
- The pruning depth has a lower bound computed as `finality_depth + 2 * merge_depth + 4 * mergeset_size_limit * K + 2 * K + 2`, ensuring that pruning never occurs before finalization.

## Monetary Policy and Emission

| Parameter | Value | Description |
|-----------|-------|-------------|
| Maximum sompi | **29 billion KAS** (2,900,000,000,000,000,000 sompi) | Hard cap encoded as `MAX_SOMPI` in the protocol |
| Base unit | **sompi** | 1 KAS = 100,000,000 sompi (10^8) |
| Pre-deflationary base subsidy | **50 KAS** per block at 10 BPS | `50,000,000,000 / BPS` sompi per block |
| Emission schedule | **Chromatic** | Named after the 12 semitones in a musical chromatic scale |
| Halving interval | **~1 year** (by chromatic phases) | Reward halves approximately once per year |
| Monthly reduction factor | **(1/2)^(1/12)** ~= 0.9439 | Reward reduces by this factor each month |
| Pre-mine | **None** | No tokens were pre-mined or allocated before launch |
| Deflationary phase DAA score | **15,519,600** | DAA score at which mainnet switched from fixed to deflationary subsidy (at original 1 BPS) |

### Chromatic Emission Schedule

Kaspa's emission schedule is called **chromatic** because it divides each halving cycle into 12 equal phases (like the 12 semitones in a musical octave). Instead of an abrupt 50% halving, the block reward decreases smoothly:

| Phase | Reduction from start of cycle | Approximate reward factor |
|-------|-------------------------------|--------------------------|
| Month 1 | (1/2)^(1/12) | 0.9439x |
| Month 2 | (1/2)^(2/12) | 0.8909x |
| Month 3 | (1/2)^(3/12) | 0.8409x |
| Month 4 | (1/2)^(4/12) | 0.7937x |
| Month 5 | (1/2)^(5/12) | 0.7492x |
| Month 6 | (1/2)^(6/12) | 0.7071x |
| Month 7 | (1/2)^(7/12) | 0.6674x |
| Month 8 | (1/2)^(8/12) | 0.6300x |
| Month 9 | (1/2)^(9/12) | 0.5946x |
| Month 10 | (1/2)^(10/12) | 0.5612x |
| Month 11 | (1/2)^(11/12) | 0.5297x |
| Month 12 | (1/2)^(12/12) | 0.5000x |

After 12 months, the reward is exactly half of where it started, and a new cycle begins. This produces a smooth, predictable decline in emission rather than the sharp halving events seen in Bitcoin.

<Callout type="info">
The chromatic schedule means miners never experience a sudden 50% revenue drop. Instead, the reward decreases by approximately 5.6% each month, providing a smoother economic transition.
</Callout>

## Transaction Fee Parameters

| Parameter | Value | Description |
|-----------|-------|-------------|
| Minimum relay transaction fee | **1,000 sompi** per gram of mass | Minimum fee rate for a transaction to be relayed by nodes |
| Minimum fee calculation | `(mass * 1000) / 1000` | Fee is computed per-gram, with a floor of the base relay fee |
| Lock time threshold | **500,000,000,000** | Values below this threshold are interpreted as DAA scores; values at or above are interpreted as Unix timestamps (milliseconds) |

<Callout type="info">
The fee market in Kaspa is mass-based rather than byte-based. This means fees account for computational cost (signature verification), transient bandwidth, and persistent UTXO storage impact -- not just raw transaction size.
</Callout>

## Mining Parameters

| Parameter | Value | Description |
|-----------|-------|-------------|
| Mining algorithm | **kHeavyHash** | Optical-mining-friendly proof-of-work algorithm |
| Hash output | 256 bits | Output size of the kHeavyHash function |
| Matrix size | 64x64 | Dimensions of the heavy hash matrix |
| Nonce size | 64 bits | Size of the nonce field in the block header |

### kHeavyHash Algorithm

The kHeavyHash proof-of-work algorithm consists of:

1. **Pre-hash**: Compute a domain-separated cSHAKE256 hash of the block header (domain: "ProofOfWorkHash").
2. **Matrix multiplication**: Multiply the pre-hash result by a 64x64 matrix (derived from the DAG state) in GF(2^4).
3. **XOR**: XOR the matrix multiplication result with the original pre-hash.
4. **Post-hash**: Compute a domain-separated cSHAKE256 hash of the combined result (domain: "HeavyHash").

This construction was originally designed with optical computing hardware in mind. In practice, Kaspa is now predominantly mined with ASICs (e.g., Bitmain KS series).

## Crescendo Hardfork

The Crescendo hardfork transitioned mainnet from 1 BPS to 10 BPS. The following parameters changed at activation:

| Parameter | Pre-Crescendo (1 BPS) | Post-Crescendo (10 BPS) |
|-----------|----------------------|------------------------|
| Target time per block | 1,000 ms | 100 ms |
| GHOSTDAG K | 18 | 124 |
| Max block parents | 10 | 16 |
| Mergeset size limit | 180 | 248 |
| Merge depth | 3,600 | 36,000 |
| Finality depth | 43,200 | 432,000 |
| Pruning depth | 108,000 | 1,080,000 |
| Coinbase maturity | 100 | 1,000 |
| DAA sample rate | 4 blocks | 40 blocks |

| Network | Activation DAA Score |
|---------|---------------------|
| Mainnet | 110,165,000 (~May 5, 2025) |
| Testnet-10 | 88,657,000 (~March 6, 2025) |
| Simnet | Always active (since inception) |
