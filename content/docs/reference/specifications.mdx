# Protocol Specifications

This document provides the formal specifications for Kaspa's core data structures and cryptographic primitives. These specifications define how blocks, transactions, and scripts are constructed and validated across the network.

---

## Block Header Format

Every block in Kaspa's BlockDAG contains a header with the following fields. Unlike linear blockchains, Kaspa block headers reference **multiple parent blocks**, reflecting the DAG structure.

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `version` | `uint16` | 2 bytes | Block header version, indicating the ruleset for validation |
| `parents` | `Hash[][]` | Variable | Array of parent hash arrays, grouped by level. Level 0 contains direct parents; higher levels contain selected ancestors for merge set optimization |
| `hashMerkleRoot` | `Hash` | 32 bytes | Merkle root of all transaction hashes in the block |
| `acceptedIdMerkleRoot` | `Hash` | 32 bytes | Merkle root of the accepted transaction IDs from the block's merge set |
| `utxoCommitment` | `Hash` | 32 bytes | Commitment to the UTXO set state after applying this block |
| `timestamp` | `uint64` | 8 bytes | Block creation time in milliseconds since Unix epoch |
| `bits` | `uint32` | 4 bytes | Compact representation of the target difficulty |
| `nonce` | `uint64` | 8 bytes | Nonce used for proof-of-work mining |
| `daaScore` | `uint64` | 8 bytes | Difficulty Adjustment Algorithm score, monotonically increasing count of blocks in the DAG's selected chain |
| `blueWork` | `BigInt` | Variable | Cumulative proof-of-work on the blue chain from genesis to this block |
| `blueScore` | `uint64` | 8 bytes | Number of blue blocks in the selected chain from genesis to this block |
| `pruningPoint` | `Hash` | 32 bytes | Hash of the current pruning point block |

### Parent Blocks

The `parents` field is a two-dimensional array structured by **block level**. Each block has a level determined by the number of leading zeros beyond the required difficulty target in its hash:

- **Level 0**: Direct parent blocks in the DAG. A block references up to `maxBlockParents` current tips (16 on mainnet post-Crescendo).
- **Level N (N > 0)**: Contains the selected parent from the block's level-N merge set. Higher-level parents enable efficient SPV proof construction by providing skip-list-like pointers through the DAG.

<Callout type="info">
The multi-level parent structure is a key innovation enabling compact proofs of chain state. A block's level is probabilistic: approximately 1 in 2^N blocks will be level N or higher.
</Callout>

### Block Hash Computation

The block hash is computed from the canonical serialized header using Kaspa's domain-separated `BlockHash` hasher:

```
blockHash = BlockHash(serialized_header)
```

The serialization includes all header fields in canonical order. Kaspa uses domain separation for protocol hashers rather than a single undifferentiated hash call.

### Proof-of-Work

Kaspa uses the **kHeavyHash** algorithm for proof-of-work. The mining process requires finding a `nonce` such that:

```
kHeavyHash(serialized_header) < target
```

The `target` is derived from the `bits` field using the standard compact target representation. kHeavyHash applies `ProofOfWorkHash` cSHAKE, a matrix-generated heavy-mixing step, XOR with the pre-hash, and a final `HeavyHash` cSHAKE.

## Transaction Format

Kaspa transactions follow a UTXO model similar to Bitcoin but with several Kaspa-specific extensions.

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `version` | `uint16` | 2 bytes | Transaction version |
| `inputs` | `TxInput[]` | Variable | Array of transaction inputs |
| `outputs` | `TxOutput[]` | Variable | Array of transaction outputs |
| `lockTime` | `uint64` | 8 bytes | Earliest DAA score or time at which this transaction may be included in a block |
| `subnetworkId` | `SubnetworkId` | 20 bytes | Identifier of the subnetwork this transaction belongs to |
| `gas` | `uint64` | 8 bytes | Gas limit for subnetwork computation (0 for native transactions) |
| `payload` | `bytes` | Variable | Arbitrary payload data (used by coinbase and subnetwork transactions) |

### Transaction Inputs

Each input references a specific UTXO being spent:

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `previousOutpoint` | `Outpoint` | 36 bytes | Reference to the UTXO being spent (transaction ID + output index) |
| `signatureScript` | `bytes` | Variable | Script satisfying the spending conditions (typically a Schnorr signature + public key) |
| `sequence` | `uint64` | 8 bytes | Sequence number for relative lock-time and replacement signaling |
| `sigOpCount` | `uint8` | 1 byte | Number of signature operations in this input's script |

The `Outpoint` structure:

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `transactionId` | `Hash` | 32 bytes | Hash of the transaction containing the UTXO |
| `index` | `uint32` | 4 bytes | Index of the output within that transaction |

### Transaction Outputs

Each output defines a new UTXO:

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `value` | `uint64` | 8 bytes | Amount in sompi (1 KAS = 100,000,000 sompi) |
| `scriptPublicKey` | `ScriptPublicKey` | Variable | The locking script defining spending conditions |

The `ScriptPublicKey` structure:

| Field | Type | Size | Description |
|-------|------|------|-------------|
| `version` | `uint16` | 2 bytes | Script version for future upgradability |
| `script` | `bytes` | Variable | The serialized script bytecode |

### Subnetwork IDs

Kaspa supports subnetwork-specific transactions through the `subnetworkId` field:

| Subnetwork ID | Description |
|---------------|-------------|
| `0x00...00` (all zeros) | Native subnetwork (standard KAS transfers) |
| `0x01...00` | Coinbase subnetwork (block reward transactions) |
| Other | Reserved for future protocol extensions and non-native subnetworks |

### Transaction ID Computation

The transaction ID is computed by hashing the serialized transaction **without** the signature scripts:

```
txId = Blake2b(version || inputs_without_sig || outputs || lockTime || subnetworkId || gas || payload)
```

This ensures that transaction IDs remain stable regardless of signature malleability (similar to SegWit in Bitcoin).

<Callout type="info">
Kaspa's transaction ID computation excludes signature data by design, inherently solving transaction malleability without requiring a separate witness structure.
</Callout>

### Transaction Mass

Kaspa tracks transaction/resource usage with three mass dimensions:

| Component | Calculation |
|-----------|-------------|
| Compute mass | Based on the number of signature operations (`sigOpCount` across all inputs) |
| Transient mass | Based on serialized transaction size (bandwidth-oriented) |
| Storage mass | Contextual mass commitment related to UTXO-state impact |

Consensus does **not** assign protocol meaning to a single `max(...)` transaction mass value.  
`max(compute, transient, storage)` is used as a mempool/template-selection simplification, while block validation enforces limits per dimension.
([source](https://github.com/kaspanet/rusty-kaspa/blob/master/consensus/core/src/mass/mod.rs#L163-L166), [source](https://github.com/kaspanet/rusty-kaspa/blob/master/consensus/core/src/mass/mod.rs#L188-L191))

At block-validation time, totals are accumulated separately and each must stay within the block bound (`500,000`):

- total compute mass <= max block mass
- total transient mass <= max block mass
- total storage mass <= max block mass

([source](https://github.com/kaspanet/rusty-kaspa/blob/master/consensus/src/pipeline/body_processor/body_validation_in_isolation.rs#L63-L90))

## Script System

Kaspa's scripting language is based on Bitcoin's Script with modifications to suit the DAG environment and improved security posture.

### Supported Opcodes

Kaspa supports a subset of Bitcoin script opcodes. The following categories are available:

**Constants:**

| Opcode | Hex | Description |
|--------|-----|-------------|
| `OP_0` | `0x00` | Push empty byte array (false) |
| `OP_1` to `OP_16` | `0x51`-`0x60` | Push the number 1 through 16 |
| `OP_DATA_1` to `OP_DATA_75` | `0x01`-`0x4b` | Push next N bytes onto the stack |
| `OP_PUSHDATA1` | `0x4c` | Next byte is length, then push that many bytes |
| `OP_PUSHDATA2` | `0x4d` | Next 2 bytes are length, then push that many bytes |
| `OP_PUSHDATA4` | `0x4e` | Next 4 bytes are length, then push that many bytes |
| `OP_1NEGATE` | `0x4f` | Push -1 onto the stack |

**Flow Control:**

| Opcode | Hex | Description |
|--------|-----|-------------|
| `OP_IF` | `0x63` | Execute following block if top of stack is true |
| `OP_NOTIF` | `0x64` | Execute following block if top of stack is false |
| `OP_ELSE` | `0x67` | Execute alternative block |
| `OP_ENDIF` | `0x68` | End conditional block |
| `OP_RETURN` | `0x6a` | Mark transaction output as provably unspendable |

**Stack Operations:**

| Opcode | Hex | Description |
|--------|-----|-------------|
| `OP_DUP` | `0x76` | Duplicate top stack item |
| `OP_DROP` | `0x75` | Remove top stack item |
| `OP_SWAP` | `0x7c` | Swap top two stack items |
| `OP_IFDUP` | `0x73` | Duplicate if not zero |

**Cryptographic:**

| Opcode | Hex | Description |
|--------|-----|-------------|
| `OP_SHA256` | `0xa8` | Hash the top item with SHA-256 |
| `OP_BLAKE2B` | `0xaa` | Hash the top item with Blake2b-256 |
| `OP_CHECKSIGECDSA` | `0xab` | Verify an ECDSA signature against a compressed public key |
| `OP_CHECKSIG` | `0xac` | Verify a Schnorr signature against a public key |
| `OP_CHECKMULTISIG` | `0xae` | Verify M-of-N multisignature |
| `OP_CHECKSIGVERIFY` | `0xad` | `OP_CHECKSIG` followed by `OP_VERIFY` |
| `OP_CHECKMULTISIGVERIFY` | `0xaf` | `OP_CHECKMULTISIG` followed by `OP_VERIFY` |

**Comparison and Logic:**

| Opcode | Hex | Description |
|--------|-----|-------------|
| `OP_EQUAL` | `0x87` | Push true if top two items are equal |
| `OP_EQUALVERIFY` | `0x88` | `OP_EQUAL` followed by `OP_VERIFY` |
| `OP_VERIFY` | `0x69` | Remove top item and fail if false |

<Callout type="warn">
Kaspa provides both `OP_SHA256` and `OP_BLAKE2B`, with Blake2b used by many Kaspa-specific script patterns. Code ported from Bitcoin should verify opcode semantics instead of assuming one-to-one replacements.
</Callout>

### Standard Script Types

**Pay-to-Public-Key (P2PK):**

The most common script type in Kaspa. Locks funds to a Schnorr public key.

```
ScriptPublicKey: <32-byte-pubkey> OP_CHECKSIG
SignatureScript: <64-byte-schnorr-signature>
```

**Pay-to-Script-Hash (P2SH):**

Locks funds to a script hash, enabling complex spending conditions such as multisig.

```
ScriptPublicKey: OP_BLAKE2B <32-byte-script-hash> OP_EQUAL
SignatureScript: <signatures...> <serialized-redeem-script>
```

**Pay-to-Public-Key ECDSA (P2PK-ECDSA):**

An alternative script type using ECDSA signatures for compatibility with existing tooling.

```
ScriptPublicKey: <33-byte-compressed-ecdsa-pubkey> OP_CHECKSIGECDSA
SignatureScript: <der-encoded-ecdsa-signature>
```

## Signature Schemes

Kaspa primarily uses **Schnorr signatures** over the **secp256k1** elliptic curve, with ECDSA available as an alternative.

### Schnorr Signatures (Primary)

Kaspa's default signature scheme uses Schnorr signatures following a scheme compatible with BIP-340, adapted for Kaspa's transaction structure.

| Property | Value |
|----------|-------|
| Curve | secp256k1 |
| Public key size | 32 bytes (x-coordinate only) |
| Signature size | 64 bytes |
| Hash function | Blake2b-256 |
| Signature format | `(R.x, s)` where R is the nonce point |

**Signing process:**

1. Compute the **SigHash** of the transaction input being signed. The SigHash serializes the transaction data according to the `hashType` flag and hashes it with Blake2b.
2. Generate a deterministic nonce `k` using RFC 6979 with Blake2b.
3. Compute `R = k * G` (nonce point on secp256k1).
4. Compute `s = k + e * d` where `e = Blake2b(R.x || pubkey || sigHash)` and `d` is the private key.
5. The signature is the 64-byte concatenation `R.x || s`.

**SigHash types:**

| Type | Value | Description |
|------|-------|-------------|
| `SIGHASH_ALL` | `0x01` | Sign all inputs and outputs (default) |
| `SIGHASH_NONE` | `0x02` | Sign all inputs, no outputs |
| `SIGHASH_SINGLE` | `0x04` | Sign all inputs, only the output at the same index |
| `SIGHASH_ANYONECANPAY` | `0x80` | Can be combined with above; only sign the current input |

<Callout type="info">
Schnorr signatures are preferred over ECDSA because they are more compact, enable efficient batch verification, and allow for native key and signature aggregation schemes.
</Callout>

### ECDSA Signatures (Alternative)

ECDSA is supported for compatibility. ECDSA transactions are distinguished by using a 33-byte compressed public key (instead of 32-byte Schnorr key) in the script.

| Property | Value |
|----------|-------|
| Curve | secp256k1 |
| Public key size | 33 bytes (compressed) |
| Signature size | Variable (DER-encoded, typically 70-72 bytes) |
| Hash function | Blake2b-256 |

## Address Format

Kaspa addresses use the **Bech32** encoding scheme with the prefix `kaspa:`.

| Address Type | Prefix | Payload | Description |
|-------------|--------|---------|-------------|
| P2PK (Schnorr) | `kaspa:q` | 32-byte public key | Standard Schnorr pay-to-public-key |
| P2PK (ECDSA) | `kaspa:q` | 33-byte compressed public key | ECDSA pay-to-public-key |
| P2SH | `kaspa:p` | 32-byte script hash | Pay-to-script-hash |

Testnet addresses use the prefix `kaspatest:` and other network types use their respective prefixes (`kaspasim:`, `kaspadev:`).
