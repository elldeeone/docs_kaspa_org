## Kaspa Improvement Proposals

This page provides a complete index of all Kaspa Improvement Proposals (KIPs). Each KIP goes through the lifecycle described in the [KIPs Overview](/docs/protocol-evolution/kips-overview): Draft, Review, Accepted, Implemented, and Active/Final.

<Callout type="info">
The canonical source for all KIP documents is the [KIPs repository on GitHub](https://github.com/kaspanet/kips). This index is a convenience reference. Always consult the GitHub repository for the latest status and full text of each proposal.
</Callout>

## Active KIPs

These KIPs have been implemented and are active on the Kaspa network.

| KIP | Title | Status | Summary |
|---|---|---|---|
| KIP-1 | Rewriting the Kaspa Full-Node in the Rust Programming Language | Implemented | Defines the rationale and plan for rewriting the Kaspa full-node implementation from Go to Rust, improving performance, memory safety, and maintainability. |
| KIP-4 | Sparse Difficulty Windows | Active | Introduces sparse sampling of the difficulty adjustment window to improve efficiency of the DAA at higher block rates. |
| KIP-5 | Message Signing | Active | Defines a standard for cryptographic message signing using Kaspa keys, enabling proof of ownership and off-chain authentication. |
| KIP-9 | Extended Mass Formula for Mitigating State Bloat | Active | Introduces a storage mass component to the transaction mass calculation. Accounts for the long-term cost of growing the UTXO set by charging mass proportional to the number of outputs created minus inputs consumed. This prevents UTXO bloat attacks that could degrade node performance. |
| KIP-10 | New Transaction Opcodes for Enhanced Script Functionality | Active | Proposes new opcodes for transaction introspection, enabling scripts to inspect their own transaction context. This opens the door to advanced smart contract functionality such as covenants and conditional spending logic on Kaspa. |
| KIP-13 | Transient Storage Handling | Active | Refines the mass model to introduce transient mass, more accurately pricing the bandwidth dimension of transaction cost as a prerequisite for efficient smart contract execution. |
| KIP-14 | The Crescendo Hardfork | Active | The hardfork that transitioned Kaspa from 1 BPS to 10 BPS. Changed GHOSTDAG K from 18 to 124, adjusted DAA window size, finality depth, pruning depth, coinbase maturity, timestamp deviation tolerance, max block parents, and mass limits. Activated on mainnet in May 2025. |
| KIP-15 | Canonical Transaction Ordering and SelectedParent Accepted Transactions Commitment | Active | Defines a canonical ordering for transactions within blocks and commits to the set of accepted transactions from the selected parent, improving verification efficiency and enabling light client support. |

## KIP Categories

**Protocol** — Changes to consensus rules, network protocol, transaction validation, or other aspects that require a node software upgrade. Protocol KIPs that alter consensus rules require a hardfork for activation.

**Informational** — Design documents, best practices, guidelines, or analysis that do not propose protocol changes. These serve as reference material for the ecosystem.

**Process** — Changes to the governance, workflow, or organizational processes of the Kaspa project.

## KIP Status Definitions

| Status | Meaning |
|---|---|
| Draft | Initial submission; open for early feedback |
| Review | Under active community and technical review |
| Accepted | Approved by rough consensus; awaiting implementation |
| Implemented | Code merged into the reference implementation; awaiting activation |
| Active | Activated on mainnet (for protocol KIPs) or considered complete (for process/informational KIPs) |
| Withdrawn | Removed by the author |
| Rejected | Rejected by community consensus |
| Superseded | Replaced by a later KIP |

## Contributing

Anyone can propose a KIP. The process is fully open and permissionless:

1. Review existing KIPs for formatting and submission conventions.
2. Draft your proposal using the standard template.
3. Submit a pull request to the [kaspanet/kips](https://github.com/kaspanet/kips) repository on GitHub.

<Callout type="warn">
Before submitting a new KIP, search the existing proposals and community discussions to ensure your idea has not already been proposed or addressed. Duplicate proposals slow down the review process.
</Callout>
