## Source Location

The Protocol Buffer definitions for Kaspa's gRPC interface are maintained in the [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) repository. The relevant files are located at:

```
rusty-kaspa/
└── rpc/
    └── grpc/
        └── core/
            └── proto/
                ├── messages.proto    # Stream wrapper messages + gRPC service definition
                └── rpc.proto         # RPC request/response and shared model message types
```

For client generation, use both `messages.proto` and `rpc.proto`. The stream service and top-level `KaspadRequest`/`KaspadResponse` wrappers are in `messages.proto`; payload message definitions are in `rpc.proto`.

<Callout type="info">
Always use `.proto` files from the same rusty-kaspa version as the node you connect to. Regenerate stubs when upgrading node versions.
</Callout>

## Service Definition

The gRPC service is defined in `messages.proto` and exposes a bidirectional streaming RPC:

```protobuf
service RPC {
  rpc MessageStream (stream KaspadRequest) returns (stream KaspadResponse);
}
```

All communication flows through this single bidirectional stream. Clients send `KaspadRequest` messages and receive `KaspadResponse` messages (including notification messages for active subscriptions) over the same stream. Each message uses a `oneof` field to identify the specific request or response type.

## Key Message Types

### RpcBlock

Represents a complete block in the Kaspa DAG, including header, transactions, and verbose metadata.

```protobuf
message RpcBlock {
  RpcBlockHeader header = 1;
  repeated RpcTransaction transactions = 2;
  RpcBlockVerboseData verboseData = 3;
}

message RpcBlockHeader {
  uint32 version = 1;
  repeated RpcBlockLevelParents parents = 12;
  string hashMerkleRoot = 3;
  string acceptedIdMerkleRoot = 4;
  string utxoCommitment = 5;
  int64 timestamp = 6;
  uint32 bits = 7;
  uint64 nonce = 8;
  uint64 daaScore = 9;
  string blueWork = 10;
  string pruningPoint = 14;
  uint64 blueScore = 13;
}
```

### RpcTransaction

Represents a transaction with its inputs, outputs, and associated metadata.

```protobuf
message RpcTransaction {
  uint32 version = 1;
  repeated RpcTransactionInput inputs = 2;
  repeated RpcTransactionOutput outputs = 3;
  uint64 lockTime = 4;
  string subnetworkId = 5;
  uint64 gas = 6;
  string payload = 8;
  RpcTransactionVerboseData verboseData = 9;
}

message RpcTransactionInput {
  RpcOutpoint previousOutpoint = 1;
  string signatureScript = 2;
  uint64 sequence = 3;
  uint32 sigOpCount = 5;
  RpcTransactionInputVerboseData verboseData = 4;
}

message RpcTransactionOutput {
  uint64 amount = 1;
  RpcScriptPublicKey scriptPublicKey = 2;
  RpcTransactionOutputVerboseData verboseData = 3;
}
```

### RpcUtxoEntry and RpcOutpoint

Used for UTXO queries and transaction construction.

```protobuf
message RpcOutpoint {
  string transactionId = 1;
  uint32 index = 2;
}

message RpcUtxoEntry {
  uint64 amount = 1;
  RpcScriptPublicKey scriptPublicKey = 2;
  uint64 blockDaaScore = 3;
  bool isCoinbase = 4;
}

message RpcUtxosByAddressesEntry {
  string address = 1;
  RpcOutpoint outpoint = 2;
  RpcUtxoEntry utxoEntry = 3;
}
```

### Common Request/Response Patterns

Most RPC operations follow a consistent request/response pattern. Each request message has a corresponding response message, and every response includes an optional `RPCError` field:

```protobuf
message GetBlockDagInfoRequestMessage {
}

message GetBlockDagInfoResponseMessage {
  string networkName = 1;
  uint64 blockCount = 2;
  uint64 headerCount = 3;
  repeated string tipHashes = 4;
  double difficulty = 5;
  int64 pastMedianTime = 6;
  repeated string virtualParentHashes = 7;
  string pruningPointHash = 8;
  uint64 virtualDaaScore = 9;
  RPCError error = 1000;
}

message SubmitTransactionRequestMessage {
  RpcTransaction transaction = 1;
  bool allowOrphan = 2;
}

message SubmitTransactionResponseMessage {
  string transactionId = 1;
  RPCError error = 1000;
}
```

## Generating Client Code

### Rust

Rust is the native language of rusty-kaspa. Protobuf code generation is handled in the gRPC core workspace (`rpc/grpc/core/build.rs`) and consumed by client/server crates.

```toml
[dependencies]
kaspa-grpc-client = { git = "https://github.com/kaspanet/rusty-kaspa.git", branch = "master" }
kaspa-rpc-core = { git = "https://github.com/kaspanet/rusty-kaspa.git", branch = "master" }
tokio = { version = "1", features = ["full"] }
```

No manual protobuf compilation is required when consuming the existing Rust crates from the workspace.

### Go

```bash
# Install protobuf compiler and Go plugins
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# Generate Go code from proto files
protoc --go_out=. --go-grpc_out=. \
  -I ./proto \
  ./proto/rpc.proto \
  ./proto/messages.proto
```

### Python

```bash
# Install gRPC tools
pip install grpcio grpcio-tools

# Generate Python code
python -m grpc_tools.protoc \
  -I ./proto \
  --python_out=./generated \
  --grpc_python_out=./generated \
  ./proto/rpc.proto \
  ./proto/messages.proto
```

This produces generated modules for both files (for example `rpc_pb2.py`, `messages_pb2.py`, and `messages_pb2_grpc.py`) in the `./generated` directory.

### TypeScript / Node.js

```bash
# Install dependencies
npm install @grpc/grpc-js @grpc/proto-loader

# Or use ts-proto for TypeScript-first generation
npm install ts-proto
protoc --plugin=./node_modules/.bin/protoc-gen-ts_proto \
  --ts_proto_out=./generated \
  --ts_proto_opt=outputServices=grpc-js \
  -I ./proto \
  ./proto/rpc.proto \
  ./proto/messages.proto
```

<Callout>
When generating client code, make sure the `protoc` compiler version is compatible with the proto3 syntax used in Kaspa's `.proto` files. Version 3.x or later of the Protocol Buffers compiler is required.
</Callout>

## Versioning

The protobuf schema evolves with rusty-kaspa releases. Changes follow these conventions:

- **New fields** are typically added with new field numbers.
- **Deprecated fields** may be marked as reserved and should not be reused by clients.
- **Schema changes** can occur across releases, so client stubs should be regenerated during upgrades.

When upgrading your node, regenerate client stubs from the updated `.proto` files to ensure compatibility. The `RPCError` field (always at field number 1000) provides a consistent error reporting mechanism across all response types.
