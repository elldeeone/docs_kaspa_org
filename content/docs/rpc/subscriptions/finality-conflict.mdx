## Overview

The finality-conflict subscription notifies your application when a finality conflict is detected in the network. A finality conflict occurs when the GHOSTDAG selected chain diverges from the finality point -- meaning a block that was previously considered final is no longer on the selected chain.

Finality-conflict notifications are safety-critical and should be treated as high-severity events in monitoring pipelines.

<Callout>
If your application receives a finality conflict notification, treat it as a major network event. Log it, alert operators, and apply your risk controls (for example pausing sensitive processing) until the conflict resolves.
</Callout>

## Subscribe

```typescript
await rpc.subscribeFinalityConflict();
await rpc.subscribeFinalityConflictResolved();
```

**Wire contract note:** wRPC notification control uses `subscribe` / `unsubscribe` with `FinalityConflict` and `FinalityConflictResolved` scopes. gRPC uses `NotifyFinalityConflictRequestMessage` with `command` set to `NOTIFY_START` or `NOTIFY_STOP`.

## Unsubscribe

```typescript
await rpc.unsubscribeFinalityConflict();
await rpc.unsubscribeFinalityConflictResolved();
```

## Notification Format

When a finality conflict is detected:

```json
{
  "violatingBlockHash": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2"
}
```

When a finality conflict is resolved:

```json
{
  "finalityBlockHash": "b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2c3"
}
```

### Fields

| Field | Type | Description |
|---|---|---|
| `violatingBlockHash` | string | Hash of the block causing the finality violation |
| `finalityBlockHash` | string | Hash of the finality point block when the conflict resolves |

## What Triggers a Finality Conflict

Kaspa finality processing is based on blue-score depth. A finality conflict can occur when:

1. A block is beyond finality depth on the selected chain.
2. A competing branch emerges that does not include that finalized block.
3. The competing branch is selected by consensus.

Operationally, this is the kind of scenario where applications should enter a defensive mode until a finality-conflict-resolved event is observed.

## Event Handling

```typescript
rpc.addEventListener("finality-conflict", (event) => {
  if (event.data.violatingBlockHash) {
    console.error(
      `FINALITY CONFLICT: violating block ${event.data.violatingBlockHash}`
    );
    // Alert operators, pause processing
  }
});

rpc.addEventListener("finality-conflict-resolved", (event) => {
  if (event.data.finalityBlockHash) {
    console.log(
      `Finality conflict resolved at block ${event.data.finalityBlockHash}`
    );
    // Resume normal operation
  }
});
```

## Use Cases

- **Security monitoring** -- Alert node operators and exchange administrators when network finality is threatened.
- **Exchange safety** -- Halt deposits and withdrawals during a finality conflict.
- **Network health dashboards** -- Display finality conflict events as critical alerts.

<Callout type="info">
For most applications, subscribing to finality conflicts is a safety measure. You should implement the handler even if you never expect to receive a notification. Think of it as a circuit breaker for your application's interaction with the Kaspa network.
</Callout>
