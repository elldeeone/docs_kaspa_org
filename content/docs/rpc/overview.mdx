## RPC Architecture

Kaspa nodes expose a Remote Procedure Call (RPC) interface that allows external applications to query blockchain state, submit transactions, monitor events via subscriptions, and manage node operations. The RPC layer sits between your application and the Kaspa node's consensus and mempool engines.

Kaspa nodes expose **wRPC** (the primary interface) and **gRPC**. A separate public **REST API** service at `api.kaspa.org` provides HTTP endpoints backed by node data.

## Protocols

### wRPC (WebSocket RPC) -- Primary Interface

wRPC is a high-performance RPC protocol developed in Rust by the Kaspa team, built on standard WebSocket connections. It provides full-duplex communication, meaning the server can push notifications to clients without polling. All RPC methods are available over wRPC.

- **Transport**: Standard WebSockets (`ws://` or `wss://`)
- **Encoding**: Borsh (binary, compact) or JSON (human-readable, WebSocket-framed JSON-RPC-like protocol)
- **Subscriptions**: Full support for real-time event notifications
- **SDK integration**: Fully integrated with the Rust and WASM SDKs, including resolver-based endpoint discovery
- **Best for**: Often used for wallets, explorers, dApps, monitoring tools, and browser-based apps

### gRPC (Protocol Buffers)

gRPC is an open-source universal RPC framework that uses HTTP/2 and Protocol Buffers for strongly-typed communication. It is well-suited for server-to-server integrations where both ends can share `.proto` definitions.

- **Transport**: HTTP/2
- **Encoding**: Protocol Buffers (binary)
- **Subscriptions**: Supported via streaming gRPC
- **Best for**: Often preferred for server-to-server communication and environments that already use protobuf/gRPC tooling

<Callout type="info">
Rusty Kaspa implements streaming gRPC, which may be incompatible with certain routing systems and load balancers. Additionally, much Kaspa data is transmitted as hex or string-serialized formats over gRPC, which reduces the efficiency gains typically associated with protobuf encoding. gRPC has no integration with the Kaspa WASM SDK.
</Callout>

### REST (via api.kaspa.org)

A public REST API is available at `api.kaspa.org` for simple HTTP queries and selected operations (including transaction submission). It wraps a subset of RPC methods behind standard HTTP endpoints.

- **Transport**: HTTPS
- **Encoding**: JSON
- **Best for**: Simple queries, quick prototyping, browser-based tools that need CORS support

## Choosing a Protocol

| Use Case | Recommended Protocol | Reason |
|----------|---------------------|--------|
| Wallet or dApp development | wRPC (JSON or Borsh) | Full SDK integration, subscriptions |
| Real-time monitoring / subscriptions | wRPC | Full-duplex WebSocket push |
| Browser-based applications | wRPC (JSON) or REST | Supported by modern browsers and standard HTTP tooling |
| High-performance server integration | gRPC | Strong typing, HTTP/2 transport, code generation |
| Go / Python / Java backends | gRPC | Works well with standard protobuf/gRPC toolchains |
| Simple balance or UTXO lookups | REST | No SDK needed, standard HTTP |
| Mining software | wRPC or gRPC | Both support block template subscriptions |

<Callout>
wRPC is commonly used for application-facing integrations. It provides access to all RPC methods, supports subscriptions for real-time updates, and works in both Node.js and browser environments via the Kaspa WASM SDK. The JSON encoding enables straightforward third-party integration.
</Callout>

## Encoding Options

wRPC supports two encoding formats on separate ports:

- **Borsh** (Binary Object Representation Serializer for Hashing): A compact binary format used natively by the Rust and WASM SDKs. It is often preferred for performance-sensitive applications.
- **JSON**: Human-readable format following a WebSocket-framed JSON-RPC-like protocol. Easier to debug and inspect, and often convenient for browser development and third-party integrations.

Both encodings expose identical methods and return identical logical data. The only difference is wire format and port number.

## Client Libraries

### WASM / JavaScript / TypeScript

The Kaspa WASM SDK compiles the core Rust codebase to WebAssembly with an idiomatic JavaScript/TypeScript API. It includes:

- **`RpcClient`** -- Main RPC class for interacting with the node over wRPC
- **`Resolver`** -- Endpoint discovery for resolver-backed deployments (including public-node setups)
- Full wallet operations, transaction construction, and event subscriptions

```bash
npm install kaspa-wasm
```

See the [WASM SDK documentation](/docs/sdks/wasm-sdk) for installation and usage details.

### Rust

The Rust SDK provides native access to wRPC and gRPC clients:

- **`KaspaRpcClient`** (in `kaspa-wrpc-client`) -- wRPC client with Borsh and JSON encoding support
- **`GrpcClient`** (in `kaspa-grpc-client`) -- gRPC client built on the `tonic` crate
- **`RpcApi` trait** -- Defines all RPC methods, shared across both transports
- **`Resolver`** -- Endpoint resolution for resolver-backed environments

See the [Rust Crates documentation](/docs/sdks/rust-crates) for crate dependencies and usage.

### Python

The Python SDK provides PyO3 bindings to the core Rust crates, supporting RPC communication, wallet operations, and transaction construction.

See the [Python SDK documentation](/docs/sdks/python-sdk) for installation and usage.

### gRPC Code Generation

The gRPC `.proto` files can be used to generate client code in languages supported by protobuf/gRPC tooling. Protocol definition files (`messages.proto` and `rpc.proto`) are maintained in the [rusty-kaspa repository](https://github.com/kaspanet/rusty-kaspa/tree/master/rpc/grpc/core/proto).

## Public Node Network (PNN)

The Public Node Network (PNN) refers to community-operated public Kaspa RPC infrastructure that can be used by applications that do not run their own node.

<Callout type="info">
Operational guidance (non-normative): PNN topology, routing policy, capacity management, and onboarding processes are service-level choices outside the node RPC protocol and can change over time.
</Callout>

### Appropriate Use Cases

PNN nodes are well-suited for:
- Web wallets and browser-based applications
- Development and testing
- Community tools and explorers

<Callout type="warn">
PNN nodes are community-operated and best-effort. Exchanges, high-volume production systems, and applications handling significant value should run their own dedicated node rather than relying on PNN infrastructure.
</Callout>

## Resolver Architecture

The Resolver is an SDK-facing endpoint discovery component used by Rust and WASM clients.

### Client-Side Behavior (Protocol-Backed)

1. If no explicit URL is provided, the client asks the resolver for an endpoint.
2. The client connects to the returned endpoint.
3. On reconnect attempts, the client can resolve again and connect to another endpoint.

### SDK Integration

The Resolver API is built directly into the Rust and WASM SDKs. Rather than specifying a fixed endpoint URL, developers pass a `Resolver` object that dynamically retrieves the optimal node endpoint for each connection attempt:

```typescript
import { RpcClient, Resolver, Encoding } from "kaspa-wasm";

const rpc = new RpcClient({
  resolver: new Resolver(),
  encoding: Encoding.Borsh,
  networkId: "mainnet",
});
await rpc.connect();
```

<Callout type="info">
Operational guidance (non-normative): endpoint ranking and failover policy are resolver-service behaviors and may vary by deployment.
</Callout>

### Private Clusters

Resolver deployments can also be used to create private node clusters for your own infrastructure.

The Resolver source code is available at [github.com/aspectron/kaspa-resolver](https://github.com/aspectron/kaspa-resolver).

## Proxies and Relay Infrastructure

HTTP proxies can be placed in front of Kaspa nodes to route traffic while maintaining security. Proxies enable:

- Exposing wRPC endpoints to the public internet without direct node exposure
- Mapping multiple nodes or networks to different subdomains or URL paths
- Adding TLS termination for secure `wss://` connections
- Can be configured for load balancing across multiple nodes

NGINX is commonly used as a reverse proxy for Kaspa nodes. It can be configured to route WebSocket traffic to different node instances based on URL path, enabling a single proxy to serve mainnet, testnet, and multiple encoding formats simultaneously.

<Callout type="info">
NGINX capacity depends on your `worker_connections` and worker process settings. For high-traffic deployments, tune `worker_connections` in `nginx.conf` and validate limits under realistic load.
</Callout>

## kHOST

[kHOST](https://github.com/aspectron/khost) is a Rust-based deployment automation tool for deploying and managing Kaspa nodes. Adoption and operating patterns vary by environment.

## RPC Availability

### Verifying Node Availability

Two methods are available to verify that an RPC server is operational:

**Rusty Kaspa CLI Wallet**: Download the latest release and run:
```
network mainnet
connect localhost
rpc get-info
```

**Kaspa NG Desktop**: Configure the settings to connect to a remote node by selecting the network, setting the connection type to "Remote", and entering the wRPC connection URL.

<Callout type="warn">
The online version of Kaspa NG at kaspa-ng.org cannot connect to a local RPC server. Browser security policies require SSL-secured endpoints, while local RPC servers typically lack SSL encryption. Use the desktop version or place a TLS-terminating proxy in front of your node.
</Callout>

### When to Use Public Nodes vs Your Own Node

**Use public nodes (PNN) when:**
- Developing and testing applications
- Building browser-based wallets or tools
- Prototyping and experimenting with the RPC API
- Building community tools with moderate traffic

**Run your own node when:**
- Operating an exchange or payment processor
- Running high-volume production systems
- Requiring guaranteed uptime and reliability
- Needing full control over node configuration and version
- Processing transactions with significant value

## Subscription Model

wRPC supports a full-duplex subscription model. Clients can subscribe to events such as new blocks, UTXO changes for specific addresses, or virtual chain updates. When subscribed, the node pushes notifications to the client over the same WebSocket connection -- no polling required.

Subscriptions are managed with paired `subscribe` and `unsubscribe` calls. See the [Subscriptions](/docs/rpc/subscriptions) section for details on available notification types.

## Authentication and Security

<Callout type="info">
Kaspa's RPC interface has no built-in authentication mechanism. Any client that can reach the RPC port can issue exposed RPC calls. State-changing administrative calls such as `Shutdown` require starting the node with `--unsaferpc`.
</Callout>

To secure your node's RPC interface:

- **Firewall rules**: Restrict RPC port access to trusted IP addresses.
- **VPN / private network**: Run your node on a private network and expose RPC only to authorized services.
- **Bind address**: Configure the node to listen on `127.0.0.1` (localhost) rather than `0.0.0.0` if only local access is needed.
- **Reverse proxy with TLS**: Place a reverse proxy (e.g., NGINX) in front of the RPC port to add TLS encryption and optional authentication headers.

## Rate Limiting

Kaspa exposes RPC connection limits (for example, max client settings) but does not provide built-in request-per-second quota controls at the RPC layer. If you expose an RPC endpoint publicly, place a rate-limiting proxy in front of it. Public infrastructure such as the Resolver service and `api.kaspa.org` may apply their own service-level limits.
