## What Is the WASM SDK?

The Kaspa WASM SDK is the official Rust codebase compiled to WebAssembly and exposed through an idiomatic JavaScript/TypeScript API. It brings the full power of the `rusty-kaspa` wallet, RPC, and transaction-building logic to browser and Node.js environments with near-native performance. Because it is compiled from the same Rust source as the node, all consensus-critical operations are guaranteed to match the canonical implementation.

The WASM32 bindings can be used in both TypeScript and JavaScript environments. In JavaScript, types are not constrained by TypeScript type definitions; in TypeScript, full type information is available. Note that names on the JavaScript side use `camelCase` convention while the underlying Rust source uses `snake_case`.

The SDK is separated into the following top-level categories:

- **RPC API** -- WebSocket RPC for the Kaspa node.
- **Wallet SDK** -- Bindings for primitives related to key management and transactions.
- **Wallet API** -- API for the Rusty Kaspa Wallet framework.

## Installation

Install from npm:

```bash
npm install kaspa-wasm
```

A convenience wrapper package called `kaspa` is also available. It automatically installs the W3C WebSocket shim required for Node.js and re-exports all `kaspa-wasm` exports:

```bash
npm install kaspa
```

<Callout type="info">
The package name may vary across release channels. Check the [rusty-kaspa repository](https://github.com/kaspanet/rusty-kaspa) for the latest published package name and version.
</Callout>

### Release Package Variants

The SDK is distributed as multiple packages optimized for different use cases:

**Web Browser packages (4 variants):**

| Package | Contents |
|---|---|
| KeyGen | Key and address generation only (smallest binary) |
| RPC | RPC functionality only |
| Core | RPC + Key and Address Generation + Wallet SDK |
| Full | Full SDK + Integrated Wallet |

**Node.js package:** A single package containing all features.

The release folder structure is organized as follows:

- `web/kaspa` -- Full WASM32 SDK bindings for web browsers.
- `web/kaspa-rpc` -- RPC-only bindings for web browsers (reduced WASM binary size).
- `nodejs/kaspa` -- Full WASM32 SDK bindings for Node.js.
- `docs` -- TypeDoc-generated API documentation.
- `examples/` -- Example code for both Node.js and web browsers.

### Redistributables

Pre-built WASM redistributables are available for both web browsers and Node.js.

**Stable releases:** Download from the [rusty-kaspa GitHub releases](https://github.com/kaspanet/rusty-kaspa/releases) page.

**Development releases:** Nightly builds are available at [kaspa.aspectron.org/nightly/downloads/](https://kaspa.aspectron.org/nightly/downloads/). The latest development build is always available as `rusty-kaspa-wasm32-sdk-latest.zip`.

<Callout type="info">
The entire framework can also be built from Rusty Kaspa sources into WASM, or used within Rust directly by depending on the crates. See [Building from Source](#building-from-source) below.
</Callout>

## Platform Support

The SDK supports the following environments:

| Platform | Status | Notes |
|---|---|---|
| Chrome, Firefox, Safari, Edge | Supported | Requires async WASM initialization |
| Node.js 16+ | Supported | Synchronous module loading; needs WebSocket shim |
| Bun | Supported | No WebSocket shim required |
| Deno | Experimental | ESM imports |
| React Native | Experimental | Community-tested |

## Browser Integration

Loading the Kaspa WASM SDK in a web browser requires importing the JavaScript ES6 module and awaiting the WASM bootstrap initialization. Both the JavaScript glue code (`kaspa-wasm.js`) and the WebAssembly binary (`kaspa-wasm_bg.wasm`) must be served together.

```html
<html>
    <head>
        <script type="module">
            import * as kaspa from './kaspa/kaspa-wasm.js';
            (async () => {
                await kaspa.default('./kaspa/kaspa-wasm_bg.wasm');
                console.log(kaspa.version());
                // SDK is now ready to use
            })();
        </script>
    </head>
    <body></body>
</html>
```

<Callout type="warn">
WASM modules cannot be loaded using the `file://` protocol. You must serve the application from a web server, even during local development.
</Callout>

### Key Points for Browser Loading

- The `import` statement loads the JavaScript glue module.
- Calling `kaspa.default()` with the path to the `.wasm` file triggers the asynchronous download, compilation, and instantiation of the WebAssembly module.
- No SDK classes or functions are usable until the `await` resolves.
- For development, you can use any static file server. A simple option:

```bash
cargo install http-server
http-server
```

### Content Security Policy (CSP)

If your application uses a strict Content Security Policy, ensure the following directives are set:

- `script-src 'wasm-eval'` or `script-src 'wasm-unsafe-eval'` -- Required to compile and execute WebAssembly.
- `connect-src ws: wss:` -- Required for WebSocket RPC connections.

### Panic Hooks

The SDK provides panic hooks for debugging. In a browser environment, you can enable a full-page overlay that displays panic details (useful on mobile where the console is not accessible):

```javascript
kaspa.initBrowserPanicHook();
```

## Node.js Integration

In Node.js, the WASM module loads synchronously as a CommonJS module. No async initialization step is required.

```javascript
// If using kaspa-wasm directly (not the kaspa wrapper), apply the WebSocket shim:
globalThis.WebSocket = require('websocket').w3cwebsocket;

let {
    RpcClient,
    Encoding,
    Resolver,
    initConsolePanicHook
} = require('./kaspa');

// Enable console panic hooks for detailed error output
initConsolePanicHook();
```

### WebSocket Shim Requirement

Node.js does not include a W3C-compatible WebSocket implementation. Before using `RpcClient`, you must install and apply a WebSocket shim.

The recommended package is [websocket](https://www.npmjs.com/package/websocket) (version 1.0.34 or later):

```json
{
  "dependencies": {
    "websocket": "1.0.34"
  }
}
```

Apply the shim before loading the SDK:

```javascript
globalThis.WebSocket = require('websocket').w3cwebsocket;
```

<Callout type="info">
If you install the `kaspa` npm package (as opposed to `kaspa-wasm`), the WebSocket shim is automatically installed in `globalThis` for you. The shim is not needed in browsers or the Bun runtime.
</Callout>

### ESM vs CommonJS

The Node.js build is packaged as a CommonJS module. Use `require()` to load it:

```javascript
const kaspa = require('kaspa');
```

If you are working in an ESM environment, use a dynamic import or the `createRequire` helper:

```javascript
import { createRequire } from 'module';
const require = createRequire(import.meta.url);
const kaspa = require('kaspa');
```

The web browser build is an ES6 module and uses standard `import` syntax.

## Building from Source

To build the WASM32 SDK from source, you need the Rust toolchain installed. Follow the setup instructions in the [Rusty Kaspa README](https://github.com/kaspanet/rusty-kaspa).

### Prerequisites

- **Rust** (latest stable) with the `wasm32-unknown-unknown` target
- **wasm-pack** for building the WASM output
- **Node.js** (for running examples and building documentation)
- **TypeDoc** installed globally: `npm install -g typedoc` (needed for release builds and documentation)
- **clang / LLVM** (required by some native dependencies on certain platforms)

### Build Commands

Run these scripts from the `wasm/` directory of the rusty-kaspa repository:

| Command | Description |
|---|---|
| `./build-release` | Build the full release (WASM SDK + docs). Includes both release and debug builds. |
| `./build-web` | Build only the web browser package (ES6 module) |
| `./build-node` | Build only the Node.js package (CommonJS module) |
| `./build-docs` | Run `build-web`, then generate TypeDoc documentation from the result |

### Running Examples After Building

Once built from source, you can run the Node.js examples:

```bash
cd wasm
./build-release
cd examples
npm install
node init
node nodejs/javascript/general/rpc.js
```

The `node init` command creates a local `examples/data/config.json` containing a private key (mnemonic) shared across Node.js examples. Most examples accept the following arguments:

```bash
node <script> [address] [mainnet|testnet-10|testnet-11] \
  [--address <address>] \
  [--network <mainnet|testnet-10|testnet-11>] \
  [--encoding <borsh|json>]
```

By default, all wRPC connections use Borsh binary encoding.

For web examples, serve the files from a local web server rooted at the SDK folder:

```bash
cargo install http-server
http-server
# Access examples at http://localhost:7878/examples/web/index.html
```

### IDE Configuration

If you are using JavaScript with Visual Studio Code, replicate the `jsconfig.json` configuration file from the SDK examples. This enables TypeScript-like code completion, type checking, and inline documentation even in plain JavaScript projects.

## Security Considerations

<Callout type="warn">
When building applications that handle private keys or real funds, treat security as a first-class concern at every layer of the stack.
</Callout>

### Supply Chain Security

Third-party JavaScript and Node.js module dependencies should be treated as potentially insecure due to a variety of attack vectors, including code injection vulnerabilities in transitive dependencies. To mitigate these risks:

- **Build from source.** For security-critical applications, build the WASM SDK directly from the Rust source code yourself, or obtain pre-built binaries and embed them directly into your project.
- **Pin dependency versions.** When using npm, set fixed dependency versions including patch numbers (e.g., `"kaspa-wasm": "0.15.1"` rather than `"^0.15.1"`) to prevent unexpected automatic updates.
- **Audit dependencies.** Manually review all direct and transitive dependencies before integrating them into production applications.

### Serving WASM Libraries

It is strongly recommended to serve WASM libraries and associated JavaScript from a server you control. Serving from CDNs or third-party servers can expose your application to code injection attacks if the CDN is compromised.

### Subresource Integrity (SRI)

When loading WASM or scripts via `<script>` tags from any external source, use the `integrity` attribute to verify the resource has not been tampered with:

```html
<script
  src="https://example.com/kaspa-wasm.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous">
</script>
```

Generate the integrity hash for your specific files and update it each time you deploy a new version. For more information, see the [MDN Subresource Integrity documentation](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity).

### Key Management in the Browser

Browser environments pose unique challenges for key management:

- **Never store private keys or mnemonics in localStorage, sessionStorage, or cookies.** These storage mechanisms are accessible to any script running on the same origin, including injected third-party scripts.
- **Minimize key lifetime.** Derive keys on demand, use them for signing, and discard them. Avoid keeping private key material in memory longer than necessary.
- **Use secure contexts.** Always serve applications over HTTPS. WebCrypto APIs and certain WASM features may be restricted in insecure contexts.
- **Isolate sensitive operations.** Consider performing signing operations in a Web Worker to reduce the attack surface from DOM-based XSS.

## Core Modules

- **`RpcClient`** -- WebSocket RPC client supporting Borsh and JSON encodings.
- **`Resolver`** -- Automatic public node discovery for a given network.
- **`UtxoProcessor` / `UtxoContext`** -- Tracks addresses, caches unspent outputs, emits balance-change events.
- **`PrivateKey` / `PublicKey`** -- Schnorr key pair generation over secp256k1.
- **`Address`** -- Bech32 address creation, parsing, and validation.
- **`Mnemonic` / `XPrv`** -- BIP-39 mnemonics and BIP-32 HD key derivation (`m/44'/111111'/0'`).
- **`createTransactions`** -- Transaction builder with automatic UTXO selection, fee calculation, and compound chaining.

## Connecting to a Node

Using the `Resolver` for automatic public node discovery:

```typescript
import { RpcClient, Encoding, Resolver } from 'kaspa-wasm';

const rpc = new RpcClient({
  resolver: new Resolver(),
  encoding: Encoding.Borsh,
  networkId: "mainnet",
});
await rpc.connect();
const info = await rpc.getBlockDagInfo();
console.log("Network:", info.networkName, "DAA score:", info.virtualDaaScore);
```

Connecting directly to your own node:

```typescript
const rpc = new RpcClient({
  url: "127.0.0.1",
  encoding: Encoding.Borsh,
  networkId: "testnet-10",
});
```

If a port is not specified, the SDK will use the default port for the given network.

<Callout type="warn">
Public nodes are suitable for development and testing. For production applications handling real funds, always run your own Kaspa node.
</Callout>

### Node.js Connection Example

A complete Node.js example using CommonJS:

```javascript
globalThis.WebSocket = require('websocket').w3cwebsocket;

let kaspa = require('./kaspa');
let { RpcClient, Resolver } = kaspa;

kaspa.initConsolePanicHook();

const rpc = new RpcClient({
    resolver: new Resolver(),
    networkId: "mainnet",
});

(async () => {
    try {
        await rpc.connect();
        console.log(`Connected to ${rpc.url}`);
        const info = await rpc.getBlockDagInfo();
        console.log(info);
    } finally {
        await rpc.disconnect();
    }
})();
```

## Creating a Wallet

```typescript
import { Mnemonic, XPrv } from 'kaspa-wasm';

const mnemonic = Mnemonic.random(24);
const seed = mnemonic.toSeed("");
const xprv = new XPrv(seed);
const account = xprv.derivePath("m/44'/111111'/0'");
const receiveKey = account.derivePath("0/0").toPrivateKey();
const address = receiveKey.toPublicKey().toAddress("mainnet");
console.log("Address:", address.toString());
```

## Tracking Balances and Sending Transactions

Use `UtxoProcessor` to track UTXOs, then `createTransactions` to build, sign, and submit:

```typescript
import { UtxoProcessor, UtxoContext, createTransactions, kaspaToSompi, PrivateKey } from 'kaspa-wasm';

const processor = new UtxoProcessor({ rpc, networkId: "mainnet" });
const context = new UtxoContext({ processor });
await processor.start();
await context.trackAddresses(["kaspa:qr35..."]);

// Build and send a transaction
const privateKey = new PrivateKey("your-hex-key");
const sender = privateKey.toPublicKey().toAddress("mainnet").toString();
const { transactions } = await createTransactions({
  entries: context,
  outputs: [{ address: "kaspa:recipient", amount: kaspaToSompi(1.5) }],
  changeAddress: sender,
  priorityFee: 0n,
});
for (const tx of transactions) {
  tx.sign([privateKey]);
  console.log("Submitted:", await tx.submit(rpc));
}
```

<Callout>
If the wallet contains many small UTXOs (common for miners), `createTransactions` automatically produces a chain of compound transactions that consolidate UTXOs before the final transfer. Sign and submit each transaction in order.
</Callout>

## Subscribing to Events

The RPC client supports real-time subscriptions for blocks, UTXO changes, and DAA score updates:

```typescript
await rpc.subscribeBlockAdded();
rpc.addEventListener("block-added", (e) => console.log("Block:", e.data.block.header.hash));

await rpc.subscribeUtxosChanged(["kaspa:your-address"]);
rpc.addEventListener("utxos-changed", (e) => {
  for (const entry of e.data.added) console.log("Received:", entry.utxoEntry.amount, "sompi");
});
```

## Error Handling and TypeScript

Wrap SDK calls in try/catch blocks. Common errors include connection failures, insufficient funds, and UTXO sync issues:

```typescript
try {
  await rpc.connect();
} catch (err) {
  console.error("Connection failed:", err.message);
}
```

The SDK ships with full TypeScript declarations -- all classes, method signatures, event payloads, and option objects are typed, with `BigInt` support for sompi amounts.
