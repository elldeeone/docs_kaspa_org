## SDK Layers

Kaspa application tooling is anchored in the `rusty-kaspa` codebase. The two canonical integration paths documented in this docs set are:

- **Rust crates** for native/infrastructure applications.
- **WASM SDK** for JavaScript/TypeScript browser and Node.js applications.

Other language wrappers may exist, but their API coverage and maintenance vary by project.

## Choosing an Integration Path

| Use Case | Preferred Path | Reason |
|---|---|---|
| Browser app / frontend wallet | [WASM SDK](/docs/sdks/wasm-sdk) | Official JS/TS bindings and wallet/RPC primitives |
| Node.js backend service | [WASM SDK](/docs/sdks/wasm-sdk) | Shared JS/TS runtime and RPC/event model |
| Native infrastructure service | [Rust Crates](/docs/sdks/rust-crates) | Direct crate-level control and performance |
| Language not officially covered | [Community SDKs](/docs/sdks/community-sdks) | Evaluate third-party wrappers against official behavior |

## Capability Guidance

Capabilities such as RPC calls, transaction construction, and address handling are fully documented for Rust/WASM in this docs set. For external wrappers (including Python/community projects), treat capability claims as project-specific and verify directly in that project's repository/docs.

<Callout type="info">
Rust and WASM documentation in this site tracks primary-source `rusty-kaspa` behavior. External wrappers should be validated against the same primary sources before production use.
</Callout>

## Transport Protocols

- **wRPC**: Primary application transport for SDK integrations.
- **gRPC**: Useful for infrastructure and generated clients in multiple languages.

Both require a running Kaspa node endpoint.

## Network Identifiers

Use explicit network identifiers in SDK configs:

| Network | Identifier | Address Prefix | Use |
|---|---|---|---|
| Mainnet | `mainnet` | `kaspa:` | Production |
| Testnet | `testnet-10` | `kaspatest:` | Public testing |
| Simnet | `simnet` | `kaspasim:` | Local development |
