## Current Position

Python integrations exist in the ecosystem, but package names, API surfaces, and maintenance status can change. Treat Python support as project-specific and verify the exact repository/version before adopting.

<Callout type="warn">
Do not assume feature parity with Rust/WASM unless the Python project explicitly documents and tests that parity against current `rusty-kaspa` behavior.
</Callout>

## Stable Python Integration Paths

### Option 1: Generate a gRPC Client

Use Kaspa protobuf definitions from `rusty-kaspa/rpc/grpc/core/proto` and generate Python stubs:

```bash
python -m grpc_tools.protoc \
  -I /path/to/rusty-kaspa/rpc/grpc/core/proto \
  --python_out=. \
  --grpc_python_out=. \
  /path/to/rusty-kaspa/rpc/grpc/core/proto/messages.proto \
  /path/to/rusty-kaspa/rpc/grpc/core/proto/rpc.proto
```

This keeps schemas tied to canonical node sources.

### Option 2: Use a Community Python Wrapper

If you use a published package/wrapper:

1. Pin an explicit version.
2. Validate key flows (address derivation, send, confirmation tracking).
3. Compare critical outputs against Rust/WASM fixtures.
4. Track upstream protocol changes and retest on upgrades.

## Production Checklist

- Verify supported network identifiers and address formats.
- Verify transaction and fee behavior with controlled fixtures.
- Verify reconnect/subscription handling under node restarts.
- Verify recovery and deterministic key derivation behavior.

## Recommendation

For strict correctness requirements, use Rust crates directly or WASM in a Node service boundary, then expose a Python-facing service/API layer. This reduces protocol drift risk in long-lived Python systems.
