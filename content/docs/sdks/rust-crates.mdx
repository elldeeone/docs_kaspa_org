## Overview

The [rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) repository is a Cargo workspace containing dozens of interconnected crates that implement Kaspa's full node, wallet, RPC layer, and consensus engine. As an application developer, you can depend on individual crates to build native tools, services, and integrations without pulling in the entire node. Because these crates are the canonical implementation, the WASM and Python SDKs are both derived from them.

## Crate Taxonomy

The rusty-kaspa workspace can be divided into two broad categories:

- **Client crates** are intended for application developers building wallets, tools, and integrations. These crates provide transaction construction, RPC communication, address handling, and wallet functionality. You can depend on them without pulling in the full node.
- **Node crates** implement the internals of kaspad itself — consensus, mining, P2P networking, database storage, and server-side RPC. Application developers rarely need these directly, but they are available for building custom node variants or deep infrastructure.

## Key Client Crates

| Crate | Purpose |
|---|---|
| `kaspa-consensus-core` | Core types: `Transaction`, `Block`, `Header`, `Hash`, network config |
| `kaspa-consensus-client` | Client-side consensus utilities for transaction construction and validation |
| `kaspa-wallet-core` | HD wallet, key derivation, UTXO tracking, transaction creation |
| `kaspa-wallet-keys` | Key management, keypair generation, and signing primitives |
| `kaspa-wallet-pskt` | PSKT (Partially Signed Kaspa Transaction) support for multisig workflows |
| `kaspa-rpc-core` | RPC message types, request/response structures, `RpcApi` trait |
| `kaspa-wrpc-client` | wRPC (WebSocket RPC) client for connecting to nodes |
| `kaspa-grpc-client` | gRPC client for connecting to nodes via gRPC |
| `kaspa-txscript` | Script engine for locking/unlocking scripts |
| `kaspa-addresses` | Bech32 address encoding, decoding, validation |
| `kaspa-hashes` | Blake2b and other protocol hash functions |
| `kaspa-bip32` | BIP-32 hierarchical deterministic key derivation |
| `kaspa-math` | Numeric utilities used across the protocol (difficulty, target calculations) |
| `kaspa-pow` | Proof-of-work validation and kHeavyHash primitives |
| `kaspa-utils` | Shared utility types and helpers used across the workspace |
| `kaspa-wasm-core` | Core types and utilities shared by WASM bindings |

## Key Node Crates

| Crate | Purpose |
|---|---|
| `kaspa-consensus` | Full consensus engine: GHOSTDAG, DAA, pruning, block validation |
| `kaspa-mining` | Block template construction and mining manager |
| `kaspa-p2p-lib` | Peer-to-peer networking layer (protocol messages, connection management) |
| `kaspa-grpc-server` | gRPC server exposing the node's RPC interface |
| `kaspa-wrpc-server` | wRPC server (WebSocket) exposing the node's RPC interface |
| `kaspa-database` | RocksDB storage abstraction for consensus and UTXO data |
| `kaspa-merkle` | Merkle tree construction and verification for block headers |

<Callout type="info">
Crate names and module boundaries may change between releases. Always check the workspace `Cargo.toml` in the rusty-kaspa repository for current crate names and versions.
</Callout>

## Adding Dependencies

Pin crates to the same Git revision for compatibility:

```toml
[dependencies]
kaspa-consensus-core = { git = "https://github.com/kaspanet/rusty-kaspa", branch = "master" }
kaspa-wrpc-client = { git = "https://github.com/kaspanet/rusty-kaspa", branch = "master" }
kaspa-wallet-core = { git = "https://github.com/kaspanet/rusty-kaspa", branch = "master" }
tokio = { version = "1", features = ["full"] }
```

<Callout type="warn">
Depending on a Git branch means your build tracks upstream changes. For reproducible production builds, pin to a specific commit hash or tag instead of `branch = "master"`.
</Callout>

## Connecting via RPC

```rust
use kaspa_wrpc_client::prelude::*;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = KaspaRpcClient::new(
        WrpcEncoding::Borsh,
        Some("ws://127.0.0.1:16110"),
        None,
        Some(NetworkId::new(NetworkType::Mainnet)),
        None,
    )?;
    client.connect(None).await?;

    let info = client.get_block_dag_info().await?;
    println!("Network: {}", info.network_name);
    println!("Block count: {}", info.block_count);
    println!("Virtual DAA score: {}", info.virtual_daa_score);

    client.disconnect().await?;
    Ok(())
}
```

## Constructing a Transaction

```rust
use kaspa_consensus_core::tx::*;
use kaspa_consensus_core::subnets::SUBNETWORK_ID_NATIVE;
use kaspa_addresses::Address;

let outpoint = TransactionOutpoint::new(
    kaspa_hashes::Hash::from_str("abcdef...")?, 0,
);
let input = TransactionInput {
    previous_outpoint: outpoint,
    signature_script: vec![],
    sequence: 0,
    sig_op_count: 1,
};

let recipient: Address = "kaspa:qr35...".try_into()?;
let output = TransactionOutput {
    value: 150_000_000, // 1.5 KAS in sompi
    script_public_key: kaspa_txscript::pay_to_address_script(&recipient),
};

let tx = Transaction::new(
    0, vec![input], vec![output], 0,
    SUBNETWORK_ID_NATIVE, 0, vec![],
);
```

<Callout>
In practice, use `kaspa-wallet-core`'s transaction builder rather than constructing transactions manually. The wallet crate handles UTXO selection, change outputs, fee estimation, compound transaction chaining, and signing in a single call.
</Callout>

## Subscribing to Events

```rust
use kaspa_wrpc_client::prelude::*;

client.start_notify(
    ListenerId::default(),
    Scope::BlockAdded(BlockAddedScope {}),
).await?;

client.start_notify(
    ListenerId::default(),
    Scope::UtxosChanged(UtxosChangedScope {
        addresses: vec!["kaspa:qr35...".try_into()?],
    }),
).await?;
```

## When to Use Rust vs WASM

Choose **Rust crates** when building infrastructure (mining pools, indexers, custom nodes) or when you need maximum performance, full `tokio` async concurrency, and direct access to consensus internals. Choose the **WASM SDK** when targeting the browser or Node.js, or when developer velocity in TypeScript matters more than the modest WASM performance overhead.

## API Documentation

Auto-generated TypeDoc-style API documentation for the Kaspa Rust/WASM crates is available at [kaspa.aspectron.org/docs](https://kaspa.aspectron.org/docs/). This provides browsable type definitions, method signatures, and module documentation derived from the source code.

## PSKT Multisig Example

The `kaspa-wallet-pskt` crate implements Partially Signed Kaspa Transactions (PSKT), enabling multisig workflows where multiple parties independently sign a transaction before it is finalized and broadcast. A reference example demonstrating the PSKT multisig flow is available in the rusty-kaspa repository at [wallet/pskt/examples](https://github.com/kaspanet/rusty-kaspa/tree/master/wallet/pskt/examples).
