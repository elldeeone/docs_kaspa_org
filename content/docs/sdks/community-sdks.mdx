## Scope

This page covers how to evaluate non-official SDKs and client libraries. Community projects can be useful, but they are not canonical protocol references.

<Callout type="warn">
For production signing and transaction generation, prefer official SDKs first. Use community SDKs only after compatibility and security review.
</Callout>

## Where to Discover Community Projects

- GitHub repositories and organization projects related to Kaspa.
- Language package registries (`pkg.go.dev`, NuGet, npm, PyPI, etc.).
- Community channels for maintenance/activity signals.

Treat discovery listings as starting points, not endorsements.

## Evaluation Checklist

1. Verify active maintenance (recent commits, issue triage, release cadence).
2. Verify protocol/network compatibility with current Kaspa node behavior.
3. Verify address handling, serialization, and signing against known vectors.
4. Verify dependency and supply-chain risk (direct + transitive dependencies).
5. Verify recoverability and deterministic behavior for wallet-related tooling.

## Minimum Technical Requirements

A usable SDK/client should correctly handle:

- RPC transport and request/response correlation.
- Kaspa address parsing/validation and network identifiers.
- UTXO and transaction structure handling.
- Signature workflows and fee/mass-related behavior.
- Subscription/event lifecycles for real-time updates.

## Recommended Validation Strategy

1. Start on `testnet-10` or `simnet`.
2. Run end-to-end tests: receive, send, confirmation tracking, and reorg handling.
3. Compare outputs with official Rust/WASM behavior for the same fixtures.
4. Promote to mainnet only after deterministic parity checks pass.

## If You Are Building a New Community SDK

1. Start from RPC correctness and schema compatibility.
2. Add address/key primitives next.
3. Add transaction construction/signing only after test vectors are in place.
4. Publish versioned docs with explicit network/version support.
5. Document incompatibilities and unsupported features clearly.
